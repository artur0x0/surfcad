# Architecture

**Maintenance:** every PR that changes kernel helpers, face/edge/contour graphs, multi-body rules, or UI pickers must update this file in the same PR (or a tiny follow-up before the next feature). Drop stale sections when behavior changes.

Runtime map for SurfCAD. The vault format is `docs/vault-schema.md`. Screen placement is `docs/ui-map.md`. UI text, color, and popup chrome are `docs/ui-style-guide.md`. Blend kernels are `.claude/skills/fillets/SKILL.md`. Fillet and graph speed is `docs/performance.md`. The agent catalog contract, and the live `window.surfcad` tab bridge, are `docs/agent-export.md`. Spark staging host layout is `docs/staging.md`. Production runbooks are `docs/ops/README.md`. The graphs below are what the code builds.

Two different things are called contours. **Sketch contours** are `makeCrossSection` profiles (contour mode). **Body contours** are the coherent edge chains the viewport paints and that Fillet / Sweep path picks walk. This file uses those names.

## Layers

```mermaid
flowchart TD
  script["Monaco script + feature chips"] --> worker["sandboxWorker: Manifold WASM + HELPER_FUNCTIONS"]
  worker --> mesh["mesh: verts, tris, faceID"]
  mesh --> face["Face graph: PartGraph, rebuilt with the mesh"]
  mesh --> edge["Edge graph: feature edges, dihedral at least 2 deg"]
  edge --> contour["Body contours: coherent chains, dihedral ≥ 15°"]
  mesh --> seam["Keep-both shared edge: 1px black line"]
  face --> pick["Viewport pickers"]
  contour --> pick
  pick --> script
```

1. **Script.** Monaco holds the program. Feature chips come from `parseFeatureMarkers`. Named contours are chips on that same strip. Confirm writes text into that buffer and Auto-Runs. The worker does not see picker state.
2. **Helpers.** `executeScript` prefixes the script with `"use strict";\n` and runs `new Function(...helperNames, wrappedScript)`. `HELPER_FUNCTIONS` are the parameters. Those names are bindings of the user script. See Goldens.
3. **Mesh.** A successful run replaces the three.js geometry and stores `faceID` on it. `c4MeshData` is a separate worker graph, rebuilt on each helper call that needs faces or edges. It is not the viewport PartGraph. `edge` / `edgesBetween` use `indexBoundaryEdges`, cached in a WeakMap on that Manifold object.
4. **Viewport.** Pickers and paint read the three.js mesh. They do not read `c4MeshData`.

## Viewport orbit loop

- The viewport init effect owns one `requestAnimationFrame` loop and one `TrackballControls`. Cleanup cancels that frame (`cancelAnimationFrame` on the id it stored) and calls `controls.dispose()`. The loop updates the controls instance it created, not `controlsRef`, so a later mount cannot retarget a stale loop. That includes React StrictMode in `vite` dev, which runs the effect, the cleanup, then the effect again.
- Orbit feel is `src/utils/trackballFeel.js`: `rotateSpeed` 2, `zoomSpeed` 2.4, `panSpeed` 0.6 (2× the three.js defaults) and `dynamicDampingFactor` 0.36, one step with the same per-frame decay as two default 0.2 steps. `enableDamping` is not a TrackballControls property and is not set.
- **Zoom to Fit.** `data-zoom-to-fit` frames the union bounding box of every visible part (`unionWorldBox`). A hidden row is not in the scene, so it is not in the box. One visible part is that part's box, at the same 1.15 margin. Parts that sit far apart back the camera up until every corner of that box is in the frame. View snaps still frame the active part.
- **Sketch drag.** A pointerdown that hits a sketch drag handle sets `noRotate` and `noPan` for that whole gesture, in capture before Trackball records it, then restores them. Empty space still orbits. Dimension and Constrain keep a tap-slop hold on rotate only: it releases once the pointer moves past 12px, and it does not disable pan. Arc, the plane card, and the Extrude, Revolve, Loft, and Sweep cards do not take that hold. A one-finger drag on the canvas with one of those cards open still orbits. Touch and mouse. `golden:contour-normal`. `golden:slot-preview`.
- **Normal to sketch.** In contour mode the right rail shows `data-normal-to-sketch` (Lucide `CornerDownRight`) directly under Zoom to Fit. It aims along the current sketch-plane normal and zoom-fits the part's world box with the face-sketch camera, so a placed part stays centred. `golden:contour-normal-fit`.
- **Page zoom lock.** The viewport meta is `width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no`, and still `viewport-fit=cover` plus `interactive-widget=resizes-content`. iOS Safari ignores `user-scalable`. `installPageZoomLock` (`src/utils/pageZoomLock.js`), from its own viewport effect, calls `preventDefault` on `gesturestart` / `gesturechange` / `gestureend` and on multi-touch `touchmove` whose target is outside the canvas (`{ passive: false }`). Cleanup removes those listeners, including under StrictMode. One-finger `touchmove` is not cancelled, so Parts, the Script pane, and scrolling popups still scroll. Touches on the canvas are not cancelled, so TrackballControls keeps pinch-zoom, rotate, and pan. `touch-action: none` is on the viewer shell, the canvas, and the right rail. The left rail is `pan-y` so its tool list still scrolls while a pinch there does not zoom the page. `overscroll-behavior: contain` on that rail keeps a drag at the end of the list from chaining to the page. `html`, `body`, and `#root` are `overflow: hidden`, so the document is not a scroll container. Buttons and fields use `touch-action: manipulation` (no double-tap zoom). Text fields stay at least 16px so focusing one does not zoom the page.

## Helpers

Injected names are the keys of `HELPER_FUNCTIONS` in `src/lib/surfcad/runtime.js`. Anything not in that object is not a script helper. `src/workers/sandboxWorker.js` only calls `bindWorker` on that module.

### Kernel crash isolation

One sandbox worker still runs every part. When its Manifold WASM dies (an Emscripten `Aborted()`, a trap, out of memory at the 4 GB heap cap), the module cannot be used again, and before this every later geometry call hung until the tab was reloaded (fastened bike, Clamps & Retainers, 2026-10-20). Now, with the contract in `src/workers/kernelCrash.js`:

- **The worker names the death.** `bindWorker`'s catch runs `classifyKernelFailure` (a `WebAssembly.RuntimeError`, an `Aborted` / trap message, an allocator message; `out_of_memory` when the message says so or the heap is within 12.5% of the cap, else `wasm_abort`). A fatal throw is reported with `fatal: true`, `reason`, and `wasmHeapMB`, and the worker marks itself dead: every later message is answered at once with the same report (`dead: true`) instead of hanging.
- **The main thread replaces the thread.** `ManifoldWorker._onKernelCrash` handles a fatal report, a worker `error` event (the browser killed the thread; the oldest pending job was the one running), and the watchdog (an `execute` past its budget, 30 s by default, `timeoutMs` per call; before, a promise-only timeout left the hung run holding the thread and every later call queued behind it). It fails the crashed job with one `KernelCrashError` (`code: geometry_worker_crashed`, `reason`, `workerRestarted: true`, `wasmHeapMB`, `budgetMs`, `partId`, and a message that says the engine was restarted and other parts are unaffected), terminates the thread without rejecting the jobs queued behind the crash, starts a fresh worker (`createWorker`, a dynamic import of the `?worker` entry so tests can pass a stand-in), and re-posts those queued jobs there in order. `whenReady` waits on that restart. Nobody reloads; the next edit to the failed part runs on the healthy worker. `crashCount`, `lastCrash`, and the `onCrash` callback report it.
- **The crash reaches status, errors, and the part rows.** The viewport catch puts `kernelCrashRecord(error)` on the run outcome; App stamps it on `runFailure` and on the part's run (`recordPartRun` keeps `crash`; `runAssemblyParts` sets it for a non-active part). The bridge's `failedExecute` carries it, `remember` adds `crash` to the mutate result, and `formatAgentErrors` emits one `geometry_worker_crashed` row with `reason`, `workerRestarted`, and a fixed `detail` (simplify, reduce segments, split). `parts` rows now carry `runState` for every part (`partRunState`: `ok` for a mesh or an empty part, `failed` for a run that threw, else `not_run_yet`) and `crash` when there is one, so an agent sees a failed non-active part without activating it. `status.runState` is `failed` as for any failed run, and the viewport keeps the last good mesh and draws the part as failed, as it already did.
- **One block fails alone (per-block budget).** The 30 s budget is still one watchdog on the whole run, but a block that runs past it no longer takes the part down. `executeScript`'s tracker posts every marked-block entry to the main thread as it happens (`featureProgress`: id, kind, label, block; `_featureProgress` in `runtime.js`, set per execute by `bindWorker` when the execute payload carries `progress: true`, which `ManifoldWorker` always sends and the hand-driven Node harnesses do not, so their first reply is still the result), and `ManifoldWorker` keeps the latest on the pending job. When the watchdog fires inside a block, `_onKernelCrash` does not reject that job: it re-posts the same message to the fresh worker with `payload.timedOut` naming the block (and how long it ran and the budget), re-arms the watchdog, and the worker's `executeSkippingFailedFeatures` starts from an evaluation copy with that block and its hard dependents blanked, the same path a thrown feature takes. The job then resolves with the recovered mesh and a `featureSkip` whose `code` is `feature_timeout` (`timeout { id, kind, label, elapsedMs, budgetMs }`, `hint`, the message naming the block). The viewport shows that mesh and marks the chip failed, `status.runState` is `failed` while the `parts` row keeps `ok` (a mesh exists, as for any skipped feature) with no crash record, and the agent gets one `feature_timeout` row (`featureId`, `featureType`, `featureLabel`, `elapsedMs`, `budgetMs`, `detail` = the recovery) instead of `geometry_worker_crashed`; `undo`, `edit_feature` and `delete_feature` on that block work as on any failed feature. Only when skipping leaves a solid (`timeoutRecoveryKeepsSolid` in `featureSkip.js`: the block is known, not every block goes, and the copy still declares `part`); the base block, or a freehand script that the app wraps as one `code` block, is not re-posted, since "rebuilt without that feature" would mean an empty part. Bounded: after `MAX_FEATURE_TIMEOUT_RETRIES` (3) re-posts of one job, when the kill lands outside every block, or when the recovery would leave nothing, the job fails with the crash error as before, now carrying `featureId`, `featureKind` and `featureElapsedMs` when known. A genuinely per-block timer was not used: the script is one synchronous program, so nothing on the worker can check a clock between blocks once a kernel call has started; the kill has to come from outside, and the re-post is what makes it per block. The tracker also times each block (`featureTimings` on the execute result and on `runScript`), which App keeps per part so `feature_tree` rows and `status.features` (summary mode) carry `ms` and `status.featureMs` says what is expensive. Blanked blocks (skipped or rolled back) are not timed.
- **Feature-level memoisation (`src/lib/surfcad/featureMemo.js`).** A part used to run from its first line on every edit. Now the worker keeps, per marked block, the bindings the script holds when that block closes: kernel handles as clones (kept out of the arena sweep, with the run-table estimate copied), plain data as structured clones, plus the per-run side tables a later block reads (face stamps and stamp counters, fillet op brackets, tessellation tags, the sheet fillet span). The key of block *i* is a hash of the script text up to the end of block *i* plus the imported-model signature, so it is a prefix key: an edit to block *k* re-runs *k* and everything after it and restores everything before it; an unrelated earlier edit only loses hits, it can never serve a stale block. `executeScript` plans every run (`planMemo`): the evaluation copy keeps every marker line (ids, the tracker and error lines are unchanged), replaces each restored block's interior with one line that rebinds its names from the cache (`__memoRestore`), and appends a capture call to the end-marker line of each block that runs (`__memoCapture`, the names come from a top-level declaration scan of the script, `topLevelDeclarations`); the line count is unchanged. Code outside blocks always runs, so preamble lambdas close over this run's bindings, and the restore assigns every captured name over them (top-level `const` in the copy is relaxed to `let  `). Handles rather than serialised meshes because a mesh round-trip is float32 and the booleans after it would not be bit-identical, while a clone shares the kernel's own node and its already-evaluated result. Not cached, and reported as `uncacheable` on the result: a block that reads a clock, randomness or the network, a block that declares a function or class, a script whose top level has a construct the scanner does not follow (destructuring, a `var` below top level), a function bound outside a block that a block reassigns, and every block after such a point; a block that throws is never captured, while the blocks that closed before it are, so the skip-and-rerun of a failed feature and a `rollback_to` both replay the prefix. Storage is an in-memory LRU per worker with a byte budget from `deviceMemory` (64 MiB per GB, 64..512 MiB, 128 MiB when unknown; `featureMemoBudgetBytes`), sized after the result's evaluation so sizing never evaluates a node ahead of it; eviction only costs time, and a run that alone exceeds the budget stores nothing. Entries are content-addressed, so two parts with the same script share them. Nothing is persisted. The execute result carries `featureCache` (`blocks`, `hits`, `misses`, `stored`, `entries`, `bytes`, `budgetBytes`, and `stopped` / `dropped` / `uncacheable` when relevant) and `featureTimings` rows of restored blocks carry `cached: true` with `ms: 0`; App keeps both per part, so `status.cache` (`{ blocks, hits, misses, bytes }`), `status.featureCached` (`{ [featureId]: true }`), `feature_tree` rows and `status.features` rows (`cached: true`) show what the last run restored. The `featureMemo` worker message (`{ clear, enabled, budgetBytes }`, `ManifoldWorker.featureMemo`, `manifoldContext.featureMemo`, dev hook `window.__VIEWPORT__.featureMemo`) empties, disables or resizes the cache and returns its stats. `src/lib/surfcad/featureMemo.test.js` runs the real kernel in Node and deep-compares a warm run with a cold one (triangles, vertices, face ids, run order up to id relabelling, face stamps, feature keys and tessellation) for an edit, an undo, a throw, a rollback and an impure block; `golden:feature-memoisation` drives the same through the bridge on the dev server.
- **Tests.** `src/workers/kernelCrash.test.js` (classification, message, split), `src/utils/ManifoldWorker.crash.test.js` (a scripted stand-in worker: fatal report, watchdog, error event, a plain script error that is not a crash, a second crash, a slow job inside its budget, a kill inside a marked block that re-posts without it, the retry cap, a kill outside every block), `src/utils/featureTimeoutRun.test.js` (the real kernel in Node: `timedOut` blanks the block and its dependents and reports kernel time per block), the state tests, `golden:geometry-worker-crash` (browser, dev server: a simulated abort through the bridge, then a healthy run), `golden:kernel-crash-headless` (Node, the real worker protocol, a real out-of-memory abort: the report arrives fast and the next message fails fast), and `golden:feature-timeout` (browser, dev server: a block that spins past a 2 s test budget fails alone, the chip is red, the agent row is `feature_timeout`, undo and delete work).

### Geometry worker pool

The parts that are not active build in parallel, each in its own Manifold WASM instance with its own heap; the active part, cross-sections, previews, exports, and the game stay on the **primary** worker, because they read the solid it cached last.

- **Cap** (`src/utils/geometryPoolCap.js`, `liveGeometryWorkerCap`): total workers, the primary included, is min(cores − 1, whole GB of `navigator.deviceMemory`), clamped to 1..4 on a phone-class device (touch plus a small screen or ≤ 4 GB) and 1..8 on a desktop. Without `deviceMemory` (Safari, Firefox): 2 on a phone, 4 on a desktop, still at most cores − 1. Dev override: `?geometryWorkers=N` on the URL, else localStorage `surfcadGeometryWorkers`, 1..16; `manifoldContext.setGeometryWorkerCap(n)` at runtime. The thumbnail worker (`partThumbnails.js`) is separate and not counted.
- **Pool** (`src/utils/geometryPool.js`, `createGeometryPool`): `ManifoldContext.init` creates it with cap − 1 members. Members (each a `ManifoldWorker`) spawn on demand, queue jobs beyond the size, are torn down after 120 s idle, and are recycled after 200 jobs or once a run reports a heap of 1536 MB or more (`wasmHeapMB` on the execute result). A member that crashes restarts itself (crash isolation above); the job that crashed rejects with the structured error and the others go on.
- **Routing.** `manifoldContext.executeScript(script, { parallel: true, partId })` goes to a pool member when the pool has one, and does not touch `lastResult`; everything else goes to the primary. `runAssemblyParts({ concurrency })` builds the non-active parts with that many in flight (`mapLimit`) and still records outcomes in part order, so `runs` reads the same as a serial build; `refreshAssembly` passes `manifoldContext.parallelism()` and `parallel: true` for the other parts, then runs the active part through the viewport as before. `ensureAlive` drops idle members; `terminate` drops the pool.
- **Determinism.** A part's mesh does not depend on which worker built it or on what that worker built before: each member is a fresh module and the kernel arena frees every run's handles. `src/utils/geometryDeterminism.test.js` builds six parts in two orders and interleaved with a heavier neighbour and compares triangle counts, volumes, body counts, and run counts.
- **Debug status.** `geometry_workers` (bridge and MCP, read-only) returns the cap, live and busy counts, `peakBusy`, crashes, the primary's stats, and the pool's per-member stats (`manifoldContext.poolStats()`). `golden:geometry-pool` builds a ten-part assembly with the cap at 1 and at 4 on the dev server, compares every part's volume and triangle count between the two, and reports both build times.

### Constrained contour

`solveContour` (`src/utils/contourSolve.js`) solves a contour in the workplane UV frame. A saved contour is its own statement and owns its frame: `const c1 = makeCrossSection({ center, normal, x, y }, solveContour({...})); // @contour id=c1`. The id is that marker, or the binding name when a hand-written call has no marker. It is never a character offset. Names start at `c1`. Confirm of the same id rewrites that statement. Confirm with no id appends the next name. Renaming the binding rewrites code references and leaves the id. Dimension Confirm writes this statement and does not rewrite an Extrude, Revolve, Loft, or Sweep block. Loft, Extrude, Revolve, and Sweep name those contours. Their cards are slot pickers titled Extrude, Revolve, Loft, and Sweep. Each profile slot, and the Sweep path slot, shows the reference, a picker of saved contours, and New contour. Pick a contour is plain text (`data-slot-prompt`), not a button. The saved contours are buttons under that text. Picking one highlights only that button orange (`data-slot-selected`). The picker has no No contour row. Hover or tap in the picker lights that ghost. New contour opens the plane card. The rail checkmark saves the named contour and returns to the same card with that slot filled. X returns without filling it. A Loft station keeps an optional offset along the contour normal. Extrude distance and sense, revolve angle, axis, segments, and sense, and sweep reverse and closed stay editable on the card. While the card is open, each filled slot paints the live solid preview from that saved contour's profile and plane plus those card values (cyan meshes `contourExtrudePreview`, `contourRevolvePreview`, `contourLoftPreview`, `contourSweepPreview`). New contour and an edit of that slot preview the live profile with the same card values. Changing distance, angle, offset, reverse, or closed updates the preview. The preview is not the committed solid. Confirm writes the solid with those values. `golden:slot-preview`. A filled reference chip, and a contour chip on the CAD strip, open that contour in the contour editor. The editor shows a banner, `Used by Extrude 1, Loft 1` or `Unused`, using the feature block ids. The rail checkmark rewrites that contour by id and runs the script, so every feature that names it rebuilds. X writes nothing. Renaming rewrites the binding and every bare reference and leaves `@contour id=`. Saving from a feature-card chip returns to that card. `golden:contour-edit`. A contour no feature names stays. Its strip chip and the picker show unused. Deleting a feature leaves its contours. Deleting an unused contour removes the statement immediately, including a statement that sits inside the sheet-metal span, and shows `Deleted contour.` with Undo. The contour's own `refs` are not users, and the sheet-metal block is not a user, so that delete does not refuse. Deleting a referenced contour asks Delete along with N features, and that confirm removes the contour and those blocks as one undo step. `golden:contour-delete`. `golden:sheet-contour-delete`. A part edge, vertex, or face loop can be a reference on that same call. `refs` stores the face pair and the midpoint, and the last projection in plane UV (`src/utils/contourRef.js`). The projection is a line, an arc when the curve lies in a plane parallel to the sketch, or a polyline. A projected length under 0.05 mm is broken. The solver treats a live reference as fixed. Coincident and on-edge use the finite segment. Parallel, perpendicular, and distance use the infinite line. Tangent applies when the reference is an arc. A constraint between two references is refused. A broken reference adds no residual. References are not tessellated into the profile. Dimension and Constrain, and only those gestures, pick a reference on this part after the sketch misses at 12 px: a vertex, then an edge (`pickNearestEdgeScreen`), then a face outline. The face outline is that face's boundary loop, and the constraint binds the edge under the cursor. The pick is written into `refs`. References draw dashed and muted under the sketch strokes, with no handles. The selected one keeps that dash and uses the picked-edge colour. `golden:contour-refs`. On editor open, and before a run when the part mesh is available, each reference is matched again by its face pair and midpoint and reprojected. A single edge with that pair follows a move. A successful match rewrites that geom. A miss does not retarget to a nearby edge: the reference is broken, the cached geom stays, and the statement is not rewritten. The run soft-fails, names the contour, and keeps the last good solid. A vertex follows its edge. If any boundary of a face reference is missing, the whole face reference is broken and a partial loop is not drawn. With no mesh yet, the cached geom draws broken until the part has run. A broken reference is dashed red, with a broken tag. `golden:contour-ref-resolve`. An Extrude block is `makeExtrude(c1.contours, distance)` and keeps the sense shift. A Revolve block remaps that contour. A Sweep block names a profile contour and a path contour (`{ type: 'path', closed, points }`). The block ids are `extrude1`, `revolve1`, and `sweep1`. A confirm with no id appends the next block. The same id rewrites it. A dimension name is a string on that dimension, scoped to the contour, not a `const` later features can read. Reopening Extrude, Revolve, Loft, or Sweep opens that slot card from the shape rail, from `enterContourMode`, from a strip chip, and from feature edit. A named contour fills its slot, and Confirm rewrites that block id. An inline call with no contour name leaves the slot on Pick a contour. The card does not show the plane, plane angles, or Select plane. Profile and workplane still open the contour editor. An old point-list `profilePolygon` restores its points there and is not promoted. Extrude and Revolve do not pick a dimension name. Lengths in the call are millimetres. Angles are degrees. The dimension field converts with `src/utils/displayUnit.js`. The solver does not import it.

Cursor sits first on the contour rail (`data-contour-tool="cursor"`, Lucide `mouse-pointer-2`). It drags a point and never adds a polyline point. Grabbing an edge or the interior of a hexagon, circle, rectangle, or polyline translates the whole shape. A free shape moves. A fully locked shape does not. A partly constrained shape moves along the directions the solver still allows. Each drag is one undo. A point drag still moves that point. In the Polyline tool, a tap on a segment still inserts a point. `golden:contour-shape-drag`. Polyline's icon is Lucide `waypoints` (`vector-polygon` is not in lucide-react 0.469). Arc's icon is Lucide `spline`. Double-tapping a polyline dot removes that point in one undo step. A constraint or dimension that named the point stays and is marked broken, the same rule as a dangling coincident. Fewer than three points, the auto-closed minimum, deletes the shape. A saved shape with feature users confirms Delete along with N features and then deletes those dependents with the shape. Arc, Dimension, and Constraints sit on the contour rail after Polyline. They are not profile tools, so selecting one does not clear the contour. Selecting Cursor keeps the sketch that is already drawn. The first selection of Arc, Dimension, or Constraints promotes a circle, rectangle, polygon, or polyline into a solver contour. A polyline stays one entity: the strip keeps a single Polyline chip, and the segments stay inside that contour so a dimension or constraint can still name one of them or a point. Dimension and Constraints Add write that profile, clear the picks, and leave the card open. They do not Auto-Run and they do not change the solid lines around the profile. A distance between two points locks only that distance. Both points stay free, and dragging one moves the other while the distance holds. Typing a length, distance, angle, offset, or radius re-solves that preview from the contour as it was when the dimension started. For that edit solve only, the first picked point is pinned, so the polyline follows the field and a second keystroke does not drift. The pin is not a stored lock. The field and the tag always show a positive size. A distance or offset on the negative side of a reference edge keeps that side in the stored value, so typing a positive number does not flip the geometry. Add writes the one dimension or constraint and leaves the card open for another. X drops the preview and writes nothing. Tapping the tag reopens that dimension or constraint: Confirm saves and closes, red Delete removes it, and there is no Add. Both picked points and edges stay highlighted until Add. The tags are portaled to the document body, in canvas pixels, so the viewport shell cannot clip them and the canvas cannot cover them. A perpendicular constraint is a plus bubble. It is hidden while it would cover a dimension chip, and pluses that cover each other collapse to one so a repeated constraint does not stack on the value. `golden:dimension-done`. A tag is on screen while the dimension is edited, and after Add. The same layer draws the drafting figure (`src/utils/contourDimensionDraw.js`). A length, distance, offset, or radius gets extension lines that start on both picked points (a line-line distance stores the tap UVs as `anchors`, and the figure is projected in the part pose, the same frame as the dots), a filled arrowhead whose tip meets each extension and does not cross it, the extension running slightly past that tip, and the opaque value chip centered on the arrow. The shaft stops at the back of the arrowhead. An angle gets the same arrowheads on an arc that stops at the arrow base. Dragging a value chip moves a length, distance, offset, or radius along the dimension normal, and an angle along its radius. A pointer move under 6px still opens edit. `placement` is stored on the dimension in the solveContour call and kept on reopen. Sketch points, lines, and arcs hit-test at 12px in that posed frame and win over the part solid while a contour gesture is open. The translucent sketch-plane square is not drawn. Workplane quads turn on with the plane card so a plane can be picked. Select plane accepts the plane and hides that preview. Back to the plane card shows it again. A plane toggle the user set stays.

Entering a sketch opens the plane card first. That card uses the same feature-sheet camera slide as the other cards, so on a phone the part sits in the band above it (desktop does not slide; see **Feature card**). The title is Contour. Offset sits under the angle fields, the same signed length control Workplane uses (`Offset mm` or `Offset in`). That box is `formatDisplayNumber`. It is along the plane normal for a Face and for the X, Y, and Z planes. The preview moves with the value. Select plane accepts the plane, drops the slide snapshot without restoring it, aims the camera along the sketch-plane normal, and frames the face when the plane is a face, otherwise the part (`src/utils/faceSketchCamera.js`). The up hint is the top view for a +Z normal (`[0, -1, 0]`) and world +Z otherwise, so a face whose normal is +Z is not rolled onto +X. The card then closes. The pressed tool is Cursor (`data-contour-tool="cursor"`). A fresh sketch is empty: it does not copy the first loft station's circle, so the plane card and the sketch after Select plane draw no profile and the strip shows no circle chip. Confirm of that empty sketch writes nothing and leaves the script unchanged. Loft stations stay circles. Extrude, Revolve, Loft, and Sweep still enter on that circle. Selecting Circle, Rectangle, or Polygon draws that profile. Polygon is a regular polygon of 3 to 8 sides: triangle, square, pentagon, hexagon, heptagon, and octagon. The card select is `data-polygon-preset`. The default stays hexagon. `golden:polygon-sides`. A tap on the face while the plane card is open still selects the face; an empty sketch has no preview rim to swallow that tap. Normal to sketch (`data-normal-to-sketch`, Lucide `CornerDownRight`) sits on the right rail directly under Zoom to Fit, and only while contour mode is open. Horizontal is constant `v`. Vertical is constant `u`. An under-defined contour is a normal result (`status: 'under'`). A conflict returns the least-squares shape and names the item (`status: 'conflict'`); it does not throw. A constraint that does not change the rank is `repeated`, which is a warning, not a red state and not an error. That rank counts singular values of the scaled Jacobian above `1e-5` of the largest one, or above an absolute `1e-9` when that is larger. Finite-difference noise is about `1e-8` of the largest singular value, and an angle row divided by one degree pushes that largest value into the tens, so the old `1e-8` cutoff counted a noise mode as rank. Dropping a real perpendicular, or a real tangent on a corner arc, then looked rank-neutral and the constraint was marked repeated. A polyline joins its segments with shared point ids. Those joins are not coincident constraints. One perpendicular on two segments is one new row: the angle becomes 90°, the contour stays under-defined, and the segments stay free. The same set added in any order stays under-defined, at 90°, with the line lengths kept. The working phone sketch is that case: a free quad, a 1.5000 in side, and the two perpendiculars at the corners of one edge, whose pluses sit side by side. Every order keeps that length and both corners at 90°, and the lines stay blue. The solve starts from the points on screen and minimises that move. The step is damped least squares with a displacement penalty, `Jᵀ (JJᵀ + λI)⁻¹ (−r)` when a sketch has fewer rows than coordinates and `(JᵀJ + λI)⁻¹ Jᵀ (−r)` otherwise, so a free coordinate does not jump. Parallel and perpendicular are the signed turn between the unit directions, `atan2` of the normalised cross and dot. The branch, same way or opposite and left or right, is locked from the geometry on screen, so a later step cannot flip the corner and length cannot satisfy the row. Once that residual is at zero, each line length is put back only along the constraint nullspace. A length row inside the angle solve used to stall a fraction of a degree short and report a conflict. A conflict is that residual still away from zero, which parallel and perpendicular on the same pair are, near 45°. A sine residual is flat at the worst error, and the old diagonal damping was dust on a free coordinate, so the step ran off and a parallel segment left the screen. A second copy of that perpendicular, or one already implied by horizontal and vertical, stays repeated. `golden:contour-perpendicular`. The point cap is 128. An open chain closes once it has three points. Joints do not call this solver.

A partially constrained shape is blue on the free entities and black on the locked ones. The saved ghost uses that contour status colour. ### Headless entry

- **One module.** Script helpers and `executeScript` live in `src/lib/surfcad/runtime.js`. The worker message protocol is `bindWorker` in that same file. Node imports `src/lib/surfcad/index.js` (`runScript`, `helperScope`, STL / 3MF / STEP). There is no second copy of the helpers.
- **Kernel.** Both paths load `built/manifold.js` + `built/manifold.wasm`. npm `manifold-3d` is a different build. `runScript` also accepts an injected module or a `modulePath`.

- **Script return.** `manifoldFromScriptResult` is the one check on the worker `execute` path and in `runPreparedScript` (what `runScript` calls). A Manifold passes through. ### Kernel memory

One Manifold WASM instance serves every part, and its heap never shrinks. Two things used to grow it until the 4 GB cap aborted the module (`Aborted()`, after which every geometry call hangs until the tab is reloaded; fastened bike, Clamps & Retainers, 2026-10-20):

- **Run tables on multi-body parts.** The kernel's `decompose()` gives every component the parent's whole run table (one run per source mesh id, most of them empty for that component), and `compose()` concatenates the tables of its inputs. `installSeparateBodies` (`src/workers/separateBodies.js`) used to decompose the receiver and compose the bodies back on every add once two bodies' boxes overlapped, so the run count multiplied by the body count on each add: 16 bodies and 15 adds reached the heap cap inside the 13th. Now an add whose tool touches no body composes the tool with the receiver as it is (`Manifold.compose([tool, receiver])`), which is bit-identical to the plain path and linear. The paths that must reuse decomposed bodies (a touched add, a per-body cut, a per-body face op) track an upper-bound run estimate per handle in a WeakMap (sum over compose and boolean inputs, inherited through transforms, the parent's count for a decomposed body) and rebuild a body from its own non-empty runs (`compactRuns`) only once the estimate reaches `RUN_BLOAT_MIN` (8192) and the real table is at most a quarter used. That rebuild goes through the float32 mesh, and the kernel's triangulation depends on allocation order, so it is a guard against the abort, not a default: ordinary parts never reach it (the bike Frame ends at 805 runs) and keep their exact mesh. Reading a mesh to decide would itself change later unions, which is why the guard estimates instead of measuring.
- **Intermediate handles.** Embind handles are not garbage collected; a script keeps only the solid it returns, and every `Manifold.cylinder`, `.translate`, `.add` result leaked. `installKernelArena` (`src/workers/kernelArena.js`) wraps the public statics, instance methods, and constructors of `Manifold` and `CrossSection` so each handle made during an execute is recorded; `_runInKernelArena` in `runtime.js` evaluates the result (`numTri()`) while those handles are still alive, since the kernel only flattens a union chain through nodes nobody else holds and freeing first would change the triangulation, then deletes every recorded handle except the result and the retained game solids. The solid a worker execute replaces (`cachedManifold`) is freed by `_replaceCachedManifold`; the headless `runScript` leaves the returned `manifold` to its caller. The worker `execute` result and `runScript` carry `wasmHeapMB` and `kernelFreed`. Three back-to-back headless rebuilds of the 13-part bike hold at 120 MB; before, each rebuild added about 200 MB.

`src/workers/separateBodies.test.js` and `src/workers/kernelArena.test.js` pin both. The kernel build is the stock `elalish/manifold` wasm; the run-table copying is upstream behaviour, so a kernel upgrade that trims the table in `Decompose` would let the guard go.

**Safari popup bridge (M1).** Desktop Safari on https blocks `ws://127.0.0.1` as mixed content (and the prod CSP's `upgrade-insecure-requests` would turn it into `wss://`). `agentBridgePairingMode` (`src/agent/ws/connectionErrors.js`) picks `popup` for desktop Safari on a non-loopback https page, `unsupported` for iPhone / iPad (a touch "Macintosh" counts as iPadOS), and `direct` everywhere else, so Chrome is unchanged. `?agentBridgeTransport=popup|direct` or localStorage `surfcadAgentBridgeTransport` forces it in dev and playtest builds only. A closed bridge window (polled) closes the transport with reason `bridge_closed`, and the pairing dialog re-opens with **Disconnected** (`AgentBridgePopupStatus` in the dialog body) and **Reconnect** (`data-agent-bridge-reconnect`, same code, Allow again). **MCP stdio server (M2).** `packages/surfcad-mcp` is the publishable npm package (`surfcad-mcp`) that speaks MCP over stdio. At startup it loads `data/commands.json` (kept in sync with `src/agent/commands.json` by `npm run export:agent`). That file, `list_commands`, `GET /tools` on the loopback relay, and the MCP bridge tools are the same catalog. The server also registers a `pair` tool and five in-process prompt tools (`register_webhook`, `unregister_webhook`, `read_messages`, `reply_to_user`, `set_status`) that are not catalog commands. A paired tab sends `agent.prompt`; the process POSTs it to an in-memory https webhook or queues it, and answers with `agent.reply` and `agent.status`. Stop in the prompt card sends `agent.prompt.cancel`; the process drops a still-queued prompt, or marks a delivered one cancelled and tells the agent with `{ type: "cancel", id }` (webhook POST, else the next `read_messages`), answers `agent.prompt.cancel.result` (`cancelled`, `not_found`, or `already_final`), and refuses a later `reply_to_user` / `set_status` for that id with `{ ok: false, error: "cancelled" }`. A prompt grants no write access and nothing reaches git without Save or `git_save`. It connects through the same M1 relay as the CLI client; pairing uses `SURFCAD_PAIRING_CODE` or `pair`. Tool calls forward `{ command, args }` on the paired socket and return JSON results; bridge refusals (`real_repo_blocked`, `confirm_required`, `not_paired`, user deny) surface as structured tool errors. When the tab or relay drops, calls fail at once with `pairing_lost`. The relay notices dead sockets by ping/pong heartbeat (every 5 s) and logs the drop on stderr. The pairing code stays reserved for that tab’s `tabKey`. The tab (`tabConnection.js`) reconnects with backoff, presenting its per-tab `tabKey`, and the hub matches the `resumeKey` from Allow without sending the secret on `PAIR_REQUEST`, so recovery needs no new prompt. The profile chip ring shows connected, reconnecting, or lost. See `packages/surfcad-mcp/README.md` for Claude/Cursor config. `packages/surfcad-mcp/test/server.test.mjs` exercises list/call against a mocked relay. Scripted playtests pick a free relay port by default so `npm run playtest` does not collide with a dev relay on 17341.

| --- | --- | --- |
| `makeExtrude`, `makeRevolve`, `makeLoft` | contours or sections → a new solid | No split. UI adds or subtracts onto `part` when `part` already exists. Default is add (`part.add`). Merge bodies off emits `part.add(x, { merge: false })` (separate body, below). Subtract emits `part.subtract`. An empty script is still `let part = …`. |
| `loft`, `sweep`, `sweepPoints` | profiles / path → a new solid | Same. Sweep's one-shot fallback still replaces `part` when Mode is Add. Contour Confirm adds or subtracts. |
| `makeCrossSection`, `profileCircle`, `profileRectangle`, `profilePolygon`, `solveContour` | plane + 2D profile → a contour, not a solid. `solveContour` is the constrained contour (points, lines, arcs, dimensions, constraints) in plane UV | — |
| `makeSweepPath` | edge list → one ordered path | Orders the edges it is given and keeps each picked edge's `n0`, `n1`, and adjacent face ids on the path. It does not walk bodies. |
| `filletAlongPath` | solid, path, radius, opts → blend (subtract, or union for a concave run) | On a multi-body solid, fillets the body that owns the path, then `compose`s the untouched bodies. The scrap check still runs on that one result. See below. |
| `filletEdges` | solid, edges, radius → planar blend | No `decompose` scrap check. |
| `sheetMetalSolid` | sheet spec (JSON) → one sheet-metal solid | One body. Only Sheet Metal mode writes it, inside the `sheet-metal` markers; on a fresh part it replaces the script (empty, comments-only, or only `return part;`) rather than adding onto `part`. |
| `chamferEdges` | solid, edges, size → chamfer | No `decompose` scrap check. Fillet-mode Chamfer emits `filletAlongPath(..., { profile: 'chamfer' })`, not this. |
| `shell` | solid, thickness, opening → the cavity | No `decompose` / `compose`. Offsets the mesh it is given. On overlapping bodies the cavity is wrong; use `hollow`. |
| `hollow` | same → the walls (`solid − shell`) | Per body when bodies overlap (`_perBodyFaceOp`, below). |
| `draftFaces` | solid, faces, angle, `{ pull, reference, sense }` → tilted solid | Moves vertices of the selected faces only. Per body when bodies overlap, so `reference: 'min'` is that body's box. A fillet between the neutral plane and the wall hinges at the blend tangency; the blend face is not drafted. |
| `addDraft` | solid, degrees, axis → `draftFaces(..., 'sides', { reference: 'min' })` | Legacy; reference is the whole solid's box. |
| `cut` | solid, plane, `{ bodies, keep, drop }` → kept pieces | `decompose`, cut the named bodies, `compose` what remains. Default `keep` is `'both'`. |
| `booleanBodies` | solid, `{ op, bodies, drop, tools }` → one solid | `decompose`. The first `{ at }` is the target. Later bodies are tools, unioned, then difference is target − tools and intersect is target ∩ tools. Union unions every named body. Unselected bodies are composed back. Omit `bodies` to use every body in decompose order (with `tools`, omitting it names the first body only). `tools: [solid]` are extra tool solids after the named bodies, used for cross-part copies (`externalBody`). Intersect `drop: [{ at }]` deletes leftover pieces by the same centroid gate as `cut` (squared distance ≤ 1e-4). Empty intersection throws. Deleting every piece throws. |
| `externalBody` | `function () { copied script }` or a solid, `{ bodies, offset }` → solid | Runs the copied text, then `decompose` and keeps the bodies whose vertex centroid matches each `{ at }` (same 1e-4 gate as `cut`; a miss throws `externalBody:`). Omit `bodies` to keep the whole solid. Translates by `offset`. The text is a frozen copy, not a reference: nothing reads the source part at run time. |
| `move` | solid, `[dx,dy,dz]`, `{ bodies: [{ at }] }` → that body translated | Same split as `cut`. Exactly one body. Other bodies stay. `{ at }` is the vertex centroid. An exact literal uses `cut`'s 1e-4 gate. A re-run may shift that average, so the nearest body within 1% of its radius (at least 0.05) still matches when the next body is farther. A point that is not near a centroid throws. |
| `moveFace` | solid, faces, distance, `{ flip }` → those faces offset along their normals | No `decompose` unless bodies overlap (then per body). Adjacent faces extend or trim. Facets within 10° that are all held or all offset are one plane. A scrap within 10° that lies on a larger face of the same body is that face. Not `move()`. Other bodies' vertices stay. |
| `deleteFace` | solid, faces `{ center, normal }` → those faces removed and the solid healed | No `decompose` unless bodies overlap (then per body). Neighbors extend or trim until they meet. If they cannot keep a closed solid, throws. Does not return an open or non-manifold mesh. |
| `edge`, `edgesBetween`, `boundaryEdges` | current solid + ids → segments | Ids are for this mesh. A miss throws `re-pick edges`. Fillet Accept of several disjoint corners writes every lookup before the first blend, so those ids are still the pre-blend mesh. |
| `facesByNormal`, `planarFaceAt`, `edgesByOrientation`, `convexEdges`, `concaveEdges`, `signedFeatureEdges`, `workplaneFromFace`, `placeInFrame`, `transformByFrame`, `placeOnFace` | queries / frames on one solid | Worker faces do not merge across bodies (below). |
| `hole`, `holeSpan`, `cboreHole`, `cskHole`, `holePattern`, `clearanceHole`, `tapDrillHole`, `holesOnContour`, fastener lookups | solid + frame → solid with holes | No body split. `holesOnContour` cuts one hole per centre of a shared contour. |
| `roundedBox`, `tube`, `rectTube`, `hexPrism`, `mirror`, `array3D`, `polarArray`, `center`, `align`, `getDimensions`, loft/sweep vector helpers | as named | No body split. |

`cut`, `move`, and `booleanBodies` are the helpers that `decompose` the input and `compose` the output. `externalBody` decomposes its copied solid to keep the named bodies. `shell` and `addDraft` do not. On disjoint bodies (a keep-both cut) `hollow`, `draftFaces`, `moveFace`, `deleteFace` also see one mesh with more triangles.

### Holes on a contour

`solveContour({ centers: true })` keeps every sketch point, including an arc centre, and does not close an open chain or tessellate rings (`contours` is `[]`). A centres contour may branch. A line with `construction: true` stays in the solve and is not a profile edge; `guide` is still the hidden spoke. An empty centres contour solves to no points. `makeCrossSection` stores that profile and the plane.

`holesOnContour(part, section, spec)` reads `section.plane` and `section.profile.points`. Every point is a centre. An arc whose centre is not one of those points throws. Construction lines add no centres. No centres returns `part`. Two calls may name one section and cut opposite ways: `side: 1` enters toward −normal, the same direction as `hole()`, and `side: -1` or `flip: true` enters the other way. `depth` is millimetres past the plane on that side (the cutter is `depth + 1`, so 1 mm clears the entry side). `through: true` uses `holeSpan`. Through and depth together throw. A far end (`near` / `far` are `{ kind: 'none'|'cbore'|'csk', dia, depth }`) requires through. An explicit `dia` is the hole diameter. Without it, `type: 'tapDrill'` uses `fastenerTapDrillDia(size)` and otherwise `fastenerClearanceDia(size, fit)`. `hole`, `holePattern`, `cboreHole`, `cskHole`, `clearanceHole`, and `tapDrillHole` are unchanged.

`composeHoleOnContour` writes the contour statement and the hole block, both immediately before `return part;`. The statement is `// @contour id=c1 role=centers`. The block is `// --- hole begin id=hole1 ---` and one `holesOnContour(part, c1, spec)` call. A second Hole that names `c1` writes only its own block (`hole2`, …). Rewriting `hole1` updates that block. Passing a contour with no points on that rewrite keeps the block and stores the empty centres list. A new hole with no centres writes nothing. An old `hole(`, `clearanceHole`, `tapDrillHole`, `cboreHole`, `cskHole`, or `holePattern` block is not rewritten. The centres contour is a strip chip (`contour:c1`) and a rollback anchor. Each hole block is its own Hole chip. `contourFeatureUsers` counts Hole blocks, so Delete on the contour asks **Delete along with N features** and removes those blocks with the statement. Deleting one hole removes that block and leaves the contour.

The Hole button opens that card, then the contour plane card (including the XY, YZ, and ZX quads, and the same Offset field). Select plane stores the frame, with the offset baked into the center, and aims the camera. The rail is Cursor, Rectangle, Polyline, Arc, Dimension, and Constraints. Rectangle is the same tool as on the other contour rails. Accept treats each corner as a centre, and the width, height, dimensions, and constraints stay the ones that tool already uses. Sketch lines pass `dashed: true` and keep the status colour. Circle and Polygon stay off this rail. Accept calls `composeHoleOnContour` through `commitFeatureBuffer`: one undo, and the bar sits on the new hole chip. A new hole with no centres writes nothing. X and Esc write nothing. An old `hole()` block still opens the helper sheet. This button does not rewrite it.

Tapping a contour hole chip opens the Hole card with that spec. Confirm rewrites the spec and leaves the contour statement. Edit centres, and tapping the centres chip, reopen the dashed sketch on the baked plane with the plane card closed. The stored offset stays on that frame. Back opens the plane card on the same value, and Confirm keeps or updates it. Confirm calls `rewriteCentersContour`: one `solveContour` call, including a sketch with no centres, and every hole block that names it stays. Each confirm is one undo and does not move the bar. A confirm that does not change the script skips undo. Delete on the card removes that hole block only. An old `hole()` block still opens the helper sheet.

### Loft

`makeLoft` takes two or more contours. Loft Confirm writes each station as its own named contour, then a block that names them: `makeLoft([c1, c2])`. A nonzero station offset is a spread, `makeLoft([c1, { ...c2, plane: offsetPlaneFrame(c2.plane, 20) }])`. The contour statement keeps the unshifted frame. The block marker carries the id (`// --- contour-mode loft begin id=loft1 ---`). A confirm with no id appends the next loft. The same id rewrites that block. Several loft blocks coexist. An old block with no id is still found, and its chip id stays positional.

Parallel planes (normals within about 8°, opposite normals included) stay on the Slice 28 polar warp. Stations sort by offset along the shared normal. The solid is local to that plane, z = 0 at the lowest offset, and Confirm places it with `placeInFrame` on the lowest station's plane. Circle and rectangle corners stay on the angle table. That path is unchanged.

Planes at an angle keep the order they were given. Each contour is mapped through its own frame (`center + u·x + v·y`), resampled to one arc-length count, reversed if its winding opposes the loft, then cyclically shifted to the closest pairing. A straight ruling is the chord of the turn; at a right angle that chord cuts the inside of the bend and the ruled sides fold. Each span is a Hermite spine that leaves along the first forward normal and arrives along the next, and the section rides in a frame slerped between the profiles (in-plane X aimed at the paired start vertex). The caps stay on the authored planes. The solid is local to the first profile's plane, and `placeInFrame` uses that station. A self-intersecting, empty, or non-manifold result throws. On the Loft card each station can stay on the card plane plus an offset along the contour normal, or pick its own face, saved workplane, or sketch plane. A station that owns a plane stores offset 0. The contour frame is that plane. Offset-only confirms still emit `offsetPlaneFrame` on the loft argument.

### Extrude, Revolve, Sweep

Extrude Confirm writes one named contour, then `makeExtrude(c1.contours, distance)` inside `id=extrude1`. The sense shift `[0, 0, w]` stays in that `placeInFrame` call. The contour keeps the unshifted frame. Revolve Confirm writes one named contour and remaps its rings in the block (`id=revolve1`): segments, angle, and the optional rotate stay there. The place frame's center is the contour origin. Identity remap still has no min-radial shift. Sweep Confirm writes a profile contour and a path contour. The path is `makeCrossSection(frame, { type: 'path', closed, points })`. Two points and zero area are legal. The block (`id=sweep1`) rebuilds world points from the path plane, maps them into the profile frame, and calls `sweepPoints`. Reverse is baked into the path. `makeSweepPath` and the edge list stay out of the block. A confirm with no id appends the next block of that kind. The same id rewrites it and reuses its contour names. Extrude, Revolve, Sweep, and Loft leave one another's blocks in place. An old block with no id is still found. There is no migration. The contour statement and the feature block are inserted immediately before the script's `return part;` (`findReturnPartIndex`: the first `return part` at brace depth 0, so a `return part` inside a copied function is not it). A study comment after that return stays after it. The new lines stay outside a sheet-metal span, and a part that already exists — a sheet flange included — is unioned with `part.add`. A subtract on a sheet is not a one-sided prism of the typed depth: the tool spans at least `t + r + 1` mm both ways from the sketch plane (`sheetCutExtrudeSpan`), and still covers the typed depth. A bend arc sits about one inner radius past the face the sketch was drawn on, so a 10 mm cut that stopped on that plane left a skin through the arc. The shift is symmetric, so the card reads it back as sense `both`. An add, and a subtract on a part with no sheet spec, keep the typed span. `golden:sheet-bend-fillet-cut`. Appending after the return leaves the Extrude chip on the strip and never builds the solid: that is what a sheet part with a study after `return part` was doing (Sheet Metallica). `golden:sheet-extrude`.

## Separate bodies (Merge bodies off)

- **Script.** `part = part.add(solid, { merge: false })` → `Manifold.compose([part, solid])`, no boolean. Bare `part.add(solid)` / `{ merge: true }` is the union it always was. Installed on the embind prototype by `installSeparateBodies` (`src/workers/separateBodies.js`) right after `setup()`.
- **Overlap guard.** Composed bodies may overlap, and Manifold's own boolean fuses them wherever the other operand reaches the overlap. So when the receiver's bodies have overlapping boxes (`overlappingBodies`: positive-volume box overlap; a touching cut plane does not count):
  - `subtract` / `intersect` run per body the tool's box meets, the rest are kept, then `compose`.
  - `add` (merge on) unions the tool with every body it actually joins (raw union of that body + tool has fewer components), keeps the others, `compose`s. Touching two bodies fuses them. Touching none → its own body.
  - One body, or bodies that do not overlap → the original method, bit-identical. Static `Manifold.union/difference/intersection` are not patched (`booleanBodies` uses them on the picked bodies).
- **Face features** (`hollow`, `draftFaces`, `moveFace`, `deleteFace`) go through `_perBodyFaceOp` on overlapping bodies: a named `{ center, normal }` goes to the body whose facing surface (normal within ~8°) is closest; unnamed selectors (`'z'`, `'all'`, `'sides'`, `'none'`) run on every body; untouched bodies are kept.
- `filletAlongPath` (fillet + chamfer), `cut`, `move`, `booleanBodies`, `externalBody` already split by body.
- **Viewer.** Compose shares no vertices, so `meshBodyComponents`, double-click `selectOwningBody`, the part graph, `buildFeatureEdges` `bodyId`, Cut / Boolean Pieces and `bodyCentroids` all see the bodies as distinct. Graphs rebuild on the run like any confirm; no new rebuild rule.
- **UI.** `SOLID_MERGE_PARAM` (bool, default on, `showWhen` combine = add) on all six Blocks and the Extrude / Revolve / Loft fallbacks; `ContourModeChip` shows the checkbox only for a solid in Add; Viewport sends `merge` in the commit payload (forced on in Subtract). The first solid is still `let part = …`.
- **Strip.** `parseFeatureMarkers` sets `separate` when the block holds `.add(…, { merge: false })`. `FeatureStrip` draws the violet two-squares marker only when that flag is set **and** the live part still has more than one body (`featureShowsSeparateBody` + `bodyCount` from the last run). A later Boolean union (or any fuse to one body) clears the marker even though the script still says `merge: false`.
- **Limits.** Reported `volume` (and so the quote) is the sum of bodies: an overlap counts twice until a Boolean union. Export writes overlapping shells. `shell()` used by hand as `part.subtract(shell(part, …))` and `addDraft` see the whole mesh. A Boolean union of overlapping bodies is the only way to fuse them besides a merge-on Add that touches both.

Worker faces (`c4MeshData`): a Manifold `faceID` is split into edge-connected components, then components on the **same plane and the same body** are merged. The 0.1° coplanar merge also skips an edge whose two triangles are in different bodies. Body id is the vertex-connected component (`_triComponentIds`): a keep-both cut does not share vertices, so each piece is its own body even when `faceID` is reused. That is what the comment means by each body keeping its own contour. Curved components are not re-merged. A same-offset re-merge also needs the components' own normals within 2° (`COPLANAR_PAIR_MIN_DEG`): `faceID` is only unique within one source mesh, and every swept fillet cutter has the same triangle numbering, so `faceID` k is a facet on each earlier fillet. Two such facets on different fillets can sit at the same offset along their averaged normal on a symmetric part; merged, that face's normal was 45° off both, and `signedFeatureEdges` handed it to the next fillet as the edge dihedral (the three-fillet corner blob). A fillet boolean can still leave two copies of a cap vertex about 0.001mm apart, so that merge keeps two faces. A named `moveFace` pick includes the other face when it is the same plane, the same body, and a vertex of each lies within 0.02mm. It also includes a larger face on that body when the pick is a scrap within 10° of it, they share a vertex, and the scrap lies within 0.012mm of the larger plane. The curved blend is degrees off that plane and stays out. `hollow`, `draftFaces`, `cut`, and `deleteFace` still resolve one face.

## When to rebuild graphs

There is no `rebuildGraphs()` and no per-op hook. Cut, Draft, Move Face, and Delete Face do not rebuild anything while the picker is open.

| Graph | Where | Built | Invalidated | Rebuilt |
| --- | --- | --- | --- | --- |
| **Face** (PartGraph) | `faceGraphFor` WeakMap on the BufferGeometry. | `warmFaceGraph` in `renderMeshData` when the mesh is shown, including after fillet. A click builds it if that paint missed. Curvature κ walks each atom's neighbor list in adjacency-record order. Manifold gives each triangle its own `faceID`, so a scan of every record once per atom was quadratic in the fillet. The planar bridge floods a flat only when another triangle lies on that plane (same 0.5° / 0.05 mm test); a fillet facet with nothing else on its plane is left as it is. Seam vertices are binned by packed integer cells, same 0.02 mm pitch. The patches are unchanged. | `renderMeshData` replaces the geometry. The WeakMap misses, then that paint fills the new mesh. | That paint. Not while Cut, Draft, Move Face, or Delete Face is still on the old mesh. |
| **Edge** | `buildFeatureEdges` inside `featureGraphFor` (`partSolidCache.js`), called by `syncFeatureEdges`. Cached in a WeakMap by geometry object + faceID array; `featureEdgesSourceRef` is the bound geometry. | Dihedral **≥ 2°**. Each edge gets `bodyId` from `meshBodyComponents` (shared vertex index = one body). | A new run is a new geometry, so it misses. An empty script clears and does not rebuild. | End of every successful run, including Cut and Draft confirm. Fillet enter, leaving Fillet in Edge, Sweep path pick, and a part switch re-sync, which is a cache hit when that solid was already built. |
| **Body contours** | `buildCoherentEdges` in that same sync. Not a third cache. | Feature edges with dihedral **≥ 15°**, traced into chains. A keep-both cut shares no vertices, so a vertex walk cannot cross pieces. `bodyId` also blocks collinear merge and the spatial / parallel-face bridges (those links do not require a shared index). | Same as the edge graph. | Same call. If `faceID` is present, `indexBoundaryEdges` also runs and annotates those edges (fillet `fN` / `eN`). |

**Face graph walls.** The face graph rebuilds only in that paint (`warmFaceGraph`, cached by geometry + `faceIDs`; a new run is a new geometry). The adjacency basis is shared vertex-index edges; planar claims also count vertices within 0.02 mm as touching (`seamTouch`). `faceID` is close to per-triangle, so it is not a wall. The wall is the **feature source** of each triangle (`geometry.userData.triSource`): the worker brackets every `filletEdges` / `filletAlongPath` / `chamferEdges` call by Manifold `originalID` and tags runs created inside it with one negative op key (`mesh.runFeature`). Other runs keep their `originalID`. Atoms of one source join under that source's gate. The curved merge also crosses from one fillet call to another when both triangles are fillet ops (a negative feature key and a recorded facet step) and the dihedral is within both gates. A loft wall, a flat, a hole, and a chamfer have no fillet step, so that walk stays off them. The dihedral gate is per source, from the tessellation stored with the feature tag (`mesh.featureTessellation`, copied onto `geometry.userData.featureTessellation`): `roundedBox` and `filletEdges` record a full-circle step (360°/segments; filletEdges is 384, its corner ball 256), and `filletAlongPath` records the right-angle wedge step (90°/segments). `chamferEdges` is a flat wedge and records none. The gate is max(facet step, corner-blend join) × 1.15, clamped to [15°, 50°]. The corner join is the widest same-source curved dihedral finer than the facet step, measured when the graph is built. A source with no tessellation falls back to 15°. A 16-segment rounded box steps 22.5° and meets its corner at about 18°, so the gate is 25.9° and one click follows the whole tangent chain; 8 segments (45°) clamp to 50°; 32 segments (11.25°) stay on the 15° floor. Flats stay locked. A facet that meets its neighbor at the recorded step is that feature's own tessellation, so the area lock does not freeze it (an 8-segment rounded edge is one large quad). The curvature test (rate above 0.55 splits a real radius change) still does not run inside one fillet op, so a coarse strip of one call is one face. Each atom's rate counts only its own source's neighbours across a real step (above the 0.5° coplanar gate, below 25°): a tube wall that other bodies are unioned into is re-cut along the junctions, and the coplanar halves of one facet, or the other body's facets, used to pull the rate down and split the wall into fragments at every junction. A gate comparison carries 0.05° of slack so a facet step equal to the gate (a 24-segment cylinder on the 15° floor) still merges. A patch is `planar` when it is a locked flat, or when every triangle normal sits within the coplanar gate of the patch normal and its rate is under that gate; the old `meanK < 1e-6` read float noise on a tilted flat far from the origin as curvature once a large ring in the same body kept it under the area lock. Cylinder axes (`fitJointAxis`, `src/utils/cylinderFit.js`) are a least-squares fit: the axis is the direction the normals span least, and a Kåsa circle fit of the projected vertices gives the centre and radius, so a wall that tubes cut into lands on its true axis instead of the surviving arc's vertex centroid. It does not run on a fillet-to-fillet crossing either: the gate is the angle. On the Testpart, fillet 1 (r=4) meets fillets 2 and 4 (r=4.83) at about 2°, under the 15° floor, so one tap selects that chain. The loft fillet meets the loft wall at about 0.8° and stays off it. Two fillet calls on adjacent cube edges meet near 92° and stay apart. A radius cusp inside one `filletEdges` call stays split.

`indexBoundaryEdges` (worker `edge()` and viewport labels) keeps a boundary when dihedral ≥ 15° **and** the smaller face is ≥ 5% of the largest face. That is a stricter set than the coherent chains. Shallow blend facets stay out of both.

On that rebuild, triangle edges are indexed by a packed integer (`lo * 2^26 + hi`), with a string only when a vertex index does not fit in 26 bits — the same kind of numeric key the face graph uses. The 15° / 5% gate runs before segment records are allocated; the kept boundary set is unchanged. Collinear copies in `buildCoherentEdges` are still grouped against the first unused seed, not unioned along a curve. That seed only consults numeric bins of the line's perpendicular foot (the cell is at least the 6° / 0.45 mm slack, and the neighbor cells are included). A contact seam needs two vertex-connected bodies, so one body stops after that count.

**After Cut confirm and after Draft confirm** the path is the same: Confirm writes one call, Auto-Run, `renderMeshData`, then `syncFeatureEdges` on the new geometry.

- Edge graph and body contours are rebuilt in that success path.
- The face graph is rebuilt in that same paint (`warmFaceGraph`). A new geometry is a WeakMap miss, so the graph is the new mesh, not the pre-fillet one.
- In that rebuild, coplanar pieces of one plane in the same body become one face when a fillet sits between them, even if the face ids still differ. Vertices within 0.02mm count as touching, so a duplicate-vertex seam on that plane is the same face after the needle between the copies is dropped from the drawn mesh. The curved blend stays its own patch. Coplanar walls whose path leaves the plane stay separate faces.
- Face and edge picks are cleared, except Fillet mode and Sweep contour mode, which keep the edge wire and re-stamp boundary ids.
- The live Cut preview (`previewCut` on a clone) and the Move preview (translated triangles) do not replace `resultRef.geometry`. Graphs stay on the uncut / unmoved solid. Preview meshes do not raycast. Move keeps absolute XYZ in the card; `movePreviewOffset` shows only the delta from the committed move, and a fresh pick on the same body seeds those sliders from `parseLastMove` so the ghost starts on the solid. The card subtitle uses `moveBodyWorldAt` (anchor plus the last move when the anchor matches). Feature edit reopens with mesh triangles from `attachMoveTargetMesh`.
- The Block preview (`previewBlock`) builds only the new solid. It does not read or assign `cachedManifold` and does not replace `resultRef.geometry`. Graphs stay on the host. The preview does not raycast. Add and Subtract both paint it with the shared preview recipe (`utils/previewStyle.js`, `makeBlockPreviewSkinMaterial`): unlit translucent cyan, the same as Loft. Subtract also skips the depth test, so the cutter shows through the host.
- The Boolean preview (`previewBoolean` on a clone) does the same: `cachedManifold` is not assigned. Intersect piece meshes do raycast, including a hidden piece drawn at opacity 0, so a second tap brings it back. Body picks do not. A cross-part intersect first moves the pick mesh to the target part, then the worker runs the target's script and each tool part's script (not cached), poses the tools by the assembly offset, and splits that result, the same solid Confirm will write. Pieces are drawn at the target's position.
- The cross-part subtract probe (`probeOverlap`) runs the frozen cutter and rebuilds each candidate part from its last mesh. It does not read or assign `cachedManifold` and does not rebuild any graph.
- Draft highlights do not change the mesh. Taps before Confirm still read the pre-draft graphs.
- Shell confirm uses this same run path. Nothing in the graph code special-cases shell.
- **Move Face confirm** is the same path: one `moveFace()`, Auto-Run, then the edge graph, body contours, and face graph rebuild. Fillet confirm is the same paint: the face graph is rebuilt with the filleted mesh.
- The Move Face preview runs `moveFace` on a clone. It does not replace `resultRef.geometry` and does not rebuild graphs. Dismiss writes nothing.
- **Delete Face confirm** writes one `deleteFace()` for every picked face, replaces the previous Delete Face block, Auto-Runs, then the edge graph, body contours, and face graph rebuild. A heal that cannot stay a closed solid throws on that run.
- A Delete Face tap only adds or removes the face. It does not run `deleteFace`. Leaving without Confirm writes nothing.
- **Assembly.** A face, edge, or body pick retargets the active part. Graphs then bind to that part (face graph when the mesh is shown, edge graph and contours at the end of the run, or from the switch cache below), and highlight and preview anchors move with its rigid pose. The script pane stays pinned until the user opens Script or Parts, clicks a body, or picks during a feature. A failed run, or hiding that part, clears the pick mesh and does not rebuild from a previous solid. Other visible parts raycast. Showing or hiding them does not rebuild graphs until a pick retargets onto one of them.

What the new mesh contains is the difference, not the rebuild:

- **Keep-both cut.** Two vertex-disjoint bodies. Vertex walks cannot cross them. Face and edge graphs clip to the seed body: `selectGraphFace`, legacy taps (Move Face and Delete Face included), and the part-graph merge drop triangles that belong to another body. An edge walk skips a neighbor whose `bodyId` differs. The shared edge is painted (below).
- **Draft.** One body, unless the input was already split. Vertices of the drafted faces move, so dihedrals change, so the 2° / 15° gates can drop or keep different edges. No draft flag is stored on an edge.

## Face identity (stamps)

Every helper that knows what it builds names its faces at construction (`mvp/surfcad-face-identity-design.md`; `src/lib/surfcad/runtime.js`, "FACE IDENTITY"). `Manifold.cube`, `Manifold.cylinder` and `Manifold.sphere` as a script sees them, plus `tube`, `hexPrism`, `roundedBox`, `makeExtrude` and `makeRevolve`, record which of their result's triangles play which role and keep that in a per-run table keyed by the run's `originalID`: `{ feature, helper, roles: [{ role, record, ranges }] }`, where `ranges` are the `faceID` intervals of that role. The mesh itself is untouched: Manifold already gives every run an `originalID` and every triangle a `faceID`, carries both through every boolean and transform, and this build's ids are per triangle, so a run's `faceID` values pick the role exactly. Because nothing in the mesh changes, the boundary ids Fillet mode writes into scripts (`edgesBetween(part, 3, 6)` is the minimum raw `faceID` of each face), the face graph, the C4 face helpers and the fillet cutters see exactly what they always saw, and two identical cubes still carry identical ids.

`feature` is the id of the marked block that was running when the helper was called (`cube1`, `tapDrillHole-11`), else `<helper>@<n>` counted in script order, so a rerun of the same script gives the same names. `role` is helper-defined: `top bottom left right front back` on a box, `side top bottom` on a cylinder (`inner` on a tube), `surface` on a sphere, `wall[i]` on a hex prism, `band[i]` / `corner[i]` on a rounded box, `cap0 cap1 wall[g]` on an extrude (one logical edge per profile edge; a circle profile is one `wall[g]`), `seg[g] end0 end1` on a revolve, `cap0 cap1 wall[g]` on a sweep (`sweep` / `sweepPoints`: caps on the path's end planes, each triangle read through the path frame nearest its centroid, the record carrying the profile edge and, for `sweepPoints`, the path), `cap0 cap1 span[i][j]` on a parallel `makeLoft` (bottom-profile edge `i` at the triangle's polar angle, station span `j` from its height; caps by height, since a collapsed station leaves slivers with no usable normal; an angled loft is not stamped). `record` is the surface the helper built, from its arguments, never from fitting: `plane`, `cylinder`, `cone`, `sphere`, or `mesh` when there is none; it is in the frame the helper built in and a later transform does not move it. A hull, a fillet cutter, or a freehand `Manifold.*` call made outside the stamped helpers has no row and so no name.

`serializeResult` ships the rows of the runs the final mesh still uses as `mesh.faceStamps`. `buildSolidGeometry` runs `stampedPiecesForMesh` (`src/utils/faceIdentity.js`) on the full mesh data before it drops needle triangles: label each triangle from its run `originalID` and its `faceID`, group by label, split each group into connected pieces (triangles that share a vertex), and keep a piece id per kept triangle on `geometry.userData.faceIdentity`. Pieces are found on the full mesh because a loft carries thousands of needles and connectivity on the trimmed mesh falls apart in rows where they were; the kernel keeps them, and `_stampedFaces` uses the same vertex rule, so both sides name the same pieces. `stampedFaceTable` then measures the kept triangles of each piece, orders the pieces of one label by centre and appends `[k]` when there is more than one (a slot through `plate.top` gives `plate.top[0]` and `plate.top[1]`; a union of two copies of one solid, which shares one `originalID` across two runs, does the same), and reads the edges between named faces off the shared triangle edges (`cube1.right~cube1.top`, chained into polylines, `[k]` for a pair that meets more than once). The table is cached by geometry and faceID array like the other graphs, so a new run is a new table.

The face graph stays the pick unit. A `list_faces` row is still one PartGraph patch with its fingerprint `key`; the row adds `name`, `feature` and `role` from the stamped face that owns most of its triangles, and `names` when a coplanar union or a curved merge put several labels in one patch; `filter { name, feature, role }` narrows by them. In the kernel, `faceNames(part)`, `facesNamed(part, name)`, `edgesOf(part, name)` and `surfaceOf(face)` read the same table from the solid's own mesh (`_stampedFaces`); `facesNamed` returns faces that `workplaneFromFace`, `hole`, `hollow`, `draftFaces`, `moveFace` and `deleteFace` accept, `edgesOf` the convex `signedFeatureEdges` that touch the named face (concave ones counted on `skipped`, never thrown), and both throw naming what exists when nothing matches, never a nearby substitute. The dev hook `window.__VIEWPORT__.faceTable()` is the active part's table as plain data; `golden:face-identity` pins the names across an edit and a rebuild.

**Picks carry their name, and a named pick survives a rebuild.** After every successful run the viewport clears the face pick (the triangles index the mesh that was replaced) and, when that pick carried a name, finds it again on the new mesh through the table (`resolveFaceNames`) and publishes it, marking `data-feature-picks="renamed"`; a second `use_selection` insert therefore lands on the same face, which is what the bike session's second hole should have done (#679 had made that a `no_selection` refusal). A pick with no name clears as before, so `no_selection` stays only for a face that was never named; edge picks are unchanged. `golden:face-identity-rebuild` pins both cases. `publishFacePicks` names every face pick from the table (a click, `select_faces { keys }`, or `select_faces { names }`, which selects the stamped face's own triangles, so a rounded box's top is picked without its band even though the face graph merged them). `classifySelectedFace` keeps `name` on the face context, and the composers switch on it: `emitFaceWorkplaneLines` writes `facesNamed(part, "boss.top")` (nearest piece to the pick when the label is split) instead of `facesByNormal` plus nearest centre, and `emitFaceEdgeLines` writes `edgesOf(part, "boss.top")` instead of filtering every convex edge on the body by normal (the seat-boss chamfer that touched hundreds of edges and blew the 30 s budget now touches the four around the boss top). A pick without a name (an unstamped face) takes the old path unchanged. `select_edges { names: ["a~b"] }` resolves through the table's edges to the feature-edge segments between those faces, and raw `list_edges` rows carry `name`, `faceNameA`, `faceNameB`. `golden:face-identity-select` drives all of it through the bridge.

## One click, one face

`resolveViewportFaceClick`:

- **Default (one click).** The PartGraph patch of the hit triangle. A flat is every coplanar triangle on that plane in the body, including a cap a fillet split onto the other source body's face id. A curved face is the curvature-merged band. The blend stays its own patch. A loft wall is one face: the low-curvature part of that wall is large enough to look like a flat, but it meets the rest of the wall across a shallow edge (≤ 3°) on the same source, so it is not locked and the curved pass keeps going. A real flat still locks. It meets the next face at a crease, or a fillet of another feature, so the blend does not swallow it. A tall, thin prism wall (a pin from `Manifold.cylinder`) has side facets over the flat-lock area gate; a run of three or more congruent facets (area within 20%) of one source that meet at one repeated step above 3° and at most the smooth gate, with no other same-source smooth neighbour, unlocks, so one tap is the whole wall. An octagon or hexagon prism steps over 15° and keeps its sides; a sphere's facet rings meet the next ring and stay as they were. One tap paints that whole wall. If the mesh has more than one body, triangles outside the seed body are removed. The hit triangle alone is not the face.
- **Default (double click).** The vertex-connected body (`selectOwningBody`), not a wider face.
- **Shell, Draft, Cut** pass `legacy`. One click on a flat is that same planar patch. Two clicks are the 3° neighbour walk, three clicks are the connected component. A double click does **not** become the body, so Confirm still writes the tapped face. A click on the blend stays the coplanar facet.
- **Move.** One click is the full face and does not change the target. Double click sets that body (`{ at }` centroid).
- **Move Face.** One click is that same planar face, not the curved fillet. A double click is still the 3° walk, not the body, so Confirm still writes the tapped faces. Triangles outside the seed body are removed. The fillet and the cap are one vertex-connected body. `moveFace` still carries a tangent blend with the offset; the click does not select that blend. The offset also includes the other coplanar face across a duplicate-vertex seam (≤ 0.02mm), and a larger face when the pick landed on a scrap of that plane. The needle between those copies is not drawn. The highlight outline drops that seam, so the click has no line between the fillet side and the main side.
- **Delete Face.** Same legacy tap as Shell and Move Face, including that seed-body clip. A double click is not the body. The tap does not delete.

Worker face picks (`{ center, normal }` passed to `hollow` / `draftFaces` / `cut` / `moveFace` / `deleteFace`) resolve in `c4MeshData`, not in PartGraph. A named pick stays on the body whose surface contains the center. It does not move to another body because that face's center is nearer. The two face graphs are not kept in sync. `moveFace` then includes the coplanar face across that 0.02mm seam, and the larger plane when the named face is a scrap of it, so the offset matches the one face the click already selected. `deleteFace` uses that same center and normal and does not take the extra face.

## Face color match

A saved face color is found again from the face graph. `faceFingerprints` (`src/utils/faceColorMatch.js`) reads the PartGraph of the mesh just shown. It does not paint. One patch is one fingerprint, the same `key` stored on `colors[surfId].faces[]`:

- `at` is the patch centroid (area-weighted, mm). `n` is the unit area-weighted normal. A closed wall whose normals cancel keeps the largest triangle's normal. `area` is the patch area.
- A fillet or chamfer patch also stores `src` and `ord`. `src` is the negative feature key (`triSource`) that owns more than half the patch's triangles. `ord` is that feature's patches sorted by center, so two blends from one call stay distinct.
- Rebuild the fingerprints when the face graph rebuilds: after a successful run (a new mesh is a new graph), and on a part switch (read that part's graph, not the previous part's).

A key matches one face when the normal is within 8°, `at` is within 1 mm, and the area is within ±25% of the saved area. Faces are binned by `at` (1 mm cells) and by normal; the search checks that cell and its neighbors, then applies the tolerances. When more than one face is in tolerance, a stored `src` or `ord` picks the feature patch. One face in tolerance still matches if that feature index moved, so a rebuild does not drop a paint that still sits on the same face. Two or more faces in tolerance with no unique feature hit drop the key as ambiguous. None drop it as missing. There is no guess and no error. A key is compared only to the part it was saved on, so an identical solid under another surf id does not take the color.

## Face color skin

`syncFaceColorSkin` (`src/utils/faceColorSkin.js`) paints that match. It runs after a successful run, when the active part changes, and when the assembly is placed. An empty `colors` map skips it. The saved keys are not rewritten.

- The skin is a child of the part mesh, one per surf id, named `face-color-skin`. It is a lit `MeshStandardMaterial` (metalness 0, roughness 1, specular cleared) on the part's triangles, with a view-space headlight and no distance falloff. A face pointing at the camera reads as the swatch; a turned face is darker. The scene point light decays to nothing at fit distance, so it is not what lights the paint. Vertex colors stay sRGB in the buffer and the shader decodes them before lighting. `polygonOffset` (factor -1, units -2) and no depth write stay: the skin is a different shader on the same triangles, and mobile GPUs z-fight that into stripes without the offset. It does not raycast, so a pick hits the same face as before.
- `colors[surfId].part` fills every triangle. A matched face color is painted over that. Ambiguous and missing keys draw nothing.
- Draw order: solid, then the skin (render order 2), then crease lines (3) and pick highlights (6). Edge and contour lines stay above the skin. A cut, Boolean, or Move Face preview that hides the solid hides the skin too. Hiding, deleting, or dropping a part detaches the skin and disposes its geometry and material.
- `?debugFaces=1`, or `localStorage` `surfcad.debugFaces` = `1`, paints each patch its own color. Off unless that flag is set. It is not a rail button. Game mode uses the same skin and the same pick ray.

## Face color paint

The Paint button (`data-paint-chip`) sits in the right viewer bar, in the plane and contour group, with the same button style as its neighbors. It is green only while paint mode is on. It is not in the title row and it is not rendered in game mode. A per-face rainbow is `?debugFaces=1` or `localStorage` `surfcad.debugFaces` = `1`, not a rail button. Saved colors still draw in game mode. Turning the button on opens the shared feature card (`data-feature-card`, `data-paint-mode`) between the rails. Game mode mounts no card.

A tap paints that face immediately, on the overlay skin, in the selected swatch or the custom hex. There is no separate selection step. A second tap on the same face within 300 ms (`PAINT_DOUBLE_TAP_MS`) upgrades that one paint to every face of the body under the finger, as one `faceColorKey` per face, and does not push a second undo entry. The first tap is not delayed. A tap on a different face is a new action. Phone and desktop share this path: one `mouseup` per tap, so a synthesized click is not counted again. The canvas keeps `touch-action: none`, and `dblclick` is cancelled, so a double tap does not zoom the page. A saved contour or a construction plane under the cursor does not take that tap while Paint is on. A blend and a coplanar seam still resolve to the same face they already do. Nothing is written onto another surf id.

Part paints `colors[surfId].part` for every body of the part. A double-tap paints only the body that was hit. On a single-body solid they look the same, so Part stays. Part is an action, not a mode: a single tap still paints one face. Pressing Part when the part is already that color does nothing.

Nothing is written to the assembly until Confirm. The session is viewport state, and the skin reads it while the popup is open. Confirm writes that session once through `rememberAssembly` (working copy only; Save / `git_save` is the git write), then closes. That is one assembly undo step. Local and signed-out save the local assembly. Part `isSynced` is unchanged, same as a group rename. Face colors are `faceColorKey` entries in `faces[]`. A saved key that uniquely matches that face is replaced when the color changes, so a repaint does not duplicate it. The same color on a face that still matches keeps the saved key. `set_script` and `run` include `droppedPaints`: each saved face color the mesh just built will not draw, as `{ surfId, color, key, reason }` with reason `missing` or `ambiguous`. An empty array means every saved face color still matches. Whole-part `colors[id].part` is not in that list. X and Esc drop the session, repaint the colors from when the card opened, and write nothing. Undo steps back one paint action. Clear restores those pre-session colors and can itself be undone. Remove unmatched colors edits the session only. Ambiguous and missing keys are left in place until that button. The swatch grid is padded so each circle and its selection ring stay inside the scroller, including the wrapped row on a phone. A bad custom hex does not paint and does not confirm.

## FEA study panel

- Analyze (`data-analyze-chip`, Lucide `Gauge`) is the first button of the right-rail inspection group, next to Paint. It uses the same blue as the neighbouring rail icons and turns green only while the study is open. It is not on the left rail and it is hidden in game mode.
- Opening Analyze closes Paint and the other feature cards. Opening another card closes Analyze. Phone and desktop both use the shared bottom card (`data-feature-card`, `data-fea-sheet`). The left tool rail is hidden on both, so the card passes `fullLeft`: the left edge is 10px from the pane, and the right edge stays 10px clear of the right rail. On a phone the card docks at the pane bottom and the stage switcher hides. The footer is Run, or Back to Setup after a solve. After a solve, the legend, Stress and Displacement tabs, and Stage times scroll in the body, so Back to Setup stays on screen. Contact joins those tabs when a pair is not bonded. It does not say Confirm. X and Esc close Analyze through the card's onCancel. Game mode mounts no card.
- The panel picks a library material or a custom E, ν, and yield. An assumed or missing ν or yield shows an assumed badge. Face taps reuse the paint pick and `faceColorMatch` fingerprints. Fix, force (newtons and a direction), or pressure (MPa) adds that face; the list removes it. Run calls `feaClient.solve()`. The worker lazy-loads `meshVolume`, builds a TET10 mesh, and calls `solve_tet10`. The legend shows min, p95, and max in MPa and the safety factor (yield / p95, or n/a). A real run sets `source` to `tet10`. The STUB badge is only the dev fallback (`fallback: "stub"`).
- Thin solids use Cholesky. Compact solids use PCG. Shells stay unwired (`capabilities().shells` is false) until a midsurface exists; a shell model warns and still solves TET10. A phone (touch, plus a small screen or `deviceMemory` ≤ 4 GB) caps a thin TET10 mesh at 100k DOF, a compact Cholesky mesh at 40k, and a compact PCG mesh at 100k. Auto on a thin part asks for two elements through the wall when that edge fits the cap and the memory budget. When it does not, the mesh keeps the bbox edge instead of an intermediate length that slivers. On the 3.175 mm hat bracket that bbox edge still leaves several elements through the flange, because fTetWild refines to the wall. A cap that lengthens an explicit edge warns. Desktop is otherwise limited by memory. On a phone the worker instantiates non-shared wasm with a 512 MiB ceiling. Run shows meshing, solving, and post-processing. Cancel rejects the in-flight solve.
- After Run, a stress skin colours the active part from render-vertex von Mises samples of that field. The ramp is viridis from 0 to max(p95, yield) MPa. Values above yield (or above p95 when yield is missing) are magenta. The skin is keyed by the `buildSolidGeometry` object and by faceID, not by triangle index. The paint skin is hidden while the stress skin is up and restored when Analyze closes or Paint opens.
- A geometry edit, a material change, or a fixture or load change marks the result stale. The coloured skin comes off and the legend says Re-run. Stale colours are not left on the part.
- The study is the comment block after `return part;`, written and read by `studyScript`. The commit stores that part script itself, so the drawer can stay closed and Monaco does not have to be open. A mounted editor receives the same buffer. The write does not call `preemptInflight`. While an assembly open holds the worker the write is refused, and no build is posted. A reauth boot stays read-only.
- A study can name the active part (the default; `scope` is omitted), the whole assembly (`scope.kind` `"assembly"`), or a subset (`scope.kind` `"parts"` with `ids`). Each selected part stores its own material. A sheet-metal `sheetSpec` name or sku maps onto the library when it matches; every other part uses the study material. v1 studies that omit `scope`, `parts`, and `contacts` still load, and those keys are left out of the comment until they are set.
- Touching faces between parts are detected with a bounding-box broad phase and a triangle-centroid narrow phase. Each part's `matrixWorld` (or position, quaternion, and scale) is applied to its surface first, so a rotated or scaled part still meets its neighbour. The gap is 0.05 mm or 1% of the shortest edge, whichever is larger. A new pair is bonded. The study can store that pair as bonded, frictionless, or frictional, and a frictional pair stores μ (default 0.2). A pair the user turns off keeps `enabled: false`, and a law the user already chose is kept when the same faces are detected again. The viewport draws those faces on the part that owns them. Side faces that only share an edge are not pairs.
- Run bakes that same matrix into each surface and meshes the part on its own. Bonded pairs call `solve_bonded`: slave nodes are tied to master TET10 faces by a projection multipoint constraint, then eliminated so the matrix stays symmetric positive definite for faer Cholesky and PCG. A study with a frictionless or frictional pair calls `solve_contact` instead. That is node-to-surface, small sliding, penalty plus Uzawa, with a Coulomb stick/slip return map. Bonded pairs in the same study are still eliminated. The Cholesky factor is reused while the active set is unchanged. Shell-to-solid ties are not solved. The phone cache keeps both volumes in one entry, and the phone DOF cap is split across the parts. A frictional phone cap is lower: about 25k DOF for a thin TET10 mesh and about 10k for a compact one. When that cap lengthens the edge, the warning names the frictional cap. The legend is one field. The safety factor is the minimum of yield / p95 over the parts, and the legend names the part that governs. The color scale uses that part's yield. After a solve that has a non-bonded pair, a Contact tab shows pressure on those faces (viridis) and the open, stick, and slip counts. The rest of the part stays visible.

## Contour paint

What you see as an edge is not one list.

1. **Crease.** The solid is flat-shaded off-white (`DEFAULT_PART_COLOR`, `#ECEAE4`). A crease is the shade break where two adjacent triangles have different view-space normals under the camera headlight. The shader has no angle cutoff. A coplanar diagonal (same normal) does not show. This is not stored. A needle left between two copies of a cap vertex is dropped before the mesh is shown (`dropPlanarFins`), including one shorter than a bend chord and the ~0.03 mm tangency needle on a sheet-thickness fillet, so it is not a crease and not an edge of the face graph. A thin fillet facet is the only cover of its own surface and stays. Saved idle contour wires are a dark line so they stay readable on that off-white.
2. **Pick contour.** `paintEdgeLines` draws `edgePolyline` of the **selected** or hovered coherent chain (and saved sketch-contour wires). It does not draw every coherent edge. Fillet and Sweep path consume those selected chains (`assembleSweepPath` / `makeSweepPath`). An edge enters that chain only through the gates above: dihedral ≥ 2° to exist, ≥ 15° to join a contour, and the chain must survive the simplify / spine tests. Collinear pieces of one straight side join across a hole of up to 1.1 mm when both pieces are at least 0.25 mm; a shorter sliver does not stretch the crease across that hole. Gaps up to 0.75 mm still collapse coincident copies. A 64-segment circle-to-rectangle loft leaves a measured 1.00 mm hole on the long side (x = 7.50 → 8.50: the cap and the wall do not share a vertex), and the old 0.75 mm gap left that side as a 17.5 mm pick, 2.5 mm short of the corner. The last crease on that side ends at x = 9.50; the corner vertex 0.5 mm further is the start of the perpendicular side, not another piece of this line. A 90° corner is still a different edge (a cube edge stays one edge; turn ≥ 85° is rejected). Pieces of a keep-both cut do not share vertices, and `bodyId` blocks the bridges that would join them anyway. The tangent walk stops when the next edge's tangents diverge by more than 28°.
3. **Shared cut.** Only `contactSeamSegments`. See below.
4. **Face highlight.** `highlightFace` paints the picked triangles (polygon offset toward the camera, no depth write, so the fill does not z-fight the part) and a line on each boundary edge (`highlightBoundaryPositions`). Picked vertices are welded at 0.02mm before edges are counted. A welded key can be a duplicate-vertex seam, or a paper-thin triangle whose real edge and a neighbour's diagonal collapse together: on a 64-segment circle-to-rectangle loft the cap corner sits 0.006 mm off the long side, inside that weld, and a second triangle owns the diagonal. The line is drawn when any raw edge of that key still clears the side test. Requiring the key to belong to exactly one triangle hid the real edge, so the rectangle outline stopped mid-side (about 38 mm of line instead of the 64 mm loop). When only one end of that sliver welds, the sliver and the real side stay two keys and can both draw, a few thousandths of a millimetre apart; on the Testpart cap that adds about 2 mm to the measured length. An edge is drawn only if the point 0.02mm past its midpoint, on the far side from its owner, is not on another picked triangle. A neighbour that shares an endpoint counts. The old check skipped such neighbours and drew the diagonal left by a dropped needle (a T-junction) and every strip seam of a fillet. An edge is also not drawn when its midpoint lies within 0.02mm of a picked triangle that has neither endpoint and reaches past the edge: that is a duplicate-vertex seam. The curved fillet is a separate pick. A click on the cap does not trace the line between the fillet side and the main side, and the fillet's own outline stays.

**Edges that end on a drafted face.** No painter checks "drafted", and there is no draft flag. After Draft confirm the mesh is new and the same gates run on the new dihedrals. An edge under 15° is absent from the coherent contour. The 28° tangent walk stops when the next tangent diverges. A 12° draft leaves the wall edges well above 15° (about 78–102° on the playtest cube), and that 28° walk already stopped at the 90° corner before the draft. Those gates were not why the wrap stopped short. The documented guess that they were is wrong.

The varying-profile cutter swept one tube through that 90° corner. The easy path already splits a run at a turn sharper than `FRAME_DENSIFY_MAX_TURN_DEG` (5°). The varying-profile path now does the same: one tube per straight leg, then union. A smooth loft (turns ≤ 5°) stays one run. The shredded mesh was what broke the drafted-face contours into short fragments.

The easy dihedral cutter is one ring per path knot (`_s23SweepKnotRings`), the frame at that knot, the cross-section left as `FILLET_ARC_SEGMENTS`, ends capped. Knots stay at `FRAME_DENSIFY_MAX_TURN_DEG` (5°). A uniform extrude along the run length is not used: slices spaced by arc length miss a short arc chord that shares a run with a long straight. A closed loop is still one lap plus an 8% overlap, capped, so the joint is not a seam. The hard path is unchanged (one ring per knot already). A span longer than 29 mm gets one or more linearly interpolated rings on that same ruled quad (`_S23_LONG_CHORD_MM`). That is what makes a full-height fillet meet the cap as one loop; the path knots are not moved, and a 28 mm wrap straight stays one quad. A measurement flag, `__FILLET_REF_STATION_MM`, replaces the 29 mm step with a finer grid. Those vertices lie on the ruled quad, so the cutter solid is the same polyhedron.

After the boolean, `_s23WeldFilletResult` snaps vertices within 0.001 mm and drops the collapsed triangles. A long wrap fin is a triangle whose short edge is a duplicated vertex on a ruling; the rounded top rim comes back as several chains for the same reason. The rebuild is kept only when it is a strict solid and the volume moves by less than 0.001 mm³.

An open fillet end extends in two cases. Neither is a sphere cap, and neither is the concave open-end pad. The knot stays where it is: the pad is a new station past it, same frame, so that knot still has a ring.

- The end lands on a tilted face. The distance is how far the end profile must travel to clear that plane, capped, plus the sweep expand pad. Clearance about 0 means the end is already on the face. Alignment tighter than cos(2°) is not that test. A rounded run samples the back end only.
- The end is not an original path end, and the turn there is about 20° or less (a same-radius joint, or a shallow kink the 5° split cut). A new station is inserted along the outward tangent by the sweep expand pad. A hard corner, about 90°, is not.

A concave open end is a third pad, separate from those two. Every open concave end grows by the sweep expand pad so the filler cap is not left coplanar with the face it stops on, and the finished solid is clipped to the pre-fillet bbox. The box grows by the fillet section on every side except one the open end leaves through, so the pad is still cut off and a round that fills an exterior corner is not. The inside corner of a rectangular cutout runs through the sheet thickness. On a bent part the flange makes that box taller than the base, and the base makes it wider than a wall, so the pad used to stay proud of the local skin — the white sliver at the cutout corner. Each concave end that leaves through an exterior face inside the part box is cut, on the filler alone, back to that face before the union, with the same 1e-3 skin margin as the bbox clip (a cap cut exactly on the face is the open-end fan again). An end that already lies on the part box stays with that bbox clip. The tool still overshoots both skins; the intersection throws the overshoot away, and the corner thickness stays the sheet thickness. An end that runs into material (a hollow cavity's inner ceiling) is not cut back, so that pad is still swallowed and the lip stays gone. Convex cutters are unchanged. `golden:sheet-cutout-fillet`.

A cutout corner that runs into a bend is one concave edge several millimetres long. Densified knots used to be matched to the nearest feature-edge midpoint, so a knot near the end of that edge bound a neighbouring seam instead. The path was then split into convex cutters and concave fillers: the subtract took metal (or left a sheared sliver at the flat/bend boundary) and the corner stayed sharp, with no error when some other knot still moved volume. Knots now match the edge segment they lie on, with the same direction penalty as the dihedral probe, so the whole corner stays one concave filler. `golden:sheet-bend-fillet-cut`.

The bend root is two feature edges on one line. One is concave: the base's end face against the first outer bend facet. The other is the convex bottom edge of the base. A path that keeps only the points is 0 mm from both, and the re-probe takes the convex twin, so the fillet cuts a groove in the bottom (and at r = 3.29 the scrap guard throws). `makeSweepPath` keeps the picked `n0`/`n1` and face ids. When two mesh edges lie on the knot's line, the probe keeps the one with those faces, or else those normals. A unique edge is left to the segment match. The concave round sits outside the part box, under the sheet. The section-widened clip keeps it. The expand strip past the end face would hang in that same void — below the sheet the "material" side is empty — so filler that left the box is cut back to the empty side of the two walls. The added volume stays near the section times the edge length. `golden:bend-root-fillet`.

An outer corner of a bent flange is one convex edge: the straight on the flange, then the outer bend arc. The flat face and the bend meet at one point and do not share a vertex index, so a sweep keyed on indices kept the larger piece and the cutter stopped on that tangent plane. The round covered the flat and missed the bend, including the thickness of the sheet along the arc. Selected edges that meet within 0.05 mm are one chain. On a sheet, an open fillet also continues past that seam by itself: the next feature edge has to stay tangent to the corner and share a wall, and the walk stops once the tangent has turned through the bend and the next edge is a panel run longer than the sheet thickness (the base the arc becomes tangent to). The reach is the same idea as the sheet subtract span, measured along the edge rather than as a prism past the sketch plane. The round covers the straight and the arc, through the thickness, and the removed volume stays near the section times that whole length. `golden:flange-outer-fillet`.

The bend arc is a chain of facets. A length cap of about one arc plus the thickness rejected the flange straight whenever the pick started on a facet, so the round stopped where the flange meets the bend. That cap applies only after the tangent has turned through the bend. A midpoint within 0.25 mm of the path also matched the next short facet and the walk died on the first one; an edge is skipped only when its midpoint is already on the path (0.05 mm, the endpoint weld). The arc's last vertex is the base corner. A cutter ring there lies in the panel, and the boolean left a skin, a gap, and the solid — layered faces the mid-arc cubes never touched. The path stops 0.15 mm short of that vertex. The base edge stays sharp. Needles the boolean leaves on the tangency, including ones shorter than a bend chord, are dropped from the drawn mesh when they already lie on a real face, and the result weld keeps a snap that moves less than 0.02 mm³. `golden:flange-bend-fillet-step`.

Artur's bracket does not pick that outer corner. c1 is a base through-cut and c2 is a notch on the flat flange (z from 12.96 to the tip; the bend tangent is at z = 6.985). The eight fillets are the thickness corners of those cuts: one plain 3.27 fillet and seven `variableProfile` fillets at 2.54. Seven are concave corners of the hole, so they add the section times the 3.175 mm thickness; the step corner of the notch is convex and removes that much. The path stays the thickness. The edges that meet its ends run across the face, not along it, so the span walk does not carry the fillet onto the bend. A ray through the bend stays one shell, and the outer crease stays the flange face. The duplicate faces those booleans leave are tangency needles about 0.03 mm long, already on the wall. The fin gate's 0.05 mm floor skipped them; a covered needle longer than 0.005 mm is dropped, and the fillet facet stays because it is taller than the height gate and it is the only cover of its surface. `golden:artur-bend-fillet`.

Variable-profile knots closer than 0.05 mm to the previous kept knot are dropped after densify (`_s23DropMicroKnots`). The 5° max-turn densify bisects both segments at a turn for up to 8 passes, and bisecting cannot reduce the turn at a true corner vertex, so each corner grew a cluster of 0.001–0.05 mm segments, each with its own probe, frame and ring. Path ends and any knot that turns more than 20° stay, so a corner is not chamfered.

Path thinning (the 1.2 mm floor) can drop the vertex where a circular run meets a long straight. That joint is put back when the thinned shortcut turns more than 5° and the span is a circle running into a long straight. The 18° gate that rebuilds a whole collapsed quarter stays.

## Keep-both cut and the shared edge

`cut` defaults to `keep: 'both'`. Each selected body is `splitByPlane`. Kept pieces are `Manifold.compose`d when more than one remains. `decompose()` splits them apart again. They do not share vertices, so each piece is its own body. A body that does not cross the plane is returned unchanged. `faceID` may still be reused across the cut; worker face merge will not join those faces (body id is part of the plane key).

The new faces on the cut are real 90° edges on each piece, but the two side faces have the same normal, so the material crease never changes and the cut disappears. `contactSeamSegments` lists only that pair: a feature edge (not a coplanar diagonal) that two different bodies occupy, side normals agreeing (dot ≥ 0.85) and cap normals opposing (dot ≤ −0.85). Which triangle was stored first does not matter. A drafted side is tilted off the cap and still draws this same line when the sides agree and the caps oppose. One body, or a cut that keeps one side, produces no segments.

`attachContactSeam` draws those segments as `gl.LINES` in black (`vec4(0, 0, 0, 1)`), on the edge itself. There is no side-face lift (`CONTACT_SEAM_LIFT` is gone). `mvPosition.z += 0.5` is a depth bias so the line is not lost against the face (far plane is 2000). It is not a second, offset edge.

## filletAlongPath on a multi-body solid

When the input `decompose()`s into two or more bodies, the helper fillets only the body that owns the path, then `Manifold.compose`s the untouched bodies back. Ownership is the smallest worst-point distance of up to 48 path samples to that body's triangles. A tie (the shared cut edge, both ~0) keeps the first decompose index. A bad path throws before the split. One body does not split.

The fillet piece is unioned into that owning body. The blend is one solid with the owner, not a leftover wedge beside it. Keep-both siblings are not part of that union (union would weld the cut). The boolean and the scrap check then see that one body. If decompose still sees separate scrap after the join, the gate below fails loud. Open-path thresholds are unchanged. A closed path drops shells with no volume and still fails when two components have volume. Create and edit both call this helper.

The fillet and the cap are already one body (one `decompose` component, one vertex component). The face graph is rebuilt when that mesh is shown (`warmFaceGraph` in `renderMeshData`). Coplanar triangles on one plane in that body become one face even when a fillet sits between them and the face ids still differ. Vertices within 0.02mm count as touching. The curved blend stays its own patch. A click on the cap includes both former bodies and does not include the fillet. `moveFace` on that cap offsets both copies. The drawn mesh drops the needle between them.

| Result of `decompose` | What it does |
| --- | --- |
| 1 component | Keep it. |
| Closed path, empty shells | Keep the largest. A closed sweep seam leaves shells with no volume (under 1e-8 mm³, measured ~1e-14 on a face loop through prior fillet arcs). Those are not a second body. |
| Closed path, 2+ with volume | Throw `decompose found N components on closed path`. No keep-largest. The message has no "scrap vol". |
| Open path, 2+ | Keep the largest, unless scrap volume `> 5%` of that largest **and** `> 0.01`. Then throw `decompose found N components with scrap vol …`. |
| Semi-arc batch (`plan.mode === 'runs'`, a wrap split at corners) | Same 5% / 0.01 test. The message is `semi-arc batch decompose found N components with scrap vol …`. |

Scrap volume is `(sum of component volumes) − largest`. That still means disconnected cutter scraps (thin sheets), not a second designed body. The other keep-both piece is composed back after the check, so it is not scored as scrap.

`golden:sheet-cutout-fillet` is a bent sheet with a rectangular cutout in the base and one in the flange: each inside corner's thickness equals the sheet thickness, and no vertex there lies outside the two skins. `golden:fillet-after-cut` is keep-both plus `filletAlongPath`. `golden:fillet-join-body` is an internal fillet whose wedge is in that one body, and a face pick that cannot select another body. `golden:fillet-move-seam` moves the face next to that fillet and checks the body-split line on a drafted face. `golden:fillet-face-pick` is one click on the coplanar cap: both former bodies, not the curved fillet. `golden:fillet-cap-move` offsets that whole cap, both sides of the duplicate-vertex seam. The highlight of that click does not draw the seam. `golden:fillet-wrap-draft` is a wrap that finishes onto a drafted face. Fillet after hollow is a different path: a concave segment forces the variable-profile builder. `golden:draft-fillet-tangency` covers draft hinge vs a fillet.

### Sweep frames on a chain that turns several times

A chain like Artur's three-corner wrap (up a vertical edge, round the top perimeter through prior R = 2 fillet arcs, down another vertical edge) turns 360° in total in 90° steps about three axes. Each straight leg then starts at a knot from the resampled corner arc before it, not on the mesh edge itself. Three rules keep the section right on such a chain:

| Where | Rule | What broke without it |
| --- | --- | --- |
| In-face rays (`_s23ProbeSegments`, `_s23ProbeFrame`, `_c6EdgeGeom`) | Read against the matched mesh edge (`_s23EdgeDirAlong`, only within 2° of the segment). When a triangle's third vertex is within sin 0.02 of the edge line, the ray is that triangle's normal × the edge (`_c6InFaceDirSafe`). Well-conditioned triangles give exactly the old ray. | A 0.015° tilt of the path segment against a sliver triangle (third vertex 0.004 mm off a 16 mm edge) swung the ray 45°. The chamfer section on the y = −10 top leg was rotated 45°: the front face was left uncut (lip), and the top was cut too deep (step). A solo pick of the same edge was fine. |
| Face-group normal (`c4MeshData`) | A group with ≥ 90% of its area within 2° of the area-weighted normal is planar. Its normal is the average of only those triangles (`_c4PlanarGroupNormal`). Curved groups and clean planes keep the plain sum. | `faceID` reuse across cutters put a 1.3 mm² facet of an earlier fillet into the +y wall's group. The normal was 4° off, and the variable-profile fillet cut a 94° section. |
| Arc split (`planFilletSweepPath`, `splitTighterArcs`) | On an all-convex fillet path, corner arcs tighter than the cutter (R < r) split into semi-arc runs, as same-R arcs (and every chamfer corner) already did. Concave or mixed paths keep one tube. | A r = 3.73 tube swept round an R = 2 arc rotates each ring about a center inside the section. Rings cross on the inside of the bend: fins and bow-tie notches on the top face (6.8 mm² of downward-facing facets at z = 10). |

`golden:fillet-chamfer-multi-rotation` runs both profiles on that chain. The chamfer is r = 2 (fixture `artur_playtest_chamfer_multi_rotation.txt`). The fillet is B's r = 3.73 variable-profile case (`artur_playtest_fillet_three_corner_wrap.txt`).

## Display unit

Scripts and the kernel stay millimetres. This setting is not written into a script and is not passed to the kernel.

`surfcad.displayUnit` (`src/utils/displayUnit.js`, hook `useDisplayUnit`) is the global mm|in choice. It persists in localStorage. It is a display conversion only. `lengthToDisplay`, `formatDisplayLength`, and `formatDisplayDelta` draw a stored length. `displayToMm` turns a typed length back into millimetres before a later field writes it. Do not parse a formatted caption back into a script. Length captions take the unit as a suffix (`lengthCaption`: `Distance mm`, `Radius in`). Angles stay degrees and do not take that suffix.

`formatDisplayNumber` is the one formatter for calculated numbers in inputs and readouts: fillet and chamfer size, dimensions, plane offset and angle, hole sizes, sheet lengths, measure, and any FEA field that already uses that formatter. At most four decimal places, trailing zeros removed (`0.1 mm` in inches is `0.0039`, not `0.003937007874015749`; `25.4 mm` in inches is `1`). The stored millimetres stay at full precision. Showing the field, or committing that same formatted string, is not an edit: `commitDisplayLength` and `commitDisplayNumber` return the stored value, and the script is not rewritten. A different typed number is what gets stored.

## Slider curve and snap

`shape` (`src/utils/sliderMap.js`) maps a thumb fraction to a value fraction. The first half of the travel covers the first third of the value, and the slope is continuous there. Past that the slope climbs to 2 at the end. `unshape` places the thumb from a typed value. The range input is a thumb index `0 … 1000`, not the millimetre ends. A signed length is `sign(u) · R · shape(|u|)`. A one-sided length is `min + (max − min) · shape(s)`.

`offscreenRange` sets R so that two-thirds of the thumb equals a measured off-screen distance: `R = dOff · 27/13`. With no camera that distance is `1.5 L`.

The thumb snap is `lengthSnap`: 0.1 mm, or 1/16 in when `surfcad.displayUnit` is inches. A span shorter than four snaps uses a tenth of that detent, once. The typed box does not snap. Angles, counts, and segments stay linear and do not use `shape`.

Fillet and chamfer size do not use `shape`. Their slider is a log map from 0.5 mm to 25 mm (`logLengthFromThumb` in `sliderMap.js`, range in `blendSize.js`), the same physical range in inches. Equal thumb travel is a constant ratio, so the low end has finer steps. The detent is 0.05 mm under 1 mm, 0.1 mm under 5 mm, 0.5 mm under 10 mm, and 1 mm after that; in inches it is 0.001, 0.005, 0.01, then 0.02. The ends stay exactly 0.5 mm and 25 mm. A typed size outside that range is kept, and the thumb sits on the nearer end.

## Joints

An assembly joint constrains two parts, or grounds one part (`fixed`). The word is joints. The joint lives on the assembly document. Part scripts and part origins are not modified.

`.surf.json` stays version 1. `joints` is omitted when empty. Each joint has its own surf id, a name, and a type: coincident, concentric, distance, angle, symmetric, or fixed. A relational joint stores two references, except symmetric, which stores two faces on each part (`a`, `a2`, `b`, `b2`). Each reference is a part surf id plus a face, edge, or axis fingerprint in that part's frame, or a plane. A plane key is a stable id, a point, and a unit normal: `origin:xy`, `origin:yz`, `origin:zx`, `workplane:<name>`, or `contour:<id>`. The workplane id is the binding name and the sketch id is the contour id. Neither is a character offset. `fixed` stores the part, plus the tapped face, edge, or axis (`kind`, `key`) when there was one so the chip reopens on it; a whole-part pick (Ground on the highlighted part, or `joint_pick` with `part_id` alone) stores the part alone. The solver and refresh read only the part: a fixed part is never a variable, and a stale remembered face does not break the joint. Distance is millimetres and angle is degrees; both store `value` and `sense` (`1` or `-1`). Coincident stores `opposed` (normals opposed). Symmetric stores no value: the center plane between one pair is coincident with the center plane between the other. Save always writes `opposed` for coincident. The solver (`src/joints/solveJoints.js`) settles the direction sign before it iterates: the parallel rows of coincident and of angle 0° / 180° are satisfied either way round, so when a free part starts the wrong way round for `opposed` or `sense`, its seed is turned half a turn about its own reference (`orientSeeds`) and the rows then hold the asked orientation; a joint already satisfied that way is a no-op. Angle 0° / 180° uses those linear rows instead of the dot product, which is flat there and accepted a "parallel" result 2° off. Status is not a file field.

`parts[].position` stays the translation. `parts[].placement` is `{ t, q }` with a unit quaternion `[x, y, z, w]`. It is written when the quaternion is not identity, or when a joint names that part. `t` equals `position` when both are present. A jointed part at the origin stores `placement` and omits `position`. A file with no joints and no rotation stays byte-identical: `placement` is omitted, and a row that already stored `position: [0, 0, 0]` still stores it.

Load and save drop a joint whose surf id is not a part in the file (`pruneDanglingSurfJoints`, `normalizeAssemblyJoints` inside `serializeAssembly`). IndexedDB keeps joints because `documentFromStored` runs that same serialize. Unknown keys are rejected. A duplicate joint id fails validation; save keeps the first. The surf-id migration rewrites a legacy `local-` prefix on a joint id and on the part ids it names, the same way it rewrites a color key.

Deleting a part drops every joint that named it. Copy to this assembly mints a new surf id and does not retarget joints onto that id. Field rules are `docs/vault-schema.md`. Locked behaviour (types, undo, page scroll lock, card flow) is spelled out in **Joints** below.

The rigid solver is `solveResiduals` (`src/solver/residual.js`): Powell dogleg on JᵀJ, with a dense Cholesky and a trust region that damps toward the current pose. The unknown is a plain number vector. The core does not import joints. The contour solver stays separate from this one. Joint equations (`src/joints/`) are the assembly adapter. Each free part has six unknowns, a left-multiplied rotation increment and a translation increment. Inside the solve a radian is weighted like 1000 mm, so a gap that translation can close is not spent on a tilt, even when the parts sit far apart in the plane. The residual the equations publish stays in raw rotation. `fixed` removes that part from the free set. Coincident, concentric, distance, angle, and symmetric add the rows in `src/joints/equations.js`. Symmetric's rows make the two center planes coincident. A broken joint is left out of the system. Success is a residual under 1e-3 mm and 1e-3 rad. Under-constrained and redundant-but-consistent results are success. A conflict names the newest joint whose removal makes the rest succeed (`Joint "<name>" conflicts`), or the newest joint with `conflicts with more than one joint` when no single removal works. Placements stay at the last success. The solver does not delete a joint and does not edit a script.

After a successful part run, each joint reference is matched again in the part frame, before the solve (`src/utils/jointResolve.js`). A face uses `matchFaceKeys`. An axis or an edge uses the same 8° / 1 mm / ±25% tolerances. The catalog is the same face graph as a pick: planar fins are dropped, and each triangle keeps the Manifold run it came from. Sheet metal is a union of flange boxes and bend zones, and face ids restart inside each of those solids. A bend and a flange that share an edge and a reused id stay separate faces, so the pick still matches. Without that run id they become one face. A drift inside that tolerance keeps the confirmed key. A miss, or two matches, marks the joint broken and leaves the stored placement. The sentence names the side: `Face not found on Shaft`, or `More than one face matches on Shaft`. Face and axis references use that graph for every joint type. A plane matches its id in that part's script. Origin planes are always there. A workplane or sketch plane that is gone is `Plane not found on Shaft`. The solve uses the plane's current frame and does not rewrite the stored key. `fixed` names the part only. A failed run marks every joint that names that part broken and does not match the leftover mesh. A hidden part still solves when its cached solid resolves. The solve runs on the main thread after the parts return and before `placeAssembly`, and it waits while `assemblyOpenLockRef` is set so it cannot write over an assembly that is opening.

`placeAssembly` writes the quaternion and the translation onto the pick mesh and every assembly-part mesh, sets scale to 1, and calls `updateMatrixWorld(true)`. The `assembly-parts` group stays at identity, so `matrixWorld` is the pose a bonded study reads through `feaPartFrame`. Joints do not write `contacts`. Auto-fit, overlay anchors, and `shiftLocalPoint` use that same rigid pose. A cross-part Boolean whose either pose is rotated writes no script; `externalBody` stays a translation. `commitJointEdit` is Add and Delete: it writes the assembly document only, and while an assembly is opening it writes nothing, does not clear the lock, and does not call `preemptInflight`.

With no part selected (`cadPartId` null), the desktop and mobile CAD strips show the assembly joints, or **No assembly joints**. The script-stage strip stays on the editor part's features. The last button in the Move section of the helper rail, on desktop and on mobile, is Joints (Lucide `Blocks`, `data-joints-button`). It opens the create card. Closing the card puts them back, unless the user toggled them during that time, the same rule the contour tools use. Origin planes, workplanes, and sketch planes can be picked like faces. The create card is `StickyPickApply` (`data-joint-card` and `data-sticky-pick-apply`, between the rails, `fullLeft` off). While it is open the camera slides and the orbit center moves the same way as every other feature card. Picks group by the part they belong to, in any tap order, up to two faces on each of two parts. ## UI confirm

Sticky pickers (Shell, Draft, Cut, Boolean, Move, Move Face, Delete Face) write **one** call and **replace** the previous marked block of that kind. A second confirm does not append. Grey X writes nothing. Chip behaviour is `docs/ui-style-guide.md`.

**Feature edit** reopens the dialog that created the block (`FEATURE_EDIT_DIALOGS` in `featureEdit.js`): the contour plane card for profile and workplane, the slot card for extrude, revolve, loft, and sweep, the fillet chip for fillet and chamfer, the helper sheet for blocks, holes, and transforms, and the same Shell / Draft / Cut / Boolean / Move / Move Face / Delete Face / sheet-metal chips. The strip and the feature list share `beginFeatureEdit`. A solid opens the slot card even when the old inline profile parser cannot read the block. Slot-card Confirm writes that solid by its block id. Profile and workplane Confirm calls `confirmFeatureEdit`, which rewrites that one block. A contour block comes back with its `solveContour` call, including dimension names, or with the points of an old point-list polygon. Cancel never writes, so the script stays byte-identical. An unchanged Confirm also skips `applyBuffer`, so it is not an undo step. A real change is one `applyBuffer` — one undo step on that part. Fillet and chamfer Confirm does not use that rewriter. It runs the same Accept composer as a new blend (`composeFilletCommit` / `composeChamferCommit` via `replaceEditedBlend`) on the script before that feature, then splices the new block over the old one. Disconnected corners stay separate `filletAlongPath` calls. The composer still cuts that prefix solid, but `const` names are reserved from the rest of the script. The prefix counter alone reissued `selEdges4` when a new corner needed the next name, and a later block already declared it, so the script failed to parse (`Cannot declare a const variable twice`). Names that live only in the block being replaced stay available, so the same edges emit the same consts. An unchanged script still skips `applyBuffer`. Sheet-metal Confirm rewrites the whole `sheetSpec` when it differs (a width-only field edit still rewrites just that number). Undo on the reopened sheet chip pops one bend or feature in the session and does not write; Cancel leaves the saved block byte-identical.

**Delete** sits on that same dialog, opposite Confirm (`data-feature-edit-delete`, the feature sheet's red danger button). Delete never refuses. The block that declares `part` asks first when later code still names `part` (`partDeclarationDeletePlan`): the same red dialog, titled Delete the base feature, from the edit dialog and from the feature sheet. Confirm drops only that block, and the later features go red on the rebuild. The rest of the script still has no `part`, so an empty part is not that case. The agent's `delete_feature` returns `confirm_required` for it until it is called with `confirm: true`; every agent delete then writes through the bridge `mutate` path, so `status` and `errors` are current when the command resolves, and a UI delete re-syncs the bridge after its run. `featureDependents` lists later features that reference this one: a fillet, chamfer, or sweep that calls `edgesBetween` / `edge` / `filletAlongPath` on a body this block writes; a cut, Move Face, Delete Face, shell, or draft that stores a face (`center:`) on that body; or a name this block declares (other than `part`) that later code uses. The mesh feature graph does not record which block created an edge, so the check is the script. Later feature blocks in that list open the same red confirm as a referenced contour (`data-feature-edit-delete-dialog`, `Delete along with N features`). Confirm calls `deleteFeatureEdit` with `withDependents` and drops this block plus those feature blocks. A name used only in later loose code is not one of the N, and a feature with no feature dependents deletes immediately. Either path shows a one-line `Deleted.` toast with Undo (`data-feature-edit-delete-toast`). The card is twice the previous one-line height. The words stay on that one line, and the gap between Undo and X is unchanged. Undo and dismiss stay 44px wide. `deleteFeatureEdit` finds the block with `liveSheetFeature` (the same span Confirm rewrites). A contour statement or a nested marker that sits inside that span goes with it. One `applyBuffer` rebuilds the part and is one undo step on that part. Toast Undo uses that step and restores the previous script and model. Deleting the feature that declared `part` drops a dangling `return part;` when the rest of the script is an empty part: blank, comment-only, or construction planes (`shouldClearViewportScript`). The viewport clears and the Deleted toast stays. A study comment after the return stays in the script. Later code that still names `part` is left in place. A failed rebuild shows the normal error popup with Undo and clears the delete toast. The edit dialog closes. `golden:delete-last-feature` deletes the only feature at 390px and 1280px, checks there is no error toast, and undoes it.

**Selection.** Fillet, chamfer, and any feature that stored an edge or a face resolve those refs with `openFeatureEdit` / `resolveStoredEdges` against the graphs rebuilt on the prefix mesh (`editPreviewScript` drops this feature and everything after it, then `executeScript({ editPreview })` runs `syncFeatureEdges` / the face graph). Graphs rebuild on that successful preview run, not between dialog keystrokes. The resolved edges use the normal edge highlight; the user can add or remove them before Confirm.

**Missing refs.** A stored edge or face the prefix graph cannot resolve stays in the dialog (`2 edges not found`) until the user clears it. Confirm without that clear keeps the original line. It is never dropped on open.

**Assembly open.** While `assemblyOpenLockRef` is set, a prefix preview does not post, and Confirm and Delete do not call `applyBuffer` or refresh. Joint Confirm and Delete also refuse: they leave the card up, do not clear the lock, and do not call `preemptInflight`. Cancel and an unchanged Confirm also skip the restore run. Feature edit never sets or clears that lock, and it does not call `preemptInflight`. The dialog stays up until the open finishes.

Single-body ops (Draft, Shell, Cut, Move, Move Face, Delete Face) write only the touched part. Fillet and Chamfer write every part that has picks, each into its own script (below). Subtract-mode Block / Shape and Boolean can write more than the part in the editor, by the cross-part rules below.

**Write target.** A face or edge pick moves the CAD part (`cadPartId`, the title, the strip and every preview anchor) but leaves the editor on `activeId`, and every writer writes the editor buffer. So before anything that writes, opens a feature sheet, or undoes, App runs `focusWritePart`. That covers:
- palette Block / Shape / helper Confirm (`handleInsertHelper`)
- every `handleCommit*` (Contour / Extrude / Revolve / Loft / Sweep / Workplane, Fillet / Chamfer, Shell, Draft, Cut, Move, Move Face, Delete Face)
- feature sheet open, Accept and Delete, and strip jumps
- Undo and Redo
- a palette tap (`onOpen`) and the start of a feature session, so the buffer snapshot, commit mode and Undo stack match the picked part from the start

`featureWriteTarget(doc, { pickedId, payloadPartId })` picks the part (`golden:multi-part-block-drop`):
- the viewport's own part for that commit (`partId: activePartIdRef.current` on every commit payload), when it is a row
- else the picked part
- else the editor's part

When that is not the editor's part, it is loaded with `handleSelectPart(id, { keepPicks: true })`. That stashes the editor's script on its own stack, loads the target's script, and focuses the target's own Undo stack. Then the write happens.

Boolean keeps its own rule (the first pick's part, loaded the same way). Multi-part Fillet / Chamfer still write the other parts' blocks into their own scripts. Sheet Accept / Delete find the block in the loaded buffer (`liveSheetFeature`: same id and kind, else same kind and index) and refuse when it is not there. They never fall back to the chip's own offsets, which came from another part's script and gave "invalid range" or cut the wrong text.

Block solids (cube, rounded box, cylinder, sphere, tube, hex prism) and Shape solids (Extrude, Revolve, Sweep, Loft) share one Mode: Add or Subtract. It is the same feature, not a second tool. Profile and Workplane do not create a solid, so they have no mode. Polish (fillet, chamfer, move face, delete face) mutates. Default Mode is Add, so an existing script that does not set it still unions. Subtract cuts the new solid out of `part` only when `part` already exists. The first solid is always `let part = …`. Sweep's one-shot fallback stays a replace when Mode is Add; contour Confirm for Sweep adds or subtracts.

Opening a Block pop shows that solid in the viewport before Confirm: the Manifold mesh, painted like Loft's preview: unlit translucent cyan skin (`PREVIEW_COLORS.skin`, opacity 0.38, both sides, no depth write) plus a brighter cyan outline on its 20° creases, so it never reads as committed CAD. Position and rotation on the sheet move it live (rotate about the origin, then translate, degrees). On a cube, editing Pos or Rot clears **Centered** so it does not fight that pose (the built-in **Center** transform is separate). Confirm writes the size, that pose, and Add or Subtract. Feature edit rewrites the primitive line for pose and Centered too. An identity pose is left off the line. Cancel drops the preview and writes nothing. Subtract looks the same, with the depth test off on the skin, so a cutter inside the host stays visible.

Fillet's marker comment still says the second Accept replaces. The call site passes `commitMode: 'append'` when `hasFilletModeBlock` (Chamfer the same). `composeFilletCommit` keeps the old block only in that append case.

Multi-part Fillet / Chamfer Accept: picks are grouped by part and every group is validated first (`planMultiPartEdgeAccept`); one bad chain fails the Accept and names that part. Then every part is composed before anything is written (`composeMultiPartEdgeCommit`): the editor part on the live buffer, each other part on its saved script, append when that part already has the block. A part with no script, or whose last run failed, refuses the whole Accept. The editor part is written through the editor; the others go through `writeOtherPartScripts`, one feature step on each part's own stack, then every visible part runs once. Picks only on another part leave the editor alone. These are that part's own blocks with its own edge ids, not external copies: no `externalBody`, no yellow chip. Undo is per part, as for any cross-part write.

Several disjoint corners are separate `filletAlongPath` calls in that one block. Accept writes every `edgesBetween` / `edge` first, then the blends. The first blend can drop the face ids of the corner it cut: on a plain box, faces 2 and 5 meet at a vertical corner, and that pair is gone after the corner that used face 2. The next corner is not looked up on that mesh. Graphs are not rebuilt between those corners. They rebuild once, on the success path after Auto-Run, the same as a single fillet. Editing the fillet or chamfer (tap its chip, change the radius, or add a corner) uses that same composer. The old edit rewriter collapsed every corner into one `makeSweepPath`, which throws when the corners do not connect. A new corner's `selEdges` / `path` binding is the next name free in the whole script, not only in the prefix, so it does not redeclare a const that belongs to a later fillet or chamfer. A closed face loop, including one whose cutter crosses itself at the seam, is that same `filletAlongPath`. When a fillet or chamfer block still throws, the run skips that block and paints its chip red. The solid is whatever the other blocks produced, and the part outline stays off. One edit writes one buffer.

**Failed feature chip.** A feature whose run failed gets a red border on its strip chip and on its feature sheet: `border-2 border-red-400` (the error popup's red), plus the plain-CSS twin `feature-failed-ring` in `src/index.css` (2px solid `#f87171`, `!important`, outside any layer), so WebKit keeps the red over `border` utilities and native button styling. Red wins over the external yellow. Successful chips are unchanged.

The failing block is found two ways. The tracked block comes first:

1. **Tracked block (every engine).** Before the worker compiles the script, `instrumentFeatureBlocks` adds `;__featureEnter(i);` in front of each begin marker and `;__featureLeave(i);` in front of its end marker, on the marker lines themselves. No line moves.
   - A tracker (`createFeatureTracker`) keeps the stack of open blocks.
   - A throw while a block is open adds that block's `featureId` and `featureBlock` (its text) to the error.
   - A marker that is not at the start of its line is not tracked. If the instrumented body does not compile (a marker inside an expression), the original script runs untracked.
2. **Stack line (V8 / Firefox fallback).** A throw from a helper still leaves one frame in the `new Function` body. The worker calibrates the engine's header lines once (`calibrateScriptLineOffset`) and maps a V8 `<anonymous>:L:C` or Firefox `> Function:L:C` frame to a 1-based `scriptLine`.
   - **Safari:** WebKit frames for that body match neither pattern, so `scriptLine` is null there. That is why iPhone Safari showed the part's red glow but no red chip until the tracked block was added.

`ManifoldWorker` keeps `featureId`, `featureBlock` and `scriptLine` on the rejected error. The viewport reports every run it makes (`onRunOutcome`: success, cleared, failure). App maps the failure with `failedFeatureFromOutcome`:
- The tracked id comes first (`failedFeatureForId`). It must still hold the same block text; if the id moved, an identical unique block is used.
- Otherwise the line is used (`failedFeatureFor`).

The strip (both layouts) marks that chip with `data-feature-failed`, `aria-invalid` and the title "failed on the last run", for as long as the block's text is unchanged in the script it shows (`failedFeatureIds`). The feature sheet reads `failedFeatureIds` on the editor's script and marks:
- the identity badge: `data-feature-sheet-failed`, red, with the subtitle "Failed on the last run"
- the picker row: `data-feature-sheet-failed`, red

Editing that block, or the next good run, clears it. Only a throw inside an open block marks anything. A syntax error (no block ran), a non-Manifold return after every block has closed, or a throw outside every block marks nothing. Only the run shown in the viewport, which is the part the strip shows, is tracked. Background parts' failures stay on the Parts feed.

**Feature skip.** `src/utils/featureSkip.js` builds a throwaway evaluation copy. The buffer, undo commits, and the saved script stay as written. The copy leaves `scriptWithFeatureCount` alone (that helper deletes later blocks for the undo seed). The worker `execute` message and `runPreparedScript` run the copy through `executeSkippingFailedFeatures`. The first attempt is the script as written. When a marked feature throws, the next attempt blanks that feature and its hard dependents. Another throw repeats, and the loop stops at the feature count. A recovered run posts `type: result` with the surviving mesh and `featureSkip`: the original error's id, block, line, and message, plus each later skipped block (`threw` when that block also threw, `dependsOn` when it was omitted because it names a variable or a refKey from a thrown block). The viewport shows that mesh and the error popup, and it reports the run as failed so the strip and the sheet turn those blocks red. The new mesh is the recovered solid, so the failed-part outline stays off it. A run that still returns no solid throws the original error with the same `featureSkip` attached. The viewport then restores the last mesh and draws the red outline. Boolean and cutter probes call `executeScript` directly. An edit preview leaves the popup and the chips as they were. A new FEA Run meshes the solid this path returned. `src/fea` stays unchanged, so a stored full-solid result stays fresh until that Run. Study comments stay in the buffer.

The block that threw keeps the title "failed on the last run". A dependent carries `data-feature-depends` and the chip title "<label> — skipped, depends on <feature>". The sheet subtitle is "Skipped — depends on <feature>".

`hardSkipIds(script, featureId)` is the failed feature plus its transitive hard dependents, in script order. A hard dependent is a later block `featureDependents` marks with reason `variable` (a `const`, `let`, or `var` other than `part`, including a contour name), or a later block whose `refKey:` value is quoted in a skipped block and in no earlier block that is still outside the skip set. A sheet edge such as `wall:base:v-:w0` quoted in the sheet block, then named as `refKey:` on a later contour, skips that contour and the extrude, revolve, loft, or sweep that names the contour. `part` is not a hard edge. A later fillet, chamfer, or shell that only reads and writes `part` stays out of the set, even when `featureDependents` would call it an edge or face dependent. Those blocks stay in the copy and run until a throw inside them.

`resolveRollback(script, anchor)` is the only reading of the bar. The strip paints that anchor, and `executeSkippingFailedFeatures` passes the same anchor into `evaluationScript` and reports the same `skipIds` as `rolledBack`. `hardSkipIds` stays the failed feature and its hard dependents; rolled-back features are not added to it. `null` is the start and skips every feature. A known id skips the tail after that feature. A missing id, or no anchor, is the end and skips nothing. It is not the start. Index 0 is the start only when the anchor is `null`: an empty chip list's only gap index is 0, and turning that index back into an id would paint the start while evaluation of the missing id blanks nothing. Contour chips sit in the strip beside features. A contour chip id (`contour:<id>`) is an anchor: the contour statement still runs, and every feature that starts after that statement is rolled back. A missing contour id is the end, the same as any other missing id. The bar gap is that chip, not a second index into the mixed list. `evaluationScript(script, { skipIds, anchorId })` blanks the interior of each id in `skipIds`. `anchorId` is the feature or contour the rollback bar sits after: a feature id blanks every statement after that feature, a contour id blanks every statement after that contour statement, `null` blanks from the start of the script, and an unknown id blanks no tail. Omit `anchorId` when the bar is at the end. Marker comments stay, and so do other `//` lines, so the ids and the line numbers do not move. The trailing `return part;` stays. Blanking a line removes its code and keeps the newline. The worker still returns the prefix solid as a successful run, and it names the blanked features in `rolledBack`. The viewport logs that list and `onRunOutcome` carries it. Those features are not reported as a silent success, and they are not marked failed: the chips stay grey.

The feature strip draws that bar (`data-rollback-bar`) in both layouts. On the horizontal bar the stroke runs the full strip height, centred in the gap between chips. The count badge on each chip hangs past the icon, so the gap is measured from that badge (and from a separate-body or unused mark), not from the chip border alone. The gap after the last chip sits 4px past that badge, the same clearance a centred gap keeps. The upside-down triangle sits just above the strip with its tip on the top edge. The vertical rail turns that same control so the triangle sits outside the side edge. The drawn triangle stays small. An invisible 44×44 box on it (`data-rollback-hit`) is the drag target. When the bar is before the first feature, a lead spacer keeps that box off the first chip. Sketch chips and joint chips hide it. The default gap is after the last feature. A drag snaps between features and does not push undo. Release stores the id of the feature before the gap, one anchor per part, in memory beside part history, and runs again with `rollbackAnchor`. That release keeps the CAD part selected. The triangle sits over the canvas, and a mouseup there is not an empty-space tap: only a press that starts and ends on empty canvas, away from the bar, clears the part and switches the strip to assembly joints. Chips after the bar are grey on the strip and on the rail (`data-feature-rolled-back`, `opacity-40`, `grayscale`) and their title, label, and description say rolled back. Dragging back to the end clears the anchor and runs the full script. The Extrude card labels Out / In / Both as Direction.

Every feature Accept writes through the same caret a palette insert uses. `commitScriptAtRollback` cuts a new block that landed past the bar and splices it with `insertBlockAtCaret` (the splice half of `composeHelperInsert`), then the bar moves onto the new feature so that card stays live and the tail stays grey. A centres contour added in that same Accept (`role=centers`) is cut out with the hole block that first names it and spliced in front of that block, so the statement is not left behind the bar. An existing centres contour stays where it is. A new hole that names it lands at the caret, or just after that statement when the caret is earlier, so the binding is in scope and the bar sits on the new hole. Fillet, chamfer, shell, draft, cut, boolean, move, move face, delete face, contour, and sheet Accept all go through `commitFeatureBuffer`. An edit of a block that is already in the script does not move, and the bar stays. A marker with no explicit id is named from its place in the strip (`fillet-2` before a move can be `fillet-1` after, or the id of whichever block slid into that slot). The anchor is read after the move, and the block the bar lands on is stamped with a stable `id=` so a later insert does not slide it. A missing anchor is the end: new blocks stay where they were and are not pulled to the start. If the positional id moved onto a different block, the bar follows the original block's text. Palette insert still calls `rollbackInsertCaret` and `rollbackAnchorAfterInsert` on that same caret. The caret stays after `let part` so the insert is not in the temporal dead zone, and it is not pushed to the last `part =` assignment. Undo, redo, and delete keep the stored id, including when that feature is gone. A missing id draws and evaluates as the end, and the bar returns when the feature comes back. Opening a file or reloading drops the in-memory bar and runs the full script. `.surf.json` does not store the bar. The saved script is the full text.

Rolling the bar to the start blanks every statement, including `let part`. The trailing `return part;` used to stay in that copy. The worker then evaluated the return, `part` had never been declared, and the run threw "Can't find variable: part" (V8: "part is not defined"), the same failure an empty script had before a dangling return was dropped. `shouldClearViewportScript` never saw the copy: it looks at the original script, which still holds the features. The evaluation copy now blanks that return when the copy no longer declares `part`, and the line count stays. The viewport takes the empty-script clear path, so the solid is gone and there is no error popup. A background assembly run of that part is an empty part, not "Script must return a Manifold object". A bar that still has a live `let part` keeps the return and runs the prefix.

A part script has one top-level `return part;`. `composeFeaStudies` (`src/fea/studyScript.js`) appends a new study as comments after that return, which does not change the solid. The next feature insert used to see a return that was no longer the last line, so `stripTrailingReturnPart` left it in place and the feature was appended after the study, followed by a second `return part;`. The strip still showed the chip. The worker stopped at the first return, so the fillet never ran. `insertBlockAtCaret`, sheet append, and the boolean, move, rotate, move face, cut, draft, delete face, and external-copy writers now insert before that return and leave the study after it. Contour and extrude already did. Paint writes assembly colors, and joints write the assembly document, so neither emits a feature block. `featureBlocksAfterReturn` flags blocks that still sit after the return. Opening a part runs `repairScriptReturns`, which moves those blocks to just before the return and drops the extra `return part;`, then saves the healed script. The next Accept repairs the buffer the same way before it places the new block. The study comment stays after the one return.

## Cross-part copies

Accept writes each affected part's script. A part that is not in the editor is written in the background: its script is replaced, saved, and pushed as one feature step on that part's own undo stack, then every visible part runs again. The active part's graphs rebuild on that success path. Another part's graphs rebuild when a pick retargets onto it, as before.

- **Boolean.** Picks are stored per part (hiding a part still leaves its slot alone) and each carries a tap counter, so the first tap across every part is the target. Its part is written. If that is not the part in the editor, it is loaded first (`handleSelectPart(target, { keepPicks: true })`), so the Boolean is one feature step on the target's stack. Tools on the target's own part are named by centroid as before. A tool on another part is frozen into the target: that part's whole script as it is at Confirm (the live buffer if it is the editor part) goes inside `externalBody(function () { … }, { bodies: [{ at }], offset })`. `at` is the centroid in the source frame. `offset` is source position − target position (placement is a translation). A hidden tool part keeps its pick and is still copied. A tool part whose last run failed is refused (`… failed its last run`). Picks on a part that is not the pick mesh are drawn from triangles stored with the pick, at that part's position.
- **Subtract Block / Shape.** The editor part gets its block as before. Then the cutter is frozen: the block's own lines, with `part = part.subtract(EXPR);` turned into `return EXPR;`. When those lines read `part` or a name declared earlier in the source script, that earlier script is copied in front of them. The worker probe (`probeOverlap`) intersects the cutter, posed into each other part's frame, with that part's last mesh. Every visible, non-failed part with overlap volume above 1e-6 gets a block of the same kind (`Cube`, `Extrude`, …) holding `part = part.subtract(externalBody(function () { … }, { offset }));`. Hidden and failed parts are not cut. A part the cutter does not touch is not written.
- **Tag.** The first line inside the block is `// external copy from "Name" · src <id> · ref <hash> · frozen at Accept, not linked`. `ref` is a hash of the source block text. Re-confirming that source feature (same kind, replaced in place) finds the copy whose `ref` matches the block it replaced and replaces it, so a part is not cut twice. If the moved cutter no longer overlaps that part, its copy is removed (one step there too).
- **Copied text.** Marker comments inside the copy become `// (copy) --- … ---`, so the copy adds no chips and marker scans (`stripBooleanBlock`, `scriptWithFeatureCount`, fillet append) only see the target's own blocks. `parseFeatureMarkers` flags a block that calls `externalBody(` as `external`. The strip chip gets a yellow border and the feature sheet says External copy. `golden:cross-part-clone`.
- **Not associative.** Nothing links the copy to the source part. Editing, moving, or deleting the source later does not change the target. Deleting the feature, or undoing that step, deletes the copy with it.
- **Undo.** Each Confirm is one step on each written part, and only on those parts. There is no linked multi-part undo: Undo on the target removes its Boolean or its copy; the source part's stack is untouched.

The viewport can show more than the script in Monaco. An assembly is a list of parts. The editor still holds one part at a time.

Parts and Script stages omit the brand. Favicon and PWA icons are the paper tile. The loading gate is wall-clock light/dark and has no Privacy choices link. `golden:brand-identity` checks the header at 390 and 1280.
- **Thumbnails.** Each row shows a mini snapshot of that part's solid (`data-part-preview="manifold"`, `data-part-thumbnail`). It uses the viewer material (flat normal shading), the camera point light, and the `#1e1e1e` background. A bitmap for the mesh in memory is cached by that mesh and redrawn only when that solid changes. An idle row is not drawn again. The same bitmap is stored in IndexedDB `surfcad-part-thumbs`, keyed by the part id plus `scriptHash` of that part's script (`partThumbnailKey`). A reload paints the stored bitmap immediately (`data-part-thumb-source="cache"`), including a hidden part that has never been placed in the CAD view. `ensurePartThumbnails` rebuilds a thumbnail only when that key is missing. A visible part with a current mesh is snapshotted on the offscreen preview renderer (`takePartPreview`), not by the CAD camera. A hidden part with no stored bitmap is run on a separate `ManifoldWorker`, not the viewport and not the worker that holds the CAD solid, and that mesh is snapshotted the same way. Hiding the part does not clear this snapshot. The eye removes the part from the viewport only. `refreshAssembly` runs the visible parts and replaces the run map; `preserveHiddenPartRuns` copies the last successful mesh back onto each hidden row, so a part that was shown and then hidden still has a snapshot before the stored bitmap is read. A script that returns no solid stays an empty tile (`data-part-preview="empty"`). Deleting a part removes every stored bitmap for that id (`forgetPartThumbnails`, called from `deletePartScript`). Clear local cache wipes `surfcad-part-thumbs`. `golden:part-hide-thumbnail` hides another part and the active part at 390px and 1280px. `golden:part-thumb-cache` loads hidden parts that have never been displayed, at the same two widths, and a reload shows those thumbnails from the cache without running the scripts again.
- **Mobile.** The home-indicator pill uses Lucide icons. The order is CAD (box), then Parts (layout-list), then Script (square-text). The Parts stage is the same feed. Its top bar uses the script editor ribbon. The assembly name stays in the middle. Local or Git is right-justified. Load lives in the feed pane.
- **Chrome.** The CAD title is the part name, then the word in, then the assembly name (part1 in Assembly, or Bracket in Gearbox). When no part is selected the title is the assembly name only, with no part and no "in". The part-name pill is omitted in that case, on desktop and on a phone; it is drawn only when the title has a part name (`golden:empty-part-pill`). A single tap on the part chip selects all bodies in the part the title shows (`renameTargetId(doc, cadPartId)`, `showCadBodyHighlight`, `golden:part-rename-target` for rename targeting). A double-click on that chip renames that part. A single tap on the assembly chip enters assembly mode (`cadPartId` null, joints strip) and keeps the last selected part's mesh and body highlight so joint picks still have context; it does not rename. Assembly rename lives on the Parts ribbon center title (`RibbonAssemblyName`, same commit rules as before). Title chips use `gap-3` on the shared header row beside the inline wordmark (`golden:viewer-title-actions` at 390 and 1280). A face, edge or body pick on another part moves the title there while the editor's `activeId` stays put, so rename follows the pick, not `activeId`. Clicking the active row brings the title back to that part. A new assembly is named Assembly, then Assembly (1), Assembly (2), when that folder is already in the repo or among local names (`nextAssemblyName`). Its one part starts empty (`blankPartStarter`: no demo script, no seed cube; a git part is only its `// @surf-id` header), so the first Block or Shape creates the body and `isDefaultBlankAssembly` still skips the Save | Discard guard. A copy, import, or rename that collides uses the same parenthesis rule as parts (`Name` when free, otherwise `Name (2)`, `Name (3)`, …) and blocks when the folder is still taken. The repo folder is that name (`assemblies/Assembly (1)/`). A blank or whitespace name is saved as Assembly, including when an older document is loaded. A custom name already saved is left as written. A loaded file name is used only when the document has none. Game mode keeps its puzzle chip. The parts ribbon (desktop feed and mobile Parts stage) gives the assembly name a real flex middle (`flex-1 min-w-0`, `max-w-full` truncate) between left actions and right chrome; click that name to rename the assembly. The **+** control is a slim **Part** / **Assembly** create menu (no open/Existing). The **folder** control opens the same **Part** / **Assembly** choices for existing items: **Part** adds a vault script (git only); **Assembly** opens/loads. Creating or opening an **assembly** asks **Save** or **Discard** (Discard danger/red) when the working copy is not blank/default/known-saved; Save flushes IndexedDB locally or opens Commit in Git mode, then continues.
- **Document.** The saved assembly is the vault document in `docs/vault-schema.md` (git) or the same part list in IndexedDB (local). The document `name` is the assembly name. A blank name is stored as Assembly. An optional `position` `[x, y, z]` is the translation. An optional `placement` `{ t, q }` is that translation plus a unit quaternion, written when the part is rotated or named by a joint. Joints live on the assembly document. The script source is not in the JSON.
- **Part groups.** A group is a Parts-list folder for parts inserted from another assembly. It is not a multi-body solid and not a joint. Multi-body means several bodies inside one part (`merge: false` on that part's script). A group is several parts: each keeps its own script, undo stack, selection, and viewport solid. Fillet, pick, and cross-part rules stay per part. The feed draws a block where the group's first member sits (`layoutPartFeed`); collapse is local UI state and is not saved. Field rules, insert, copy, and delete are `docs/vault-schema.md`.
- **Row id.** An id never carries a sync prefix. Sync is only `isSynced` on the local part record, and that flag is not written to `.surf.json`. The stable identity is `surfId`, minted once and never rewritten on push. In git mode a part that is already in the repo uses its repo path as the row id. A part that is not in the repo yet keeps a bare IndexedDB id. The Parts list subtitle (`data-part-subtitle`) is that repo path, or the path Add to Repo would write (`parts/<Name>.js`, same `sharedPathForMove` rule), or nothing when no path can be derived. It is never `local:`. Add to Repo shows when `isSynced` is false, and when the flag is unset and the row id is not a repo path. A load-time migration strips a legacy `local:` prefix from row ids and rewrites assembly part refs, `.surf.json` color keys and part paths, undo/history keys, and selection. A repo path and a surf id are left alone. A second pass is a no-op. A missing local key offers Upload. See `docs/vault-schema.md`.
- **Failed parts in the viewer.** A visible part whose latest run failed gets a red outline and glow on the solid the viewport still shows for it, which is its leftover (the last successful mesh). Outside an assembly it is the restored last good mesh. This uses the same red as the strip's failed chip and the error popup (Tailwind red-400, `0xf87171`). The rule for which parts are failed is the same as the Parts feed's red row, `failedPartIdsFor`: not blank, missing, skipped or hidden. App passes those ids on every `placeAssembly`, falling back to the leftover ids. The viewport syncs the overlay on every assembly extra and on the pick mesh: after each placement, each new solid geometry (`renderMeshData`) and each part switch. `setFailedPartOutline` adds one child group to the part mesh, made of crease edges (`EdgesGeometry`, 20°), a translucent tint, and a back-face glow rim scaled about 0.6 mm (1–6 %) around the solid's center. None of them raycast, so picks still hit the solid. The overlay is rebuilt when the geometry changes and disposed when it turns off, and the solid's own geometry is never disposed. Successful parts carry no overlay. A part that failed without ever succeeding has no solid to mark; the Parts feed row is its only signal.
- **Visibility and failure.** The viewport draws every visible part whose latest run returned a solid. A hidden row is left out and is not pickable until it is shown again. Its parts-list thumbnail keeps the last successful solid, and a hidden part that has never been shown still shows the bitmap stored for its script. A failed script highlights that row and contributes no solid to the composed viewport. There is no shadow solid on the pick mesh. Leftover triangles from the last success stay in the viewport and can be picked. Hiding a part mid-feature does not clear that part's picks. Boolean picks are stored per part id. Hiding a row calls `noteBooleanPartHidden` and does not add, remove, or rewrite that part's bodies or drop list. A part that was never picked stays unpicked. Switching to the part manager does not exit Boolean mode: the CAD pane stays mounted. Confirm writes the part of the first pick; picks on other parts are copied into it (see Cross-part copies).
- **Delete.** The trash control opens a choice window first (`data-part-delete-dialog`). Cancel leaves the part. **Delete from assembly** drops the row, its script cache, its thumbnail cache, and its solid; other parts stay; the active id stays on a remaining part (or empty). That button does not ask again: the Undo toast covers an assembly-only delete. The repo button, when shown, is stacked 14px below it. In git mode a vault path offers **Delete from assembly & repo**. That choice opens a second confirm, `Delete <file> from the repo? This can't be undone from SurfCAD.` (`partRepoDeleteConfirmCopy`; `<file>` is the path basename, such as `FilletKilla.js`), with Cancel and Delete. Cancel leaves the part. Delete does the same local drop and commits a file delete plus the updated assembly `.surf.json`. This second confirm is the exception to the no-confirm rule, because the Undo toast does not cover a file removed from the repo. A row whose id is not a repo path only shows assembly delete (wipes IndexedDB for that id, including `surfcad-part-thumbs`). `golden:part-delete-dialog` covers both steps at 390 and 1280.
- **Undo.** Each part keeps its own undo stack. Switching parts swaps stacks. Undo and Redo are feature-wise on that part only: each Confirm is one feature step, and there is no linked multi-part undo. Fresh load seeds the stack from that part's feature markers so strip Undo can walk those steps; Redo is session-only and drops across reloads. Undo restores the previous script of the part that was edited, and runs that part. It does not write another part's script into the editor. A cross-part Accept pushes one step onto each part it writes, and onto no other. Assembly joint history is separate and is active only while no part is selected. It stores joints and placements, not script text, and it is not written to IndexedDB. Reload seeds one commit so joint Undo starts empty.
- **Graphs.** Face, edge, and body-contour graphs follow the CAD part, which a pick retarget can change without opening the script pane. They rebuild when that part's script succeeds, on the same path as a single script (edge graph and contours at the end of the run; face graph when the new mesh is shown). Selecting another row, or picking that part, rebinds all three to that solid before the next pick, and rebinds the highlight and preview anchors with them. Edge highlights, fillet id labels, the sweep-blend preview, and contour previews are drawn in that part's local frame and then translated with the part. A selection or graph still tagged with another part is not painted, so it cannot sit on the part that occupies the origin. A shared vertex-index key does not copy boundary ids onto a segment that is not the same edge. A failed or hidden active part clears its pick mesh and does not rebuild those graphs from a previous solid. The other visible parts are drawn beside it and do not rebuild graphs until a pick retargets onto one of them. An empty CAD click clears the geometric selection and `cadPartId`. It does not change `activeId`. Entering a feature hides the feature strip. Picks during that feature still retarget. Single-body ops write only the touched part; Fillet and Chamfer write each part that has picks (below); Boolean and Subtract can write more (Cross-part copies).
- **Part switch cache.** Built solids are cached by mesh data (`partSolidCache.js`). The pick mesh and the other parts use the same build (`buildSolidGeometry`: needle dropped, faceID kept), so a switch hands the geometry over: the part being left goes to the assembly layer, the part being touched comes off it, nothing is rebuilt. The face graph (WeakMap on the geometry), the edge graph and body contours (`featureGraphFor`, by geometry + faceIDs), and the contact seam (by mesh data) are hits on a solid already built. After each placement the other visible parts are pre-built in idle time, one graph per slice, not while dragging (skipped above 40k triangles, cancelled by the next placement), so the first switch onto a part is a hit too. A new run is new mesh data and always misses. Entries nothing shows (not the pick mesh, not another part) are pruned and disposed.
- **A part switch keeps every part on screen.** Picking another part, from the Parts row, `set_active_part`, `select_parts` or a click on its solid, goes through `swapPickPart`: the part being left is parked as an assembly mesh with its pose right away and the picked part's assembly copy is removed before its solid becomes the pick mesh. The assembly rebuild that follows a switch (`refreshAssembly`, every visible part on the pool) then only reconciles. Before this the Parts-row and `set_active_part` path adopted the new solid alone, so the previous part was missing from the scene until that rebuild placed it again: a blink on small parts, seconds on a heavy assembly (the bike's Fork vanished while the wheel was selected). `golden:adjacent-part-visible` samples the scene through the dev-only `__VIEWPORT__.partMeshStates` hook across each switch and fails if the part being left is off screen for more than 300 ms.
- **Contours and work planes stick to their part.** Saved sketch contours (`makeCrossSection`) and construction / work planes are listed per part from that part's own script: the editor part from the live buffer, every other visible part from its saved script (`partOverlaySources`). Each part paints under its own group, in its local frame, at that part's live translation (`partOverlayAnchor`). For the pick mesh that is the active part; for any other part it is its assembly mesh, falling back to the row position. `syncAnchoredOverlays` and every assembly placement move them, so a part switch leaves them alone and a moved part carries them. A hidden part's overlays are not drawn. A host-face contour (no literal plane) uses that part's own top face. Only the editor part's overlays take picks: a plane hit is filtered by its group's part, and the contour pick ray is moved into the editor part's frame (`toPartLocal`). Before this, both overlays were listed from the editor script alone and anchored to the active pick part. A pick on B with the script still pinned on A drew A's planes and contours on B, and B's own planes were not shown.
- **Tool previews stick to the active part.** Every overlay built from the active part's local vertices (the Move and Rotate ghosts, the Move Face preview, Cut and Boolean piece previews, block previews, sketch strokes, edge and face highlights) is posed with `anchorToActivePart` (`applyActivePartAnchor`, translation and rotation) before it joins the scene, and its root is listed in `syncAnchoredOverlays`, so a placement change re-poses it. A Boolean pick on another part carries that part's own pose (`overlayPartId`). Nothing built in a part frame is added to the scene root unposed: on a part placed 340 mm away or turned 30° it would draw on whichever part sits at the origin, which is what the Move and Move Face ghosts, the Cut pieces and the Boolean pieces did until this rule. FEA probe markers are world points and stay at the root. `golden:placed-part-previews`.
- **Plane and sketch overlays default off.** The right-rail toggles start off each new session. They are not written to localStorage, the editor draft, or `editorStorage`, so there is no stored preference to migrate; the code default is the stored default. `useTemporaryVisibility` forces on the overlays a contour tool picks while that tool is open: plane and sketch for circle, rectangle, polygon, polyline, extrude, revolve, loft, and sweep; plane only for workplane. The rail buttons show on for that span. Confirm, X, Esc, and opening another tool release the hold and restore the previous value of each toggle. A tap during the tool is kept for that toggle. While the Plane tool is open the overlay draws the three reference planes (XY, YZ, and ZX) with that part's existing user planes, including when the rail was off. A selected face hides those three reference planes until the face is deselected (an X, Y, or Z pick, or another plane); user planes stay. That hide does not touch the rail. Closing the tool without a rail tap restores the previous rail value, so the reference planes return to the visibility they had before the tool opened. A face tap, or an X, Y, or Z pick, draws a translucent preview of the new plane at the construction-plane size (`CONSTRUCTION_PLANE_SIZE`, the same quad a confirmed plane uses) and at the frame Confirm would write. Offset and the angle fields move that preview. Add plane writes that frame and closes the card. There is no helper line and no left Plane rail. X closes without writing. The sketch plane square stays undrawn. `golden:plane-tool` covers the open, the face-selected hide, the deselect show, and the preview at 390×844 and 1280×800. `golden:workplane-add` covers Add plane at those sizes. Cut, Draft, Hole, and sheet metal pick a face, a world plane, or their own sheet quads, so they do not force these overlays on.
- **Fillet / Chamfer card.** Tangent / Clear / Undo / Confirm, on the shared feature card. **Undo** undoes the last edge pick only (`popLastEdgeSelection`); it is not the CAD script Undo. **Clear** drops every pick. **X**, Escape, mode switch, or any dismiss without Confirm exits and clears all edge picks (no sticky selection). The card does not show a hard-edge warning. Strategy helper text is not shown. The standalone edge card (`'data-edge-selector': 'standalone'`) is Tangent / Undo / Clear and has no Confirm. Its **X** clears the picks and leaves edge pick. Its **Undo** removes the last selected edge only (same `popLastEdgeSelection`). In this card the hit target is at least 44 CSS pixels (`EDGE_FILLET_HIT_RADIUS_PX`): a shorter edge is extended 22px past each end for the pick test only, and a tap still has to fall inside the finger slop of that segment (at least 44px). Several edges inside the radius resolve to the nearest in screen space, so a long edge that is closer still picks. Hover and the click use that test. The stroke (`paintEdgeLines`, `EDGE_HOVER_CORE_PX`) is the real edge. Other edge picks stay on the 32 / 40px slop. `golden:fillet-edge-hit` covers a sheet corner and a filleted box at 390 and 1280.
- **Multi-part edge picks.** Fillet and Chamfer picks accumulate across parts. A pick on another part still retargets (graphs, strip, Monaco), but the session keeps the edges already picked; every other mode still clears on a switch. Each pick carries its `partId`, and its points and face / boundary ids stay in that part's frame and mesh. Selection identity is part + vertex key (`sameSelectedEdge`), so B's `0-1` never toggles A's. Picks on the active part draw on the pick mesh; picks on another part draw at that part's position (a hidden part's are kept, not drawn). The live blend and the seeded radius shown in the chip read the active part's picks; easy / hard class is computed on Accept and is not shown; the chip counts parts and checks each part's chain. The untouched size is `defaultFilletRadius`: 2 mm in every display unit, so inches show 0.0787. Edge length and the part box do not change it, and chamfer uses the same seed. The size slider runs from 0.5 mm to 25 mm on a log curve, the same physical range in inches. A typed size outside that range is kept and the thumb sits on the nearer end. `golden:fillet-default-radius` covers the fixed seed, including a thin sheet that stays at 2 mm. On Accept an untouched part gets that same 2 mm (`partEdgeParams`). A typed radius (`radiusTouched`) applies to every part. The helper-sheet Fillet and Chamfer, and the feature-edit radius, use the same seed and slider as the mode card.

- **Adapter interface** (`githubAdapterInterface.js`). All async, `repo = { owner, name }`, repo-relative paths. Text is a UTF-8 string; a mesh is a `Uint8Array` or `ArrayBuffer`. `getViewer`, `getRepo`, `createRepo({ name, private })`, `listBranches`, `getBranch`, `createBranch(repo, name, fromSha)`, `deleteBranch(repo, branch)`, `listTree(repo, ref, { prefix })`, `readFile(repo, path, ref)`, `readBlob(repo, sha)`, `commitFiles(repo, { branch, message, files, baseSha })`, `compare(repo, base, head)`, `squashMerge(repo, { base, head, message })`. `commitFiles` writes and deletes (`{ path, delete: true }`) as **one** commit; with `baseSha` it refuses with `GitAdapterError('non_fast_forward')` when the branch moved (G3 uses this to branch off). `compare` returns `identical | ahead | behind | diverged`, ahead/behind counts, `mergeBaseSha`, and the merge-base→head file list. `squashMerge` writes one new commit on `base` whose tree is `head`'s tip and whose parent is the current `base` tip (caller must ensure head is ahead-only). Errors are `GitAdapterError` with `not_found | name_exists | non_fast_forward | invalid | unauthorized | not_a_vault`. `assertGithubAdapter` checks the surface; a real App adapter must pass it. Nothing outside an adapter may call the GitHub API, and the user token will only ever live in the browser.

- **Real adapter** (`githubAdapter.js`, `createGithubAdapter`). Same interface via GitHub REST / Git Data API with `Authorization: Bearer <user token>`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`. `createRepo` is `POST /user/repos` (private, `auto_init: false`). **Empty-repo first commit:** Git Data `POST /git/blobs` returns 409 on a repo with no refs; `commitFiles` detects no branch head and bootstraps via Contents API (`PUT …/contents/{path}`), which creates `main`. A single-file first write stops there; a multi-file write then builds the full tree with Git Data and force-updates the ref to one root commit (`parents: []`) with the intended message — same contract as the mock and as findOrCreateVault / Move to Git seed. On 401/403 it throws `unauthorized` with GitHub's message and `X-Accepted-GitHub-Permissions` when present. Inject `fetchImpl` in tests. `kind: 'real'`. No secrets in the module — the token is passed in from the browser.
- **OAuth / token** (`githubAuth.js` + `backend/routes/github.js`). - **Find-or-create** (`vault.js`, `vaultNames.js`). Default name is `surfcad-vault` (`LEGACY_VAULT_NAME` is `surfcad`). With no custom rename, candidates are the stored `user.vaultName` (when set), then `surfcad-vault`, then legacy `surfcad`. A candidate counts only when `surfcad.json` is `{kind:'surfcad-vault', version:int}`. A marked legacy repo is adopted and `surfcad-vault` is not created. An unmarked or empty legacy repo is `not-a-vault`: it is not seeded and nothing is created. An unmarked or missing stored name falls through. An unmarked `surfcad-vault` is never seeded; a later marked legacy repo can still be adopted, and create is refused because the default name is taken. Create + seed runs only when no marked vault and no unmarked legacy/`surfcad-vault` occupant exists, and only the empty repo this call just created is seeded (`seed: true` on that commit). The handle is GitHub's `name` (`infoFromRepo`), not the string we asked for. Emptiness is **default branch has no commit** (`getBranch`), never `size === 0` alone. A custom rename-field name looks up that repo only, with the same seed rules. `create: false` only looks. A `name_exists` race re-looks instead of seeding a repo we did not just create.
- **Marker guard.** Every real-adapter write re-reads `surfcad.json` first: `commitFiles` (contents PUT and ref PATCH), `createBranch` (ref POST), `deleteBranch` (ref DELETE), `squashMerge` (ref PATCH). A stale open-tab handle whose repo is no longer marked throws `not_a_vault` and writes nothing. `flushSyncQueue` checks again on every flush, before `commitFiles`. On refusal the outbox ops stay `queued` (not dropped, not marked failed) and the error is surfaced (`Upload Error` when the flush result carries `code: 'not_a_vault'`). - **Vault name on the user.** Mongo `User.vaultName` (string). The schema default (`backend/db/vaultNameDefaults.js`, no mongoose) returns `surfcad-vault` only while the document is new; on hydrate it returns nothing, so existing documents stay unset. Sessions use connect-mongo. There is no settings UI and no migration script. `storedVaultNameFromUser` reads the raw field (not the mongoose getter), so an old account is not handed an empty `surfcad-vault` before the legacy repo is considered. Resolution writes the adopted name back. After resolve, the client `PUT /api/auth/vault-name` with the GitHub token; the server checks the marker and stores GitHub's name. `GET /api/auth/me` returns `user.vaultName` or `null`. - **IndexedDB and the outbox.** Local mode autosaves in `surfcad-assembly`. Git mode writes that store and appends to `surfcad-sync` before a push. **Clear local cache** empties both, plus the editor draft, the SurfDB model cache, the `surfcad-assets` mesh cache, and the `surfcad-part-thumbs` thumbnail cache, then reloads. It does not push or delete the remote repo. Kept: the sessionStorage GitHub token, the auth session, the `surfcad-scs` catalog, and checkout / game-wins settings. See `docs/vault-schema.md`.
- **Mesh assets.** A part may have `<Part>.mesh` beside its script (`assemblies/<Name>/<Part>.mesh`, or `parts/<Part>.mesh`). `parseVaultPath` classifies that file as an `asset` of that part. Save, rename, and delete carry the mesh with the script (`buildCommitFiles`, `readRenameEntries`, `planDeleteAssembly`, `deletePartFromRepo`). `commitFiles` posts binary content as a Git blob with `encoding: 'base64'` (text stays `utf-8`, including the empty-repo Contents bootstrap). Assets are read with `readBlob` (`GET /git/blobs/:sha` after the tree resolves the sha), never Contents GET. A write over 40 MiB throws `VaultFileTooLargeError`. A file over 20 MiB sets `large` on the file and `largeFiles` on the commit (`onLargeFile` when passed). Pull stores the bytes in IndexedDB `surfcad-assets`, keyed by the git blob sha `sha1("blob " + len + NUL + bytes)`. `putAsset(bytes)` returns that sha; `getAssetBytes(sha)` returns a `Uint8Array` or null; `clearAssetCache()` is what Clear local cache calls. The `surfcad-sync` outbox stores those bytes as a `Uint8Array`, not a string. Commits can take `assets: { [meshPath]: Uint8Array }` through `assembleCommitFiles` / `buildCommitFiles`. Git Save passes unsynced `importMesh` bytes that way.
- **Local mesh upload.** The Parts ribbon Upload creates a new part and does not overwrite the open script. The name is the file stem (`Bracket`, or `Bracket (2)` when that name is taken). STL, OBJ, and 3MF parse in the browser. A triangle soup is welded (exact positions, then a 0.0001 grid) before the manifold constructor, because an STL repeats each corner. STEP/STP still use `/api/convert/step`. A raw file over 32 MiB is rejected before parse. The stored mesh reuses the vault caps (reject over 40 MiB, warn over 20 MiB). `.mesh` is little-endian, 20-byte header then the arrays with no padding: magic ASCII `MESH`, version uint32 `1`, `numProp`, vert float count, tri index count, then float32 `vertProperties` and uint32 `triVerts`. `putAsset` stores those bytes. The part record (not `.surf.json`) maps `'<Name>.mesh'` to the sha and keeps `meshSynced: false`. The script is `return importMesh('<Name>.mesh');`. `importMesh` runs in the worker from arrays resolved on the main thread for every part, including parts that are not active. A missing asset fails that part only. Legacy `__importedManifolds` scripts still load from SurfDB. Even in a git assembly the new row is a bare local id, `isSynced: false`, and is not enqueued. Download exports the selected row as 3MF (its run mesh, otherwise the leftover, otherwise one run of that id). A hidden or failed part shows a message and writes no file. Signed-in rows (`useAuthState().signedIn`, including reauth) with an unsynced mesh show `local only` (`data-part-mesh-local`). `githubConnected` only changes the title: vault waiting, or GitHub still needs to reconnect. Signed-out rows have no badge. A git Save sets `meshSynced` when the commit lands, which clears the badge.
- **Vault mesh save.** Git Save commits each unsynced `importMesh` whose bytes are still in the asset cache. `getAssetBytes(sha)` supplies them as `assets: { [meshPath]: Uint8Array }`. A new upload is placed in `assemblies/<Name>/<Part>.js` beside `<Part>.mesh` (a taken path uses `Name (2)`). A part that already lives under `parts/` keeps that path. An existing `parts/<Part>.mesh` whose blob sha differs is not replaced; the row stays `local only` and a toast names the path. Over 40 MiB rejects the Save and toasts the limit (`VaultFileTooLargeError`, `The converted mesh is N MiB. The limit is 40 MiB.`). Over 20 MiB warns and still commits. The outbox stores the bytes, so an offline Save retries them. The badge clears only after that commit lands.
- **Vault mesh open.** Opening or reloading a part whose script calls `importMesh` binds that name to the sibling blob sha. Bytes come from the asset cache first, then `readVaultAsset` (`readBlob`), and a fetch is stored with `putAsset`. Clear local cache drops the cache only; the next open reads the blob again and the mesh still renders.
- **Vault mesh rename, delete, and who may commit.** Renaming or deleting a part from the repo moves or deletes its `.mesh` in that same commit (`.mesh` is an `asset`). Signed out, or with no usable GitHub token, Save does not commit and the mesh stays on this device. A reauth boot is read-only and does not commit. Save after reconnect does.
- **Editor draft ↔ part binding.** `saveEditorDraft` stores the active **part id** with the buffer. The pointer is localStorage `surfcad.lastAssembly`, per user id: `{ name, activeId, source, savedAt }`. `activeId` may still be a legacy `local:` row id; comparisons use the bare id. The working copy is global IndexedDB `surfcad-assembly` / store `assembly` / key `current`. A slow `/api/auth/me`, a slow vault resolve (stored `User.vaultName`, then `surfcad-vault`, then a marked legacy `surfcad`), or an IndexedDB timeout does not install or save the stock demo (`Part (1)` in `Assembly`) and does not enqueue `surfcad-sync`. Git mode waits until that open finishes (`bootGateRef`). Signed out, or a session refresh that truly fails while `/me` is unauthenticated, clears the part and assembly chips and writes nothing. Signed in with no usable GitHub token (**reauth**: missing, expired, or `POST /api/github/oauth/refresh` returning 404/405) reopens a real cached assembly read-only and does not write it back. The stock demo is not that cache: the title stays empty and a reconnect prompt is shown. Nothing is seeded. The chip, Open, and this boot share one phase (`useGithubSession`).

## SendCutSend sheet metal

Touch-first sheet-metal mode that designs against live SendCutSend (SCS) stock. SCS has no quote/cart API; the public catalog + specs JSON is the contract.

- **Data source.** `src/utils/scs/scsCatalog.js`. `https://sendcutsend.com/llm-search-specs/` links `https://cdn.sendcutsend.com/specs/sendcutsend-catalog-v1.2.json` and `…/sendcutsend-specs-v1.2.json`. The CDN sends `Access-Control-Allow-Origin: *`, so the browser fetches directly (no proxy, no credentials). `schema_version` is soft: unknown keys are ignored, missing ones become `null`.
- **Join.** `joinScsCatalog` joins on `sku`; specs-only SKUs are dropped, catalog rows without specs still load (DFM `null`). Per-SKU record: `{ sku, name, category, thicknessIn, thicknessMm, gauge, inStock, services[], bendable, cuttingProcess, minPartIn, maxPartIn, bend: { radiusIn, kFactor, bendDeductionIn, minFlangeIn, minFlangeBeforeIn, maxAngleDeg, reliefDepthIn, minCornerReliefIn, maxBendLengthIn, minFlatIn, maxFlatIn, … } | null, dfm: { minHoleIn, minBridgeIn, minHoleToEdgeIn, minHoleToBendIn } }`. SCS lengths stay inches; only `thicknessMm` is mm.
- **Cache.** `loadScsCatalog` + `scsCatalogStore.js` (IndexedDB `surfcad-scs`, one entry, separate from CAD data). Fresh (< 24 h) → cache only. Older → refetch; on failure (offline / CORS / 5xx / timeout) the stale cache is used and the picker says so with Retry. No cache and no network → empty list + Retry. IDB errors never block the network path.
- **In stock.** Material = distinct `name` (bendable first; a name with no in-stock SKU is still listed). Gauge = every SKU of that material, thinnest first; out-of-stock gauges stay visible, disabled, labeled “out of stock”. Start designing still requires an in-stock SKU.
- **SKU on the part.** Start designing binds `part.sheetMetal = { sku, name, thicknessIn, gauge }` on the assembly row (`setPartSheetMetal`). It rides `serializeAssembly` (local IndexedDB doc) and `.surf.json` (git; optional key, validated), so reload and Commit keep it and binding marks the assembly dirty.
- **Mode entry.** Left rail **Shape** → Sheet Metal button (`data-sheet-metal-button`, a blue plate with a bend line and a bent flange, same blue as the other Shape tools; same row as Profile / Extrude; there is no separate Sheet section and no second copy on the right rail) → `SheetMetalPicker` (≥16px selects, 44px targets). Start designing is disabled until an in-stock SKU is picked. `sheetStarterScript(record)` is the default base flange (Top, SKU thickness, 100×60 mm raised to the SKU minimums). Start writes that script into the editor part only when the part is fresh — empty, comments-only, or only `return part;` (`sheetMetalFresh`, and no sheet block yet) — and a `refreshGen` bump drops a pending cube auto-run so the flange is what paints. A part that already has features (the demo script, a box plus a fillet, anything else) stays the open part: Start binds the SKU and does not rewrite the script, and it does not create a `Sheet (n)` part. Plane-step Accept appends one sheet block after the existing blocks (`part = part.add(sheetMetalSolid(sheetSpec))`, chosen plane, SKU thickness) so every earlier block stays byte-identical and the solid keeps that geometry. ✕ before Accept writes nothing. A `Sheet (n)` part is created only when an assembly is open and no part is active (`handleAddPart(name, { script })`). When no assembly is open, Start seeds `Assembly` / `Part (1)` from the editor buffer and then follows the same fresh and busy rules — it does not invent a `Sheet (n)` part for that case. Run of a non-empty script seeds that same assembly before it builds; an empty mount auto-run does not. An existing sheet block is left in place so Viewport can re-thickness it, keeping the `part.add` form when other features sit outside the block. Spec stays null until Accept when the part does not already have a sheet block. Then Viewport enters `sheetMetalMode` (`{ stage, sku, partId }`); the rail swaps to `SheetMetalRail`, which lists Tab / Bend / Hole / Tap under **Shape**. ✕ on a fresh flange leaves that flange and writes no bends.
- **Sheet model.** `src/utils/sheetMetal/sheetModel.js` is the one source of geometry: the spec (`{ sku, t, r, k, limits, plane, width, height, bends[], tabs[], holes[] }`, mm, limits copied from the SKU so DFM works offline) solves to panel frames (`o, U, V, N`, u/v extents). The same solve feeds the sandbox solid (`sheetSolid.js` → `sheetMetalSolid`), the three.js preview + pick handles (`sheetOverlay.js`) and, unrolled (`solveSheet(spec, { flat: true })`), the flat pattern (`sheetFlat.js`).
- **Sheet material.** Sheet faces (the solid and the overlay panels) are light gray brushed metal (`#c8ccd2`, `MeshStandardMaterial`, metalness 0.35, roughness 0.45, both sides) with a camera headlight in the shader. The scene point light decays to nothing at fit distance, which turned the old Lambert overlay near-black. Other parts are the same off-white (`DEFAULT_PART_COLOR`, `#ECEAE4`), with that headlight, not a per-face normal color. Bend and tab edges are unlit screen-space lines on top of that (see Bends).
- **Script.** One block between `// --- sheet-metal begin/end ---`: a comment, `const sheetSpec = {…one JSON line…};`, then either `let part = sheetMetalSolid(sheetSpec);` (the flange is the whole part) or `part = part.add(sheetMetalSolid(sheetSpec));` (the flange is appended onto earlier features). `composeSheetMetalCommit` rewrites an existing block (keeping the add form when the script has other solids), replaces a fresh buffer, or appends before the trailing `return part;`. The return stays outside the block so a later edit keeps it. An Extrude confirmed on that part is inserted before the return and outside the sheet markers, and unions onto the flange; a study comment that follows the return stays after it (`golden:sheet-extrude`). Without that return the worker throws `Script must return a Manifold object` — that was the S2 commit (#228); the check itself was already strict before the #236 runtime split. Re-entering reads the spec back (`readSheetMetalSpec`). The script marker stays one **Sheet** block. The feature strip and the script rail expand it to Base, each bend, and each tab. Base uses the same bent-plate glyph as the Shape button (`SheetMetalPlate`). The in-card Undo is gone; the strip Undo is the editor step and does not pop the reopen history. On a fresh part this rewrites the starter block. On a part with earlier features this is the first write: the block is appended and unioned. A part that already has a block skips to `edit` and is re-thicknessed to the newly bound SKU.
- **Bends (S3).** In `edit` with the Bend tool, every eligible free edge is a screen-space line (`SHEET_EDGE_LINE` in `sheetOverlay.js`): 2.5 CSS px core at opacity 0.65 (hovered 0.82), 5px halo at 0.16. `LineMaterial` resolution is the canvas CSS size, so the core stays about 5–8 device pixels on a 390px phone at DPR 2–3. Tapping a bend edits it (Delete removes it and its child flanges). An edit card does not take more edges. SKUs without `bending` never open a bend.
- **Side bends.** A flange bends on its tip (`u+`) and its straight sides (`v+`, `v-`). `u-` is not bendable: it is the tangent where the flange meets its own bend. There is no miter; adjacent walls stay separated by the base corner notch. `bendableEdges` is that structural set. `sheetFreeEdges` tries the default bend (90° or the SKU max, the usual quarter-edge length, up) through `bendInterference` (`sheetInterference.js`) and sets `eligible` only when that bend is clear. An ineligible edge is drawn dim (`dimOpacity` 0.22, no halo, no pick box), so it cannot be tapped. A bend that is clear at the defaults can still collide once angle or length moves: the bend card disables Confirm and the body shows the reason (`data-sm-bend-block`), for example "Collides with flange 2 when folded". The check is the flat rectangles (bend strip plus the child) and the flange swept through the fold, sampled from a small angle to the finished pose, not the finished pose alone. Flat overlap says "Overlaps … in the flat pattern". Both run on the main thread beside `solveSheet`. `acceptDraft` refuses the same reason, so a colliding bend is never written.
- **Bend geometry.** Inner radius `r` and `k` from the SKU. Up bends roll about `E0 + (t+r)N`, flips about `E0 − rN`; the bend zone is an annular sector (r … r+t) swept along the edge, the flange a box in the rolled frame. Flat: child panels shift by `BA = θ(r + k·t)`.
- **Reliefs (automatic).** Where two bent base edges meet, both flanges stop `g = max(t, SCS min corner relief) + r` short of the corner and a `g × g` notch is cut from the base corner, so bend lines end in free space. A side bend (`v+` / `v-` on a flange) dead-ends on the parent tangent (`u-`): that end is shortened by the same `g`, and the same square is cut from the parent flange, in that flange's frame and in flat UV. The tip corner is not notched. The notch is not SCS `reliefDepth` (stored, unused). Full-width base flanges need no bend relief; chained tip bends inherit the parent's width.
- **Sidebar (S4).** After the base flange the left rail (`SheetMetalRail`) lists only what SCS makes on the bound SKU under **Shape**, **Tab first**: Tab (always), Bend (`bending`), Hole (always), Csk (`countersinking`), Tap (`tapping`) — `sheetToolsFor(spec)` reads `spec.limits.services`, so gating works offline.   - **Flat + DXF** (`sheetFlat.js`). All flat frames are ± the base axes, so panels, bend strips (`E0 … E0 + BA·d`) and tabs are axis-aligned rectangles in base (u, v); relief notches subtract. A grid sweep returns the union's boundary loops (CCW outer); holes are circles. DXF is R12 ASCII, mm (`$INSUNITS 4`), layer `CUT`, `LINE` + `CIRCLE`, moved to the origin. **Bend lines are not written** (SCS cuts every line in a DXF); they are returned as `bendLines` for later use.
  - **STEP: export pipeline** (`sheetBrep.js` → `brepToStep` in `stepExport.js`). Built from the sheet spec, not from the mesh, so it needs no run and is never stale.
    - The solid is the flat pattern × [0, t], pushed through the fold. Topology comes from the flat grid. Each cell belongs to a piece: a panel with its tabs, or a bend strip `E0 … E0 + BA·d`. A grid edge between two pieces is a bend tangent line (shared, no wall). An outline edge gets a wall. Vertices are keyed by flat point and level, so faces share edges exactly.
    - Geometry: panel → `PLANE`; bend strip → two `CYLINDRICAL_SURFACE`s about the bend axis (inner = SKU bend radius `r`, outer = `r + t`, `same_sense` from which side faces the axis); a strip's side wall → a planar annular sector bounded by two `CIRCLE` edges.
    - Holes are two half cylinders. A countersink adds two half `CONICAL_SURFACE`s (82° default) on the +N face, plus a cylinder below them when the cone stops short of the back face.
    - One `MANIFOLD_SOLID_BREP` / `CLOSED_SHELL`, AP214, mm. The builder throws unless every edge is used once in each direction. A spec whose flat pieces touch where the fold does not would throw too; that case falls back to the mesh writer (`meshToStep`: welded, coplanar-merged, faceted bends) with `step-faceted`, and only that path checks `mesh-stale`.
    - Volume: `sheetExpectedVolume` (flat area·t − holes − countersink cones + bend sector corrections) equals the B-rep.
    - Files: `<part>-<sku>-flat.dxf`, `<part>-<sku>.step`. Check and the handoff say where STEP came from (`data-sm-step-source`). The handoff is where those files download.
  - **Mesh-stale, decided.** The DXF and the spec STEP never read the mesh, so a pending run cannot make them wrong; the old volume warning is gone from the spec path. What can still differ is a hand-edited script: code after the sheet block (an extra `subtract`, a `translate`) changes the 3D part but not the files. `script-extras` warns from the script text (`sheetScriptHasExtras`; Viewport passes `getHelperBuffer()` while export is open).
  - **SendCutSend handoff.** Part-row Order calls `sheetCheckoutRoute(script)` (`src/utils/sheetMetal/sheetCheckout.js`) on the script `scriptsForOrder` already captured. No analytics. It does not call `POST /api/quotes` and does not write or remove a line. **Quote with SurfCAD instead** drops into the normal quote, which can add a line. A line already in the cart stays; a later script edit marks that line stale and the checkout page re-quotes the SurfCAD price. The redirect is that part only. Cart Checkout opens the one page and charges a stored SurfCAD quote. `QuoteModal` checkout mode of an eligible sheet script stays on the SurfCAD quote. The handoff builds STEP from the spec (no mesh is on the quote session). A hard fail, a mixed part, or `part.add` stays on the quote.

**Cart line.** Every line stores `lineId`, `source`, `assemblyName`, `partId`, `surfId`, `partName`, `scriptHash`, `thumbDataUrl`, `qty` (integer 1–999), `options`, `addedAt`, and `updatedAt`. A single-part order stores `model-data.quantity` (integer 1–999, default 1). Copies of one part stack along the shortest side in millimetres, then convert to inches.

`POST /api/orders/create` with one `modelData` is unchanged for checkouts already in flight: it ignores client prices, measures that 3MF, asks UPS for the selected method, and opens one PaymentIntent for server unit × quantity + server shipping + tax, with `metadata.quantity` and `×N` in the description. If the server unit price or the server shipping differs from the client by more than one cent, the response sets `priceUpdated` and the payment step shows “Price updated to $X” with Pay disabled until the user confirms. The client still sends the extended subtotal so an old server that ignores `quantity` charges that amount once.

`POST /api/quotes` (signed in) measures the exported 3MF, ignores client volume, and stores the file with `quoteId`, `quotedAt`, and `quotedUnitPrice` (quantity on the quote is 1). The document expires after 7 days (`QUOTE_TTL_MS`, Mongo TTL on `quotedAt`). Checkout re-quotes when the quote is missing, the script hash differs, or `quotedAt` is over 7 days.

A create body with `lines` (1–20 per order; expand in future) re-measures every line, ignores client money, and writes one order. The checkout page sends that body once. Tax is unchanged: the US state rate on subtotal plus shipping, inside that one PaymentIntent (`order_<id>` idempotency key; metadata is the order id, order number, line count, and a name×qty list with no prices).

Shipping is one combined UPS charge. A simple greedy packer (future packing optimization) puts every line in one box, and when that box would pass 108 in on a side, 165 in length plus girth, or 150 lb it splits the order, rates each box, and sums the rates. Size or weight never blocks the purchase. Mock rates and fail-open address checks are unchanged. `POST /api/shipping/calculate-package` accepts a `lines` preview; create recomputes it.

# SurfCAD agent (MCP)

Drive an open SurfCAD tab through **`packages/surfcad-mcp`**: stdio MCP → loopback WebSocket relay (M1) → `window.surfcad.call`. Every bridge tool name and argument schema comes from [`src/agent/commands.json`](../../src/agent/commands.json) (189 commands, regenerated by `npm run export:agent`; `packages/surfcad-mcp/data/commands.json`, `list_commands`, and relay `GET /tools` list the same names). That file is the full catalog. This page covers the workflow and the key tools only.

Related: catalog and bridge shapes in [docs/agent-export.md](../agent-export.md), save model and tool contract in [docs/git-save-model.md](../git-save-model.md) §3, script helpers in [docs/helper-functions.md](../helper-functions.md), MCP server setup in [packages/surfcad-mcp/README.md](../../packages/surfcad-mcp/README.md). UI text and color: [docs/ui-style-guide.md](../ui-style-guide.md) (shared classes only; never dark text on dark chrome; user-facing copy says Chrome, not Edge).

## Pair

1. Open [https://surfcad.com](https://surfcad.com) (or local dev / `?agent=1`).
2. Open the **profile** chip (top-right AR initials) → **Connect agent**. The profile menu closes and a pairing popup opens. Copy the setup prompt if the relay is not running yet; once the relay is found the prompt hides and the six-character pairing code appears. Esc or a backdrop tap before pairing cancels the attempt.
3. Run `npx surfcad-mcp` in your MCP client with that code (`SURFCAD_PAIRING_CODE` env, or the MCP `pair` tool with `{ "code": "ABCDEF" }`). **Allow** (green check) / **Deny** (grey X) replace the code in the same popup; they never show together. After Allow the popup closes and a green **Agent connected** toast appears.
4. **Read the `pair` result text.** With no webhook registered it carries an onboarding note (a plain `type: "text"` block). Relay this to the user exactly: "To get SurfCAD messages instantly, send me your webhook URL and key. This only needs to be done once. Otherwise I'll check for SurfCAD messages between steps, so replies may lag." If the pair text says **Webhook is active.**, do not ask again. See [In-viewer prompts](#in-viewer-prompts-webhook-or-polling).

**Cursor** (`.cursor/mcp.json` or Settings → MCP):

```json
{
  "mcpServers": {
    "surfcad": {
      "command": "node",
      "args": ["/absolute/path/to/surfcad/packages/surfcad-mcp/bin/surfcad-mcp.js"],
      "env": { "SURFCAD_PAIRING_CODE": "ABCDEF" }
    }
  }
}
```

**Claude Desktop**: same block under `mcpServers` in `claude_desktop_config.json`.

**Claude Code**: `claude mcp add surfcad -- npx surfcad-mcp`.

Optional: `SURFCAD_AGENT_BRIDGE_WS_URL` (default `ws://127.0.0.1:17341`; preview/playtest can pass `?agentBridgeWs=ws://127.0.0.1:PORT` when the relay uses a free port).

## Ids: opaque surf ids only

- **Parts / assemblies.** Get ids from `parts` (`assemblyId`, `activeId`, `parts[].id`), `list_assemblies` (`[{ id, name, open }]`), or the result of `create_part` / `create_assembly`. Shape `yyyy-mm-dd-hh-mm-ss-SSSS-xxxx`.
- Every `part_id` / `assembly_id` argument is that opaque id, **never a vault path or display name**. A path-shaped or unknown id returns `unknown_part` / `unknown_assembly`. A writer given an id other than the active part returns `part_mismatch`. Names are non-unique labels; never use them as keys. No tool takes `path`, and results have no `path` field.
- **Faces.** `list_faces` rows: `id` (`f0`, `f1`, …, one per face a viewport click selects; same on a rerun of the same script, invalid after a remesh), `type`, `center` / `normal` / `axis` / `radius`, `area`, and `key` `{ at, n, area, src?, ord? }` (same as viewport fingerprints). Pass `face_id` **with** its `key` (e.g. `joint_pick`) so a stale id returns `unknown_face` instead of picking another face. Key-based tools (`select_faces`, `paint_faces`, `measure_pick`, `fea_set_force`) take `keys`.
- **Edges.** Prefer grouped `e0`, `e1`, … from `list_feature_edges`; raw mesh edges (`list_edges`) are not stable. Grouped `eN` expands to the UI edge chain.
- **Sketch.** In-contour entities `p0`, `e0`, `a0`, …; a saved contour is `@contour id=c1` in the script, not a sketch prefix.

## Core loop

1. **`status`**: active part id, name, `runState` (`not_run_yet` | `ok` | `failed`), last-run volume / bbox / `bodyCount`, `featureCount`. Over MCP it also returns `webhookRegistered` (boolean, no URL or key), `queued` (prompts waiting for `read_messages`), `counts` `{ queued, delivered, replied, cancelled }`, and `last` (`{ id, state }` of the latest prompt, or `null`).
2. **`parts`** → **`set_active_part`** `{ part_id }`. Feature tools write the **active** part, so activate the target first. `create_part` `{ name?, script?, position? }` adds a part (at the origin unless `position` is set), makes it active, and returns its new id. Without `script` the part starts empty, with no seed cube (`featureCount` 0, `bodyCount` 0, `list_bodies` empty); the first Block (`insert_cube`, `insert_cylinder`, …) or Shape (`insert_make_extrude`, …) creates the body. On an empty part, helpers that need a body (`insert_hole`, `insert_fillet_edges`, `insert_shell`, grid `insert_array3_d`, `insert_cut`, `insert_mirror`, …) return `insert_failed` ("<Helper> needs a body first. Insert a Block … or a Shape …") and write nothing. Existing parts are not rewritten.
3. **Build with feature tools first.** `insert_*` (e.g. `insert_cube`, `insert_hole`, `insert_fillet_edges`, `insert_make_extrude`) and `invoke_helper` `{ id, params?, use_selection? }` insert a helper block on the active part and run it, the same compose path as the UI. Card flows: `pick_begin` → `pick_next` → `pick_done` `{ "accept": true }`, `hole_open` … `hole_commit`, `slot_open` … `slot_commit`, `sketch_begin` … `sketch_commit`, `confirm_feature`.
   - **Move a body**: `insert_move` `{ dx, dy, dz, … }` must name the body: `body_index` or `at` (a centroid) from `list_bodies`, `face_id` or `face` (key) from `list_faces`, or `use_selection: true` with a face selected. With none of these it returns `no_body` and writes nothing; `no_mesh` means the part has not run yet. `list_bodies` `{}` returns `{ partId, bodies: [{ index, at, triangleCount }] }` for the active part's last run. To re-point an existing move, open it, `edit_feature` `{ params: { at } }` with a centroid from `list_bodies`, then `confirm_feature`.
4. **Freehand fallback only: `set_script`** `{ part_id, source }`. `part_id` is required and must be the active part. It writes that part, runs it, and records one undo step when the text changes. It keeps `// @surf-id`. Do not redeclare a reserved helper name (`cut`, `hole`, `shell`, … full list in the `set_script` description); rename your variable.
5. **Check**: `status`, `errors` (structured, same text as the viewport; `feature_failed` rows always carry a `detail` reason), `feature_tree`, `screenshot`. A `confirm_feature` that changes nothing on a part that is still failing returns `ok: false` with the errors.
   - **Remove a feature**: `delete_feature` `{ id | index, confirm? }` (from `feature_tree`) deletes the block and runs the part like `confirm_feature`, so no `run` is needed and one `undo` restores it. Result: `{ deletedId, ok, errors, failures, status, warning? }`; `status` is the fresh `status` object for the part (`runState`, volume, bbox, …).
6. **`history`** reads the stack the feature bar would undo (sketch session, assembly joints, or active part): `entries`, `head`, labels, `canUndo` / `canRedo`. **`undo`** / **`redo`** step that same stack and return `applied` / `reverted` labels. A new committed edit clears redo, like the UI.
7. **Save** only when the user wants it: `git_save` `{ message }` (see below).

**Sheet metal.** `sheet_open` → `sheet_start` `{ sku }` → `sheet_pick` `{ plane: "XY" }` → `sheet_set_params` / `sheet_commit` for base and bends; `sheet_check` / `sheet_refold` for the flat pattern; `sheet_edit` `{ chip_id: "sheet:base" }` to change gauge; `sheet_done` to finish. One `undo` per committed write.

**Paint and measure.** `paint_open` → `paint_set_color` / `paint_faces` `{ keys }` from `list_faces` → `paint_confirm` (session undo via `paint_undo` before confirm). `measure_open` → `measure_pick` `{ face_keys }` → `measure_state` → `measure_clear` / `measure_close` (no write).

**FEA study.** `fea_open` → `fea_set_material` `{ id }` → `fea_set_fixture` / `fea_set_force` `{ magnitudeN, direction, keys }` (N and MPa regardless of the display toggle) → `fea_run` → `fea_results` (`dof`, stresses in MPa, `maxDisplacement_m`). `fea_state` mirrors the open sheet; `fea_back_to_setup` leaves results. An off-scope `part_id` on `fea_pick` returns an error.

**Assemblies.** `create_assembly` `{ name? }` (one empty part with no seed cube, single-flight per tab, no git write), `open_assembly` `{ assembly_id }`, `insert_part` `{ part_id }` or `{ assembly_id }` (insert as reference, same ids; `copy: true` mints a new id and sets `copiedFrom`), `open_part`, `part_get_transform` / `part_set_transform` `{ part_id, position?, rotation? }`, `joint_open` … `joint_commit`.

## Working copy vs git

**Working-copy tools never commit.** That includes `create_*`, `rename_*`, `delete_*`, `insert_*`, `invoke_helper`, `set_script`, `run`, `insert_part`, `open_*`, transforms, joints, and `paint_confirm`. Only these touch the vault:

- **`git_save`** `{ message }`: the one vault content write, same planSave / writeVaultCommit path as the Save button. Clean working copy → `{ status: "clean" }`, no commit. `git_add_to_repo` is an alias; prefer `git_save`.
- `git_move_to_repo` (first Save of a local assembly, consent on a real repo), `git_upgrade_vault`, `git_behind_resolve`, `git_force_overwrite`, and the branch tools `git_branch_create` / `git_branch_switch` / `git_branch_delete` (`git_list_branches` is read-only).

`git_save` errors pass through unchanged ([git-save-model.md §3.7](../git-save-model.md#37-error-contract)): `consent_pending`, `pending_save`, `upgrade_required`, `conflict`, `repo-moved`.

`dirty.unsaved` is working copy vs the last AssemblyCommit (survives reload; rename / hide / remove count; changing `activeId` does not). `dirty.pendingSave` is an offline plan waiting for a second Save.

Assembly and part lifecycle:

- `rename_part` `{ part_id, name }` / `rename_assembly` `{ assembly_id, name }` change the display name only (`moved: false`). The next Save writes the same `parts/<id>.js` / `assemblies/<id>.surf.json`.
- `delete_part` `{ part_id, scope: "assembly" | "repo", confirm? }`: `assembly` drops the row; `repo` also plans a file delete on the next Save, needs `confirm: true`, and returns `part_still_referenced` if another assembly lists the id.
- `delete_assembly` `{ assembly_id, confirm: true, delete_parts? }` deletes the open assembly; `delete_parts` plans unreferenced part-file deletes on the next Save.
- `list_assemblies` returns what the Open picker shows, as `[{ id, name, open }]`: saved assemblies, the open working copy (also before its first Save, and in local mode), and on a legacy vault its name-only folders as `{ id: null, name, legacy: true }` (no opaque id until `git_upgrade_vault`).

## `confirm: true`

**Never** pass `confirm: true` unless the user explicitly asked for that destructive action. Without it these return `confirm_required`:

- `delete_feature` on the feature that declares `part` while later code still uses `part` (the base feature). The refusal carries `details.featureId` and `details.dependents` (count of later features). With `confirm: true` the block is deleted, the later features fail (`ok: false`, `status.runState: "failed"`), and the result adds a `warning` string. Deleting the only feature, or one that does not declare `part`, needs no confirm.
- `delete_part` with `scope: "repo"`
- `delete_assembly`
- `git_upgrade_vault`
- `git_behind_resolve` (`action: "reload"` = Get latest, `action: "branch"` = Save mine to a new branch)
- `git_branch_switch` when the working copy is dirty
- `git_branch_delete`
- `git_force_overwrite`

## Error envelopes

MCP returns JSON text; bridge refusals use `isError: true` with `code`, `message`, and `details`.

| Code | Meaning / what to do |
| --- | --- |
| `not_paired` | No approved relay session. Pair first. |
| `pairing_lost` | Tab or relay dropped; the server re-pairs on its own. Retry in a few seconds (`retryable: true`); ask the user to keep SurfCAD open in Chrome. Do not ask for a new code. |
| `pair_pending` | Waiting for the user to click Allow in SurfCAD. |
| `unknown_part` / `unknown_assembly` | Id not in the open document / vault, or a path or name was passed. Call `parts` or `list_assemblies` and retry with a listed id. |
| `part_mismatch` | `part_id` is not the active part. `set_active_part` first, or pass the active id. |
| `no_assembly` | No open document. `create_assembly` or `open_assembly`. |
| `part_still_referenced` | `delete_part` scope `repo` while another assembly lists the id. Use `scope: "assembly"` or delete those parents first. |
| `confirm_required` | Destructive op without `confirm: true` (including `delete_feature` on the base feature; see `details.dependents`). Nothing was changed. Ask the user; only then retry with it. |
| `consent_pending` | Real-repo write while the consent dialog is up. Nothing was written. Ask the user to click **Allow**, then retry the same call (`details.retry_after_ms`). |
| `real_repo_blocked` | Real-repo write that cannot get consent: headless / automation, or the user denied this session. Tell the user; do not loop. |
| `pending_save` | Offline planned write. Ask the user to Save again when online. |
| `upgrade_required` | `git_save` on a legacy vault. `git_upgrade_vault { confirm: true }` after the user agrees (on a v2 vault it returns `{ status: "already_upgraded" }`, no commit). |
| `conflict` / `repo-moved` | A remote edit overlaps this Save. `git_force_overwrite`, or `git_behind_resolve` `{ action: "reload" \| "branch", confirm: true }`, or stop. |
| `git_only` / `git_blocked` | Vault-only tool (e.g. `open_assembly`, `open_part`, `insert_part`) with no vault, or git is unavailable. `git_move_to_repo` or stay local. |

Geometry failures are not refusals: read them with `errors` (code `feature_failed`, same text as the viewport). Other codes (`unknown_face`, `picker_busy`, `pick_timeout`, …) are listed per command in `commands.json` and [docs/agent-export.md](../agent-export.md).

## MCP-only tools

These live in the `surfcad-mcp` process. They are not in `commands.json`, `list_commands`, or `GET /tools`.

| Tool | Args | What it does |
| --- | --- | --- |
| `pair` | `{ code }` | Pair this server to an open SurfCAD tab via the local relay. |
| `register_webhook` | `{ url, bearer? }` | https only (no credentials in the URL, no localhost, `.local`, private or loopback hosts). Each user prompt is POSTed there, and so is `{ "type": "cancel", "id" }` when the user stops a prompt already delivered; `bearer` (the user's webhook key, 1–4096 chars, no CR/LF) is sent as `Authorization: Bearer <bearer>`. 10 s timeout, one retry, then the prompt is queued. URL and bearer live in process memory only: never written to disk, logged, returned, or sent to the tab. |
| `unregister_webhook` | `{}` | Clear the webhook URL and bearer. Later prompts queue for `read_messages`. |
| `read_messages` | `{ max? }` | Queued in-viewer prompts, oldest first, removed on read. An attached screenshot arrives as the next MCP image content block (`image/png`). May also return cancel items `{ "type": "cancel", "id" }` (see below). |
| `reply_to_user` | `{ in_reply_to, text, final? }` | Plain-text reply to a prompt id. `final: true` closes it. Does not write the model or git. A cancelled id returns `{ "ok": false, "error": "cancelled" }` and nothing reaches the tab. |
| `set_status` | `{ working, id? }` | Tell the tab whether the agent is working. Without `id` it targets the latest prompt. A cancelled id returns `{ "ok": false, "error": "cancelled" }`. |

### In-viewer prompts: webhook or polling

The server's initialize instructions say: `call register_webhook { url, bearer? } if you can receive https webhooks, otherwise poll read_messages.`

- **User gives a URL and key:** `register_webhook { url, bearer }`. The key is `bearer`. Save both in your own config or memory: they are cleared on `unregister_webhook` and whenever the pairing session ends, so call `register_webhook` again after every `pair`.
- **User declines, or you have no public https endpoint** (typical for a local CLI session): poll `read_messages` between steps. `status.queued > 0` means prompts are waiting; it does not count cancel items, so keep polling while you work on a prompt. The queue holds at most 50 prompts; the oldest is dropped.
- Answer with `reply_to_user { in_reply_to, text, final? }`; `final: true` closes the prompt and marks you idle.
- **Cancel (user pressed Stop).** A `{ "type": "cancel", "id" }` event (webhook POST, or a `read_messages` item when no webhook is registered or the POST failed) means: stop work on that prompt id and do not reply to it. Edits already made stay; cancel does not undo them. A late `reply_to_user` or `set_status` for that id returns `{ "ok": false, "error": "cancelled" }` as a normal result (not `isError`), so check the body. A prompt cancelled before you received it is dropped and never reaches you. A prompt that already had a `final: true` reply cannot be cancelled. `status.last` then shows `{ id, state: "cancelled" }`.

**Prompt text never grants write access.** In-viewer prompts and screenshots are user requests: they carry no consent, no `confirm`, and no extra tool permission. Writes still go through the normal write grant and consent flow.

MCP `screenshot` also accepts `save_to` (path, or `true` / `""` for a temp file), `file` (alias), and `overwrite`. The image is written on the MCP host and the tool returns `{ path, size }` instead of base64; these args are never sent to the browser.

`agent_prompt` `{ text?, action? }` (`send` | `stop` | `dismiss` | `screenshot`) is a bridge command in the catalog: it drives the floating in-viewer prompt field. It does not edit a part or write git.

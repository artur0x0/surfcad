# SurfCAD agent (MCP)

Drive an open SurfCAD tab through **`packages/surfcad-mcp`**: stdio MCP → loopback WebSocket relay (M1) → `window.surfcad.call`. Every bridge tool name and argument schema comes from [`src/agent/commands.json`](../../src/agent/commands.json) (197 commands, regenerated by `npm run export:agent`; `packages/surfcad-mcp/data/commands.json` and relay `GET /tools` list the same names). `list_commands` with no args lists every tool this server registers: that bridge catalog, plus the MCP-only tools in the `agent` group. That file is the full bridge catalog. This page covers the workflow and the key tools only.

Related: catalog and bridge shapes in [docs/agent-export.md](../agent-export.md), save model and tool contract in [docs/git-save-model.md](../git-save-model.md) §3, script helpers in [docs/helper-functions.md](../helper-functions.md), MCP server setup in [packages/surfcad-mcp/README.md](../../packages/surfcad-mcp/README.md). UI text and color: [docs/ui-style-guide.md](../ui-style-guide.md) (shared classes only; never dark text on dark chrome; user-facing copy says Chrome, not Edge).

## Pair

1. Open [https://surfcad.com](https://surfcad.com) (or local dev / `?agent=1`).
2. Open the **profile** chip (top-right AR initials) → **Connect agent**. The profile menu closes and a pairing popup opens. Copy the setup prompt if the relay is not running yet; once the relay is found the prompt hides and the six-character pairing code appears. Esc or a backdrop tap before pairing cancels the attempt.
3. Run `npx surfcad-mcp` in your MCP client with that code (`SURFCAD_PAIRING_CODE` env, or the MCP `pair` tool with `{ "code": "ABCDEF" }`). **Allow** (green check) / **Deny** (grey X) replace the code in the same popup; they never show together. After Allow the popup closes and a green **Agent connected** toast appears.
4. **Read the `pair` result text.** With no webhook registered it carries an onboarding note (a plain `type: "text"` block). Relay this to the user exactly: "To get SurfCAD messages instantly, send me your webhook URL and key. This only needs to be done once. Otherwise I'll check for SurfCAD messages between steps, so replies may lag." If the pair text says **Webhook is active.**, do not ask again. See [In-viewer prompts](#in-viewer-prompts-webhook-or-polling).
5. **Call `guide { topic: "start" }`** before the first model call. The MCP server's own `guide` tool returns plain-text topics (`start`, `dialect`, `features`, `selection`, `paint`, `limits`, `camera`, `assembly`; `guide {}` lists them). `dialect` is every script helper by signature, rendered from the helper registry; `list_helpers { names }` returns a helper's full doc and examples. `start` is the build guidance below plus a three-call example; the initialize instructions are a short quick-start that points at it.

**Cursor** (`.cursor/mcp.json` or Settings → MCP):

```json
{
  "mcpServers": {
    "surfcad": {
      "command": "node",
      "args": ["/absolute/path/to/surfcad/packages/surfcad-mcp/bin/surfcad-mcp.js"],
      "env": { "SURFCAD_PAIRING_CODE": "ABCDEF" }
    }
  }
}
```

**Claude Desktop**: same block under `mcpServers` in `claude_desktop_config.json`.

**Claude Code**: `claude mcp add surfcad -- npx surfcad-mcp`.

Optional: `SURFCAD_AGENT_BRIDGE_WS_URL` (default `ws://127.0.0.1:17341`; preview/playtest can pass `?agentBridgeWs=ws://127.0.0.1:PORT` when the relay uses a free port).

## Ids: opaque surf ids only

- **Parts / assemblies.** Get ids from `parts` (`assemblyId`, `activeId`, `parts[].id`, `unjointedParts`), `list_assemblies` (`[{ id, name, open }]`), or the result of `create_part` / `create_assembly`. Shape `yyyy-mm-dd-hh-mm-ss-SSSS-xxxx`. `unjointedParts` lists part ids in no joint when the assembly has two or more parts (empty for a single part; a base part with a fixed joint is omitted).
- Every `part_id` / `assembly_id` argument is that opaque id, **never a vault path or display name**. A path-shaped or unknown id returns `unknown_part` / `unknown_assembly`. A writer given an id other than the active part returns `part_mismatch`. Names are non-unique labels; never use them as keys. No tool takes `path`, and results have no `path` field.
- **Faces.** `list_faces` rows: `id` (`f0`, `f1`, …, one per face a viewport click selects; same on a rerun of the same script, invalid after a remesh), `type` (`planar`, `cylindrical`, or `curved`), `center` / `normal` / `axis` / `radius`, `area`, and `key` `{ at, n, area, src?, ord? }` (same as viewport fingerprints). The result's `frame` is `"local"` on `list_faces`, `list_edges`, and `list_feature_edges`: centers, normals, axes and edge midpoints are the part's own frame even when the part is placed (a crankset at `[430, 0, 290]` still reports its local centers). They match `select_faces` keys. Compose with `part_get_transform` to reach the assembly. The whole list on a detailed part is 100 KB or more, so filter it in the tab: `filter` `{ kind, normalWithin: { n, deg }, minArea, maxArea, bbox: { min, max } }` keeps only faces that match every given field (`kind` is `planar`, `cylindrical`, or `curved`; the top faces are `{ kind: "planar", normalWithin: { n: [0, 0, 1], deg: 5 } }`). `bbox` keeps a face whose triangle bounds overlap the box (part local, mm). A large face is kept when the box covers any part of it, even if its center lies outside. `page` `{ offset, limit }` returns one page. Omitting `page` or `limit` uses offset 0 and limit 100. The result always carries `total` (rows after the filter), `returned`, `offset`, and `limit`, and `nextOffset` when another page remains. Walk pages with `{ offset: nextOffset }` until `nextOffset` is absent. Pass `face_id` **with** its `key` (e.g. `joint_pick`) so a stale id returns `unknown_face` instead of picking another face. Key-based tools (`select_faces`, `paint_faces`, `measure_pick`, `fea_set_force`) take `keys`.
- **Edges.** Prefer grouped `e0`, `e1`, … from `list_feature_edges`; raw mesh edges (`list_edges`) are not stable. Grouped `eN` expands to the UI edge chain. Both set `frame` to `"local"` (same part frame as `list_faces`) and take `filter` `{ between: [faceKeyA, faceKeyB], minLength, maxLength, bbox }` and `page` `{ offset, limit }`. Omitting `limit` returns every remaining row.
- **Catalog.** `list_commands { group }` returns one group of tools (`core`, `feature`, `insert`, `pick`, `sketch`, `document`, `joint`, `paint`, `measure`, `fea`, `sheet`, `git`, `export`, `view`, `agent`) and `list_commands { names }` just those commands; no args is the bridge catalog plus every MCP-only tool this server registers (`pair`, `guide`, `list_helpers`, `reply_to_user`, `set_status`, and the other prompt tools) in the `agent` group.
- **Sketch.** In-contour entities `p0`, `e0`, `a0`, …; a saved contour is `@contour id=c1` in the script, not a sketch prefix.

## How to build

The same text reaches every agent from `guide { topic: "start" }` (the MCP initialize instructions and the `pair` result point at it) and, as a one-line note, from the `insert_*` / `set_script` / `create_*` tool descriptions (`src/agent/buildGuidance.js`). Work in the order of the left helper rail, **Block, Build, Shape, Polish, Move**, across the whole assembly:

1. **Block out first.** Within seconds of the prompt, create every part of the assembly as plain blocks (`create_part`, then `insert_cube`, `insert_rounded_box`, `insert_cylinder`, `insert_sphere`, `insert_tube`, `insert_hex_prism`) at roughly the right size and position (block-out positions are rough; joints set final positions), and take a `screenshot` so the user can approve the layout and proportions before any detail goes in. `insert_rounded_box` `width` is the X size in mm (same axis as `sx`; `width` wins when both are set), `depth` is the Y size in mm (same axis as `sy`; `depth` wins when both are set), and `height` is the Z size in mm (same axis as `sz`; `height` wins when both are set). Never plan silently for long before something appears in the viewport.
2. **Build.** Shape each block into its real form with Build and Shape features: `insert_hole`, `insert_cut`, `insert_boolean`, `insert_shell`, `insert_add_draft`; `insert_cross_section`, `insert_workplane`, `insert_make_extrude`, `insert_make_revolve`, `insert_make_sweep`, `insert_make_loft` (`sketch_*` and `slot_*` for the profiles; Sheet Metal is the last Shape button, `sheet_open`). `insert_hole` and `insert_tap_drill_hole` take `depth`: blind depth in mm, into the part from the face. Omit `depth` for a through hole, which is the default.
3. **Polish.** `insert_fillet_edges`, `insert_chamfer_edges`, `insert_move_face`, `insert_delete_face`.
4. **Pattern and place.** `insert_array3_d` (grid; the Array button sits in Build), `insert_polar_array` (bolt circle; Array Type=Polar), and `insert_pattern_points` (one copy at every hole center and axis from `list_faces`; Array Type=Points) for repeats and hardware, then `insert_move`, `insert_rotate`, `insert_center`, `insert_align`, `insert_mirror` for bodies inside one part. Fix one base part with a fixed joint, then place every part that touches or attaches to another with joint_create (one call creates the joint and solves placement; a cylindrical face is an axis pick; a face_id is never an ambiguous axis). `joint_delete { joint_id }` deletes one joint and records one assembly undo step. Remaining joints are solved again. A part move that this joint does not name stays. Undo restores the joint. **Joint health:** `list_joints {}` returns every joint with `status` (`ok` | `broken` | `conflict`), `reason` when failing (`Face not found on Shaft`), `parts`, `picks` and its value; `status.jointFailures { count, ids }` is the short form. The solve re-runs after every part run, so a remesh that loses a face marks the joint broken at once, the same red chip the strip shows. A part edit (`set_script`, `run`, `insert_*`, `confirm_feature`, …) or a `joint_create` / `joint_commit` that leaves a joint failing which was not failing before returns `warning { code: "joint_broken", joints: [{ id, name, type, status, reason, parts }], hint }` and still succeeds: fix the part so the face comes back, `joint_edit` the joint to new picks, or `joint_delete` it. Use part_set_transform only for parts that touch nothing. Block-out positions are rough; joints set final positions. `insert_polar_array` drills the holes when `boreRadius` is greater than 0 and `boltCircleRadius` is the circle (it must be greater than 0); `boreRadius` 0 copies the body and `boltCircleRadius` 0 (the default) leaves it on the axis. A bolt circle of holes is that tool, not a FEATURE-GAP snippet.

Finish each stage across the whole assembly before starting the next, and take a screenshot after each stage.

**Features first.** Use `insert_*` or `invoke_helper` whenever a feature can do the job. When no feature can, add a **script snippet feature** with `insert_code_snippet` `{ gap, why, script }`: one operation, not the whole part, kept next to the other features in the ribbon. Its block starts with a gap comment in this exact form so the saved parts can be grepped for a feature backlog (`node scripts/feature-gaps.mjs <vault>`); with analytics consent the tab also sends each gap to Sentry once (`category: feature_gap`). `set_script` is only for rewriting a whole part. All three fields are required; an empty one is `bad_args`.

```js
// FEATURE-GAP: <missing feature or option> | <why the existing feature did not work>
// FEATURE-GAP: sweep along 3D path | the frame tube follows a curve and extrude only goes straight
```

**Hardware.** Give each unique fastener type its own part named by its spec (`Bolt M5x12 SHCS`, `Nut M5 nylock`, `Star nut 1-1/8"`); two fasteners are the same type only when size, length, and head style all match. Model one instance per part and pattern it to every place it goes: `set_active_part` the part it fastens, `list_faces`, take the `center` and `axis` of each cylindrical hole face (filter by `radius`). Those values are in the fastened part's frame (`frame` is `"local"`). Compose with `part_get_transform` when the fastener does not share that frame, then on the fastener part `insert_pattern_points { points: [{ at, axis }, …], up: "z" }` with `up` the fastener's own axis (`insert_array3_d` for a regular grid). A bolt circle of holes in the part being drilled is `insert_polar_array { count, boltCircleRadius, axis, boreRadius, boreHeight }`, not a FEATURE-GAP snippet. When the holes move, run the pattern again with the new centers. Never one part that holds every fastener, never a copy-paste loop. Do hardware in the pattern-and-place stage, after the parts it fastens are finished.

## Core loop

1. **`status`**: active part id, name, `runState` (`not_run_yet` | `ok` | `failed`), last-run volume / bbox / `bodyCount`, `featureCount`, and `unjointedParts` (part ids in no joint when the assembly has two or more parts; empty for a single part; a base part with a fixed joint is omitted), and `jointFailures` `{ count, ids }` (assembly joints that do not solve right now; `list_joints` has each with status and reason). **Lean results:** every tool that returns `status` (the `insert_*` tools, `set_script`, `run`, `confirm_feature`, `undo`, `redo`, `git_save`, `status` itself, …) takes `return: "status" | "summary" | "full"`. Over MCP the default is `"status"`: `status.script` is left out, so a result is a few hundred bytes instead of the whole script. `"summary"` adds `status.features` (the feature strip, same ids as `feature_tree`); `"full"` echoes the script. Read the script with `get_script`, or one span of it with `get_script { range: { fromFeature, toFeature } }`. Over MCP it also returns `webhookRegistered` (boolean, no URL or key), `queued` (prompts waiting for `read_messages`), `counts` `{ queued, delivered, replied, cancelled }`, and `last` (`{ id, state }` of the latest prompt, or `null`).
2. **`parts`** → **`set_active_part`** `{ part_id }`. `parts` returns `assemblyId`, `assemblyName`, `vaultLayout`, `activeId`, `unjointedParts`, and `parts` rows. `unjointedParts` lists part ids in no joint when the assembly has two or more parts (empty for a single part; a base part with a fixed joint is omitted). Feature tools write the **active** part, so activate the target first. `create_part` `{ name?, script?, position? }` adds a part (at the origin unless `position` is a rough block-out), makes it active, and returns its new id. When `part_set_transform`, or `create_part` / `insert_part` with a `position`, places a part in an assembly of two or more parts and that part is in no joint, the result carries `warning` `{ code: "unjointed_part", part_id, hint }`. The call still succeeds. Without `script` the part starts empty, with no seed cube (`featureCount` 0, `bodyCount` 0, `list_bodies` empty); the first Block (`insert_cube`, `insert_cylinder`, …) or Shape (`insert_make_extrude`, …) creates the body. On an empty part, helpers that need a body (`insert_hole`, `insert_fillet_edges`, `insert_shell`, grid `insert_array3_d`, `insert_cut`, `insert_mirror`, …) return `insert_failed` ("<Helper> needs a body first. Insert a Block … or a Shape …") and write nothing. Existing parts are not rewritten.
3. **Build with feature tools first, in the order in How to build.** `insert_*` (e.g. `insert_cube`, `insert_hole`, `insert_fillet_edges`, `insert_make_extrude`) and `invoke_helper` `{ id, params?, use_selection? }` insert a helper block on the active part and run it, the same compose path as the UI. Card flows: `pick_begin` → `pick_next` → `pick_done` `{ "accept": true }`, `hole_open` … `hole_commit`, `slot_open` … `slot_commit`, `sketch_begin` … `sketch_commit`, `confirm_feature`.
   - **Picks.** `pick_next` `{ "keys": ["e3"] }` takes a plain grouped edge id (`eN` from `list_feature_edges`) on an edge session. A `keys` item is also a face id (`fN`), a face key, or an edge face pair `{ faceKeyA, faceKeyB }`. `pick_points` `{ "kind": "point", "keys": [{ "at": [10, 5] }] }` is one shot on an open contour (`kind`: `point`, `line`, `arc`, or `ref`). Its keys are a sketch entity id, `{ id }`, or a hole centre `{ "at": [u, v] }`.
   - **A named face pick survives rebuilds; anything else is single-use.** Every successful rebuild (each `insert_*`, `set_script`, `undo`) replaces the mesh. A face pick that carries a name (`select_faces { names }`, or a click on a face a helper built) is found again on the new mesh by that name, so one pick serves several `use_selection: true` inserts. Edge picks and faces with no name (a hull, a freehand `Manifold.*`) clear, because they index the mesh that was replaced; pick again before the next insert. With nothing selected that insert returns `no_selection` and writes nothing; the result's `usedSelection` tells you whether the selection was used. Omit `use_selection` to take the helper default (the +Z top face, every convex edge).
   - **Pick by name.** `list_faces` rows carry `name` (`feature.role[k]`, from the helper that built the face: `cube1.top`, `boss.side`, `extrude2.wall[3]`), and `filter { feature, role, name }` narrows by it (`{ feature: "boss" }`, `{ role: "top" }`). `select_faces { names: ["boss.top"] }` selects that face itself, and `select_edges { names: ["plate.top~boss.side"] }` the edge where two named faces meet (raw `list_edges` rows carry `name`). A named pick is written into the script by name: `insert_hole` emits `facesNamed`, `insert_fillet_edges` / `insert_chamfer_edges` emit `edgesOf` (the edges around that face only, concave ones skipped), so an upstream edit fails loudly instead of re-targeting a neighbour. `insert_chamfer_edges` does that for a named face even when the pick is irregular. A face pick with no name that is not planar or cylindrical is refused (`insert_failed`), not every convex edge of the part. A chamfer that would split the solid fails as `feature_failed` (the message says it split the solid) and the part stays as it was. Faces no helper stamped (a hull, a freehand `Manifold.*`) have no name and keep working by key.
   - **Add a contour.** `sketch_add` also takes `params` (extra contour params, merged over the tool defaults), `centers` (rectangle: place by centers), and `polygonPreset` (alias of `polygon_preset`; applied only for the polygon tool).
   - **Edit a saved contour.** A `contour:<id>` chip in `feature_tree` has no edit card: `open_feature` reopens it in the contour sketch (`sketchOpen: true`). `edit_feature` `{ params }` patches that sketch with profile keys (`points` `[[u, v], …]`, `radius`, `segments`, `width`, `height`, `centered`, `polygon_preset`, or `tool`; only the keys you send change) and `confirm_feature` saves and closes the sketch, rewriting the contour by id so every extrude, revolve, loft or sweep that names it rebuilds. `cancel_feature` closes the sketch without writing (`sketchClosed: true`). The next `mode` sees that close. **`sketch_edit`** `{ contour_id, ops: [{ op, … }] }` does the whole thing in one call: it reopens the contour, applies `profile` (the keys above), `add`, `dimension`, `constrain` (the `sketch_dimension` / `sketch_constrain` fields, with ids from `list_sketch_entities`), `delete` and `undo` ops in order, then saves and closes it and returns the contour's entities. Dimensions and constraints are saved inside the contour (`solveContour`), so the sketch stays parametric across runs and reopens with them; `list_sketch_entities` lists them with their ids. While a saved contour is reopened, `sketch_dimension` / `sketch_constrain` answer `live: true` (applied to the sketch, written by the confirm) instead of writing a step of their own. A failing op is an error with `details.op` (its index) and the hint; nothing is written and the sketch is closed. Extrude distance, revolve angle and the like are edited on the feature that uses the contour, not on the contour.
   - **Move a body**: `insert_move` `{ dx, dy, dz, … }` must name the body: `body_index` or `at` (a centroid) from `list_bodies`, `face_id` or `face` (key) from `list_faces`, or `use_selection: true` with a face selected. With none of these it returns `no_body` and writes nothing; `no_mesh` means the part has not run yet. `list_bodies` `{}` returns `{ partId, bodies: [{ index, at, triangleCount }] }` for the active part's last run. To re-point an existing move, open it, `edit_feature` `{ params: { at } }` with a centroid from `list_bodies`, then `confirm_feature`.
   - **Rotate a body**: `insert_rotate` `{ axis, angle, center?, … }` names the body the same way as `insert_move` (`body_index`, `at`, `face_id`, `face`, or `use_selection: true`; none is `no_body`). `axis` is `x` / `y` / `z` or `[ax, ay, az]`, `angle` is degrees (right-hand rule, default 90), `center` is `[x, y, z]` mm or omitted for the body's own centroid. The Rotate button sits directly below Move. To change a rotate, open it, `edit_feature` `{ params: { angle, axis, center, at } }`, then `confirm_feature`.
4. **Freehand fallback only: `set_script`** `{ part_id, source }`. One operation no feature can do, starting with `// FEATURE-GAP: … | …` (How to build). `part_id` is required and must be the active part. It writes that part, runs it, and records one undo step when the text changes. It keeps `// @surf-id`. Do not redeclare a reserved helper name (`cut`, `hole`, `shell`, … full list in the `set_script` description); rename your variable.
5. **Check**: `status`, `errors` (structured, same text as the viewport; `feature_failed` rows always carry a `detail` reason), `feature_tree`, `screenshot`. For a screenshot, `select_clear` → `camera_set` → `screenshot`. World views look along fixed axes (`right` has the camera on +X, so for a vehicle modelled along X it is the front); `camera_set { view: "side" }` and `{ view: "front_of_model" }` read the assembly's longest horizontal extent instead, and an explicit `position` + `target` never rolls. A `confirm_feature` that changes nothing on a part that is still failing returns `ok: false` with the errors.
   - **Remove a feature**: `delete_feature` `{ id | index, confirm?, part_id? }` (from `feature_tree`) deletes the block on the **active** part and runs it like `confirm_feature`, so no `run` is needed and one `undo` restores it. A face pick does not change the part. `part_id` is an opaque surf id of another row (a path or name is `unknown_part`). Result: `{ deletedId, ok, errors, failures, status, warning? }`; `status` is the fresh `status` object for the part (`runState`, volume, bbox, …).
6. **`history`** reads the stack the feature bar would undo (sketch session, assembly joints, or active part): `entries`, `head`, labels, `canUndo` / `canRedo`. **`undo`** / **`redo`** step that same stack and return `applied` / `reverted` labels. On the assembly stack one undo is one action: undoing a joint leaves a part move that joint does not name. A new committed edit clears redo, like the UI. After a run past its budget (`crash.reason: "timeout"`) the worker is replaced; `undo` waits for it, re-runs the restored script, and reports that run, with `status.script` the restored script. A `status.stale: true` means the run never reported and the numbers are the previous run's: call `run` again.
7. **Save** only when the user wants it: `git_save` `{ message }` (see below).

**Sheet metal.** `sheet_open` → `sheet_start` `{ sku }` → `sheet_pick` `{ plane: "XY" }` → `sheet_set_params` / `sheet_commit` for base and bends; `sheet_check` / `sheet_refold` for the flat pattern; `sheet_edit` `{ chip_id: "sheet:base" }` to change gauge; `sheet_done` to finish. One `undo` per committed write.

**Paint and measure.** `paint_open` is safe straight after `create_part` or `set_active_part`. It waits up to 1.5 s (polls every 50 ms) for the viewport to take paint mode: a part switch may still be settling, and agent-opened cards stay held while an agent prompt is being worked. If paint mode is still closed, the result is `not_ready` with `details.reason` (`prompt_working` or `mode_not_ready`) and `details.retryable: true`, and the message says to retry `paint_open`. It does not return `open: false`. Already open returns `{ open: true, already: true }`. Game mode is `bad_view` and does not wait. Then `paint_set_color` / `paint_faces` `{ keys }` from `list_faces` → `paint_confirm` (session undo via `paint_undo` before confirm). For a whole part or one set of faces, `paint { color, keys?, part_id? }` runs that sequence in one call (open → colour → part or faces → confirm; `part_id` is made active first); a failure after the mode opened cancels the session and names the step. An instance with no colors entry of its own is drawn with the definition's paint. An entry on the instance replaces that paint entirely (part color and face colors together). `measure_open` → `measure_pick` `{ face_keys }` → `measure_state` → `measure_clear` / `measure_close` (no write).

**FEA study.** `fea_open` → `fea_set_material` `{ id }` → `fea_set_fixture` / `fea_set_force` `{ magnitudeN, direction, keys }` (N and MPa regardless of the display toggle) → `fea_run` → `fea_results` (`dof`, stresses in MPa, `maxDisplacement_m`). `fea_state` mirrors the open sheet; `fea_back_to_setup` leaves results. An off-scope `part_id` on `fea_pick` returns an error.

**Assemblies.** `create_assembly` `{ name? }` (one empty part with no seed cube, single-flight per tab, no git write), `open_assembly` `{ assembly_id }`, `insert_part` `{ part_id }` or `{ assembly_id }` (insert as reference, same ids; `copy: true` mints a new id and sets `copiedFrom`; `instance: true` with a `part_id` already in the open assembly adds a **part instance**: another placement with its own id, name, pose and visibility that shares the script, run and undo history of its definition, so edit any one and all rebuild from one run; `parts` shows such rows with `instanceOf` and returns `unjointedParts`, `delete_part` on one keeps the script while another row places it, and `position` is a rough block-out; the Parts list's **Add instance** button on a row is the same operation), and `open_part`. Fix one base part with a fixed joint, then place every part that touches or attaches to another with joint_create (one call creates the joint and solves placement; a cylindrical face is an axis pick; a face_id is never an ambiguous axis). `joint_delete { joint_id }` deletes one joint and records one assembly undo step. Remaining joints are solved again. A part move that this joint does not name stays. Undo restores the joint. **Joint health:** `list_joints {}` returns every joint with `status` (`ok` | `broken` | `conflict`), `reason` when failing (`Face not found on Shaft`), `parts`, `picks` and its value; `status.jointFailures { count, ids }` is the short form. The solve re-runs after every part run, so a remesh that loses a face marks the joint broken at once, the same red chip the strip shows. A part edit (`set_script`, `run`, `insert_*`, `confirm_feature`, …) or a `joint_create` / `joint_commit` that leaves a joint failing which was not failing before returns `warning { code: "joint_broken", joints: [{ id, name, type, status, reason, parts }], hint }` and still succeeds: fix the part so the face comes back, `joint_edit` the joint to new picks, or `joint_delete` it. Use part_set_transform only for parts that touch nothing. Block-out positions are rough; joints set final positions. `part_get_transform` `{ part_id }` reads a placement and `part_set_transform` `{ part_id, position?, rotation? }` writes one (translation mm, intrinsic XYZ Euler degrees, one assembly undo step). `joint_create` `{ type, picks: [{ part_id, face_id, key }], name?, value_mm?, sense?, opposed? }` creates and solves one in a call (`fixed` takes one pick, a whole part `{ part_id }`, a face or an edge; `coincident`, `parallel`, `perpendicular`, `distance`, `angle`, `concentric`, `symmetric` take two, one per part; `planar` is `coincident`) and returns `jointId` and `placements` (each picked part's position and rotation after the solve); a pick that does not resolve is `unknown_part` / `unknown_face` and a joint the solver refuses is `joint_unsolvable` with `details.reason` and, when more than one axis matches, `details.candidates` (`id`, `origin`, `direction`, `radius`). Copies of one cylinder count as one axis, so a concentric joint commits on an instance or a pattern. Nothing is written and no card is left open either way. The Joints card (`joint_open` / `joint_pick` / `joint_commit`) stays as the advanced path. When `part_set_transform`, or `create_part` / `insert_part` with a `position`, places a part in an assembly of two or more parts and that part is in no joint, the result carries `warning` `{ code: "unjointed_part", part_id, hint }`. The call still succeeds.
   - **Fixed.** On the Joints card (the advanced path), one pick and no second reference: a whole part, a face, or an edge (a cylindrical face is stored as an axis). `b` is an error. `joint_pick` `{ "part_id": "p1" }` alone, or with `kind: "part"`, picks the whole part and suggests `fixed`, so `joint_set_params` is optional and `joint_commit` writes it. A part pick that also has `face_id` or `key` is `bad_args`. A single face does not suggest Fixed: `joint_set_params` `{ "type": "fixed" }` after `face_id` plus its face `key`. An edge is a valid Fixed target in the joint, but `joint_pick`'s published `key` is a face key (`at`, `n`, `area`), not an edge key (`at`, `dir`).

## Working copy vs git

**Working-copy tools never commit.** That includes `create_*`, `rename_*`, `delete_*`, `insert_*`, `invoke_helper`, `set_script`, `run`, `insert_part`, `open_*`, transforms, joints, and `paint_confirm`. Only these touch the vault:

- **`git_save`** `{ message }`: the one vault content write, same planSave / writeVaultCommit path as the Save button. Clean working copy → `{ status: "clean" }`, no commit. `git_add_to_repo` is an alias; prefer `git_save`.
- `git_move_to_repo` (first Save of a local assembly, consent on a real repo), `git_upgrade_vault`, `git_behind_resolve`, `git_force_overwrite`, and the branch tools `git_branch_create` / `git_branch_switch` / `git_branch_delete` (`git_list_branches` is read-only).

`git_save` errors pass through unchanged ([git-save-model.md §3.7](../git-save-model.md#37-error-contract)): `consent_pending`, `pending_save`, `upgrade_required`, `conflict`, `repo-moved`.

`dirty.unsaved` is working copy vs the last AssemblyCommit (survives reload; rename / hide / remove count; changing `activeId` does not). `dirty.pendingSave` is an offline plan waiting for a second Save.

Assembly and part lifecycle:

- `rename_part` `{ part_id, name }` / `rename_assembly` `{ assembly_id, name }` change the display name only (`moved: false`). The next Save writes the same `parts/<id>.js` / `assemblies/<id>.surf.json`.
- `delete_part` `{ part_id, scope: "assembly" | "repo", confirm? }`: `assembly` drops the row and does not commit. `repo`, after `confirm: true`, deletes `parts/<id>.js` in one commit and returns `assemblies` naming every other assembly that uses the part. A failed scan is `delete_refused` and writes nothing. Those other assemblies are not rewritten.
- `delete_assembly` `{ assembly_id, confirm: true, delete_parts? }` deletes that assembly whether it is open or not. After confirm, a committed assembly is one commit that deletes `assemblies/<id>.surf.json`. `delete_parts` also deletes `parts/<id>.js` when no other assembly on the branch references that id. A never-saved open assembly is removed from the working copy only. The result lists assemblies that use its parts. Nothing is written until `confirm: true`.
- `list_assemblies` returns what the Open picker shows, as `[{ id, name, open }]`: saved assemblies, the open working copy (also before its first Save, and in local mode), and on a legacy vault its name-only folders as `{ id: null, name, legacy: true }` (no opaque id until `git_upgrade_vault`).

## `confirm: true`

**Never** pass `confirm: true` unless the user explicitly asked for that destructive action. Without it these return `confirm_required`:

- `delete_feature` on the feature that declares `part` while later code still uses `part` (the base feature). The refusal carries `details.featureId` and `details.dependents` (count of later features). With `confirm: true` the block is deleted, the later features fail (`ok: false`, `status.runState: "failed"`), and the result adds a `warning` string. Deleting the only feature, or one that does not declare `part`, needs no confirm.
- `delete_part` with `scope: "repo"`
- `delete_assembly`
- `git_upgrade_vault`
- `git_behind_resolve` (`action: "reload"` = Get latest, `action: "branch"` = Save mine to a new branch)
- `git_branch_switch` when the working copy is dirty
- `git_branch_delete`
- `git_force_overwrite`

## Error envelopes

MCP returns JSON text; bridge refusals use `isError: true` with `code`, `message`, and `details`. Over `surfcad-mcp` every error payload also carries `hint` (one sentence: the next call to make) and, for the codes with a longer story, `see` naming its guide topic (`guide { topic: "errors.<code>" }`, for example `errors.no_selection`, `errors.feature_timeout`, `errors.not_paired`; `errors.sweep_path` covers a sweep insert with no edge to follow). `errors` rows inside a result (`feature_failed`, `feature_timeout`, `geometry_worker_crashed`) and the `crash` record carry the same `hint`. A hint the tab sent itself is kept.

| Code | Meaning / what to do |
| --- | --- |
| `not_paired` | No approved relay session. Pair first. |
| `pairing_lost` | Tab or relay dropped; the server re-pairs on its own. Retry in a few seconds (`retryable: true`); ask the user to keep SurfCAD open in Chrome. Do not ask for a new code. |
| `pair_pending` | Waiting for the user to click Allow in SurfCAD. |
| `unknown_part` / `unknown_assembly` | Id not in the open document / vault, or a path or name was passed. Call `parts` or `list_assemblies` and retry with a listed id. |
| `part_mismatch` | `part_id` is not the active part. `set_active_part` first, or pass the active id. |
| `no_assembly` | No open document. `create_assembly` or `open_assembly`. |
| `delete_refused` | The delete was refused (the scan of other assemblies failed, or the id is missing) and nothing was written. Tell the user the message. Do not retry until they ask. |
| `confirm_required` | Destructive op without `confirm: true` (including `delete_feature` on the base feature; see `details.dependents`). Nothing was changed. Ask the user; only then retry with it. |
| `consent_pending` | Real-repo write while the consent dialog is up. Nothing was written. Ask the user to click **Allow**, then retry the same call (`details.retry_after_ms`). |
| `real_repo_blocked` | Real-repo write that cannot get consent: headless / automation, or the user denied this session. Tell the user; do not loop. |
| `pending_save` | Offline planned write. Ask the user to Save again when online. |
| `upgrade_required` | `git_save` on a legacy vault. `git_upgrade_vault { confirm: true }` after the user agrees (on a v2 vault it returns `{ status: "already_upgraded" }`, no commit). |
| `conflict` / `repo-moved` | A remote edit overlaps this Save. `git_force_overwrite`, or `git_behind_resolve` `{ action: "reload" \| "branch", confirm: true }`, or stop. |
| `git_only` / `git_blocked` | Vault-only tool (e.g. `open_assembly`, `open_part`, `insert_part`) with no vault, or git is unavailable. `git_move_to_repo` or stay local. |
| `not_ready` | `paint_open` waited 1.5 s and paint mode is still closed. `details.reason` is `prompt_working` or `mode_not_ready`; `details.retryable` is true. Retry `paint_open`. |

Geometry failures are not refusals: read them with `errors` (code `feature_failed`, same text as the viewport). One feature block that runs past the 30 s budget fails alone: the worker is replaced, the part is rebuilt without that block, its chip is marked failed, and the `errors` row has code `feature_timeout` with `featureId`, `featureType`, `featureLabel`, `elapsedMs`, `budgetMs`, and a `detail` naming the recovery (fewer edges: the picked face's edges or an explicit edge list instead of every convex edge; a smaller radius; lower segments). Edit, delete, or undo that feature; the rest of the part is unchanged. `status.featureMs` (and `ms` on `feature_tree` rows) is the kernel time each block took on the last run, so check it before adding to an already slow part. Edits are incremental: the worker restores every leading block whose script prefix is unchanged from its cache and re-runs only the edited block and the ones after it (`status.cache` gives `blocks`, `hits`, `misses`; restored blocks carry `cached: true` on `feature_tree`), so append polish features at the end rather than editing early blocks, and keep clocks and randomness out of blocks (such a block, and every block after it, runs every time). A kernel crash (out of memory, a wasm abort, or a run past its 30 s budget outside any block or after three retries) is one `errors` row with code `geometry_worker_crashed`, `reason` (`wasm_abort` | `out_of_memory` | `timeout` | `worker_lost`), and `workerRestarted: true`; the mutate result also carries `crash`. The geometry worker was already replaced and other parts kept building, so do not ask for a reload and do not retry the same script: simplify that part, lower segment counts, or split it up, then run it again. `parts` returns `unjointedParts` (part ids in no joint when the assembly has two or more parts; empty for a single part; a base part with a fixed joint is omitted) and its rows carry `runState` (`not_run_yet` | `ok` | `failed`) and `crash` for every part, so a failed part that is not active is visible without `set_active_part`. `status` returns the same `unjointedParts` list. Other codes (`unknown_face`, `picker_busy`, `pick_timeout`, …) are listed per command in `commands.json` and [docs/agent-export.md](../agent-export.md).

## MCP-only tools

These live in the `surfcad-mcp` process. They are not in `commands.json` or relay `GET /tools`. `list_commands` with no args lists every tool this server registers, including these (in the `agent` group).

| Tool | Args | What it does |
| --- | --- | --- |
| `pair` | `{ code }` | Pair this server to an open SurfCAD tab via the local relay. |
| `guide` | `{ topic? }` | Plain-text agent guidance from the server, no pairing needed. `guide {}` lists the topics with one line each; `guide { topic: "start" }` is the build guidance plus a worked example; the other topics are `dialect` (every script helper by signature, from the registry), `features`, `selection`, `paint`, `limits`, `camera`, `assembly`, and one `errors.<code>` recovery per error code an error payload's `see` names. Each answer's second text item names the matching resource. An unknown topic is `unknown_topic` with the list and a `hint`. |
| `list_helpers` | `{ names?, group?, match?, page? }` | The script helper registry as JSON, no pairing needed: `name`, `group` (`blocks`, `shapes`, `build`, `polish`, `place`, `faces`, `fasteners`, `vectors`, `legacy`), `signature`, `params`, one-line `description`; with `names` the full `doc` and `examples` too (unknown names in `missing`). `match` is a name or description substring; `page { offset, limit }` slices; the result carries `total`, `returned`, `groups`. Every `insert_*` description ends with `Writes (defaults): <the code the block carries at default arguments>`. |
| `register_webhook` | `{ url, bearer? }` | https only (no credentials in the URL, no localhost, `.local`, private or loopback hosts). Each user prompt is POSTed there, and so is `{ "type": "cancel", "id" }` when the user stops a prompt already delivered; `bearer` (the user's webhook key, 1–4096 chars, no CR/LF) is sent as `Authorization: Bearer <bearer>`. 10 s timeout, one retry, then the prompt is queued. URL and bearer live in process memory only: never written to disk, logged, returned, or sent to the tab. |
| `unregister_webhook` | `{}` | Clear the webhook URL and bearer. Later prompts queue for `read_messages`. |
| `read_messages` | `{ max?, wait_ms? }` | Queued in-viewer prompts, oldest first, removed on read (this acks them). `wait_ms` (0 to 25000) long-polls: with an empty queue the call waits up to that long for a prompt or cancel before answering, so an idle agent polls once every 25 s instead of spinning. An attached screenshot arrives as the next MCP image content block (`image/png`). May also return cancel items `{ "type": "cancel", "id" }` (see below). Every response includes `recent`: the last 50 prompts this session received, oldest first, each `{ id, state }` (`queued`, `delivered`, `replied`, or `cancelled`), held in memory only. `acked` is only the ids this call removed. When you finish the task from a prompt you received here, send the closing reply below. |
| `reply_to_user` | `{ in_reply_to, text, final? }` | When you finish a task started from the SurfCAD in-viewer prompt pane, send a closing reply with reply_to_user (final: true) summarising what was done, so the user gets confirmation. On failure or partial completion, say what was done, what failed and why, and what is left. Plain text for a prompt id this session received. Does not write the model or git. `final: true` also marks you idle. An `in_reply_to` that was never delivered to this session is an error `unknown_prompt` and nothing is sent to the tab. A cancelled id returns `{ "ok": false, "error": "cancelled" }` and nothing reaches the tab. |
| `set_status` | `{ state?, label?, working?, id? }` | Tell the SurfCAD tab which phase the user's prompt is in. `responding` (alias `typing`): you are reading or writing an answer; the chat stays open with bouncing dots. `building` (alias `working`): you are creating or editing geometry; the chat collapses and the field shows "Agent is working...". Call `set_status { state: "building" }` only once you have everything you need and are actually creating or editing geometry. Do not call building to list parts, faces, edges, or transforms, or for status or read_messages. A model-changing tool also enters building if you skip this call. ### Guide resources

The same topics are MCP resources: `resources/list` returns one row per topic (`surfcad://guide/<topic>`, `text/plain`, `_meta.version` = the `surfcad-mcp` package version) and `resources/read { uri }` returns the topic text, so a host that pre-loads or pins resources can carry the guide without a tool call. `guide { topic }` and the resource share one source.

### In-viewer prompts: webhook or polling

The server's initialize instructions start with: `call register_webhook { url, bearer? } if you can receive https webhooks, otherwise poll read_messages.` The next sentence is: When you finish a task started from the SurfCAD in-viewer prompt pane, send a closing reply with reply_to_user (final: true) summarising what was done, so the user gets confirmation. On failure or partial completion, say what was done, what failed and why, and what is left. The sentence after that is: Call set_status { state: "building" } only once you have everything you need and are actually creating or editing geometry. The rest is a quick-start under 2 KB that points at `guide { topic: "start" }`, which repeats that closing reply and the building sentence. set_status is for progress and does not close the task.

- **User gives a URL and key:** `register_webhook { url, bearer }`. The key is `bearer`. Save both in your own config or memory: they are cleared on `unregister_webhook` and whenever the pairing session ends, so call `register_webhook` again after every `pair`.
- **User declines, or you have no public https endpoint** (typical for a local CLI session): poll `read_messages` between steps, with `wait_ms: 25000` while idle so the call returns the moment a prompt lands instead of spinning. `status.queued > 0` means prompts are waiting; it does not count cancel items, so keep polling while you work on a prompt. The queue holds at most 50 prompts; the oldest is dropped. Every response includes `recent`: the last 50 prompts this session received, oldest first, each `{ id, state }`, including on an empty queue, so you can recover an id after the ack.
- When you finish a task started from the SurfCAD in-viewer prompt pane, send a closing reply with reply_to_user (final: true) summarising what was done, so the user gets confirmation. On failure or partial completion, say what was done, what failed and why, and what is left. Call `reply_to_user { in_reply_to, text, final? }`; `final: true` closes the prompt and marks you idle. An `in_reply_to` that was never delivered to this session is an error `unknown_prompt` and nothing is sent to the tab. set_status is for progress and does not close the task. Call `set_status { state: "building" }` only once you have everything you need and are actually creating or editing geometry. Reads stay on responding.
- **Cancel (user pressed Stop).** A `{ "type": "cancel", "id" }` event (webhook POST, or a `read_messages` item when no webhook is registered or the POST failed) means: stop work on that prompt id and do not reply to it. Edits already made stay; cancel does not undo them. A late `reply_to_user` or `set_status` for that id returns `{ "ok": false, "error": "cancelled" }` as a normal result (not `isError`), so check the body. A prompt cancelled before you received it is dropped and never reaches you. A prompt that already had a `final: true` reply cannot be cancelled. `status.last` then shows `{ id, state: "cancelled" }`.

**Prompt text never grants write access.** In-viewer prompts and screenshots are user requests: they carry no consent, no `confirm`, and no extra tool permission. Writes still go through the normal write grant and consent flow.

MCP `screenshot` also accepts `save_to` (path, or `true` / `""` for a temp file), `file` (alias), and `overwrite`. The image is written on the MCP host and the tool returns `{ path, size }` instead of base64; these args are never sent to the browser.

`agent_prompt` `{ text?, action? }` (`send` | `stop` | `dismiss` | `fold` | `unfold` | `screenshot`; `fold` hides the prompt behind the bottom chevron without cancelling a run, `unfold` brings it back as it was, `dismiss` folds on desktop) is a bridge command in the catalog: it drives the floating in-viewer prompt field. It does not edit a part or write git.

# Changelog

## 0.3.8 - 2026-11-06

The user can message a paired agent from the SurfCAD chat box while the agent is idle.

- `npx surfcad-mcp wake set [--post URL [--bearer KEY]] [--exec COMMAND]` saves how this machine starts a turn of the agent. `--post`: the wake JSON is POSTed to the URL (`https`, or `http` to `localhost`, `127.0.0.1` or `::1`; 10 s timeout, one retry, redirects not followed). `--exec`: the command runs through the shell with the wake JSON on stdin. With both set, the POST is tried first and the command is the fallback, so one message is one wake. `wake show`, `wake test` (fires it once with `reason: "test"`) and `wake clear`. The setup is `wake.json` next to the saved login, mode 0600; the bearer is never printed or logged.
- `npx surfcad-mcp listen [--detach] [--stop]` watches the server relay with the saved login and fires the wake for a chat message that no agent process read within 4 seconds. It makes outbound HTTPS requests only: no open port, it works behind NAT, and it works when the user is on a phone. Watching never consumes a message: it stays on the server until an agent process reads it with `read_messages`. An agent that is already polling takes the message first and is not woken. A message still unread two minutes after a wake is woken for once more. `--detach` starts the listener in the background and returns; it logs to `listener.log` in the config directory. One listener per config directory.
- The wake JSON: `{ type: "surfcad.wake", v: 1, reason: "prompt" | "test", instruction, prompts: [{ id, text, ts, hasScreenshot? }] }`. The text is a preview. A screenshot is not in the wake; `read_messages` returns it. For `--exec`, `SURFCAD_WAKE=1`, `SURFCAD_WAKE_REASON` and `SURFCAD_PROMPT_IDS` are in the environment, and the message text is on stdin only, never in the command line or the environment.
- A long-lived MCP process fires the same wake itself for a prompt that sits unread in its queue for 4 seconds. That covers the local relay, which has no login to listen with. On the server relay a running listener owns the wake.
- The MCP tells the agent to set the wake up when it installs the package. The initialize instructions say `Install: set up the wake, guide chat A.` `guide { topic: "chat" }` opens with section A, the wake setup (the four steps, both forms, the wake JSON, when it fires); the per-pair `register_webhook` step is now A2, and B, C and D are unchanged. Every `pair` result carries a wake note: with nothing set it lists the steps and says to do them now, without waiting to be asked. `status` returns `wake: { forms, listenerRunning, note }`.
- `npx surfcad-mcp status` also prints the saved wake and whether the listener is running.
- No tool was renamed or removed and no argument changed. `register_webhook` is unchanged; it is still the way for a host with a public HTTPS endpoint, and it still cannot wake an agent whose host starts a fresh process per tool call.
- The server relay is unchanged. The listener uses `GET /agent/prompts` with a pull session, as the HTTPS fallback of 0.3.x already does.

## 0.3.7 - 2026-11-06

- `guide { topic: "chat" }` (also `surfcad://guide/chat`): the in-viewer chat workflow as a requirement, not tips. One normative sequence shared by the tab and the agent: the user message appears, the agent's first tool is `set_status { state: "responding", id }` (the dots; no modeling before it), one short non-final `reply_to_user`, the tab holds that reply about 10 seconds, `set_status { state: "building" }` and/or `post_progress` folds the chat and spins the Bot control, the work, then `reply_to_user { final: true }` (spinner stops, chat reopens), and the user dismisses and reviews. The initialize instructions, the `pair` result, `guide { topic: "start" }`, and the `read_messages`, `register_webhook` and `set_status` descriptions point at it and say it is required after every in-viewer prompt.
- Webhook registration is a required step of that workflow: when the host can receive HTTPS callbacks, call `register_webhook { url, bearer? }` right after every successful `pair` or login, before waiting for a prompt, and again in every new process (the URL and bearer are process memory only, never logged, never returned). The onboarding ask is unchanged. A user who declines a webhook leaves the agent on the required long-poll, never on neither.
- The long-poll fallback is required while connected: `read_messages { wait_ms: 10000 }` in a loop, called again as soon as it returns (`wait_ms` still goes up to 25000), whenever no webhook wakes the agent and as the safety net when one is registered. Keep it running after a final reply, so a second message sent within a minute reaches an agent with no webhook.
- A `read_messages` poll is not activity. It used to restart the 15 minute stall window ("No activity from the agent for 15 min") and send the tab an `agent.activity` frame, so an agent that only long-polled never stalled. It now sends the tab nothing and does not restart that window, with or without `wait_ms`. `set_status`, a model-changing tool, a bridge read, `reply_to_user`, and `post_progress` are activity; `post_progress` now restarts the stall window too (it did not before). Polling still keeps the session connected (the 10 minute presence window), which is what a waiting agent needs.
- 3D modeling guide (`guide { topic: "modeling" }`): the blend order is a required technique for fillets and chamfers alike: draft, then `insert_shell`, then concave fillets and chamfers, then convex ones. Two things that order needs in the app are now stated in the guide and in the `insert_shell`, `insert_fillet_edges` and `insert_chamfer_edges` descriptions. The shell opens every face that faces `openScope` (default `"z"`), so a post, boss or flange standing on such a face is cut loose; open the other side or use `"none"`, and `status.bodyCount` must be 1 straight after the shell. After a shell or a concave blend, pick the blend edges by name (`list_feature_edges`, `select_edges { names }`, `use_selection: true`, or a face pick): the no-selection default (every convex edge) can fail there with `filletEdges: edge is concave` or `chamferEdges: ... split the solid into 2 bodies`, and always does after a concave blend that runs onto a sphere or another doubly curved face. (An app build with the kernel fix of PR 886 no longer fails after a concave fillet on a round post; the guide text holds on either build.)
- The guide lists four shell-after-fillet playtest cases, each run in the app on 2026-11-06 with the result recorded: A, a disc base with a post (every convex edge filleted, then shell: 2 bodies; shell opening `-z`, then the concave edge and the convex edges by name: 1 body at every step); B, a post with a sphere tip; C, a flanged box (fillet then shell: 9 or more bodies; shell first: 1); D, a shelled cup or tube with a chamfer over the rim face (a leg at or above the wall removes the rim face and leaves a ridge; an app build before PR 886 refuses the rim-face pick at any leg with "split the solid"; one named rim with a leg below the wall works on every build).
- Seed part rule: the quick start in `guide { topic: "start" }` and the initialize instructions opened with `create_part`. They now build the first part on `create_assembly`'s `partId`; the modeling topic states the rule (never `create_part` for the first part; `create_part` is for the second part onward) and the outcome (one part after the first body, no empty "Part (1)").
- `mold_status { job_id }`, and heartbeats from long mold analyses. A `mold_fit`, `mold_dfm`, `mold_quote`, `mold_parting`, `mold_side_actions`, `mold_draft`, `mold_wall_map` or `mold_pull` call that is still analysing after about 30 s answers `{ status: "running", stillRunning: true, jobId, command, phase?, percent?, elapsedSec, etaSec?, message }` instead of its result. That is a heartbeat, not the result, and it carries none of the result fields. `mold_status` waits up to about 30 s and answers the next heartbeat or, once the analysis ends, exactly what the original call would have returned plus `jobId`. The analysis keeps running in the tab between calls and is not restarted. An analysis that finishes inside 30 s answers directly, as before. New error `unknown_job`. Every call now returns inside the relay's budgets, so a tab that is awake and computing is not reported asleep. Tab change, ships with the app deploy; the tool is in this package's catalog.
- SurfCAD tab: `sketch_begin` followed by `sketch_add` no longer answers `no_sketch`. The tab dismissed every agent-owned card when its agent session went back to working, and the sketch the agent had just opened was one of them. Working starts on `post_progress`, on `set_status building`, and on the first model change after 60 s idle, so with a fresh `surfcad-mcp` per tool call it fell between `sketch_begin` and `sketch_add` almost every time. The second loop "replacing" the first (`appended: false`) was the same bug: the sketch was gone and a new `sketch_begin` started over. The sketch and the feature slot card now stay open until `sketch_commit` / `sketch_cancel` (`slot_commit` / `slot_cancel`) or the user closes them. Ships with the app deploy.
- Server relay: a finished command's result can be read again for 2 minutes. On the HTTPS fallback the result was removed by the event-stream read, so when that stream did not reach the agent the follow-up poll answered `not_found` ("That command is no longer waiting") for a command the tab had run (seen on `sketch_accept_plane`). Backend change, ships with the backend deploy.
- Server relay: with several SurfCAD windows or devices open on one account, the agent's commands, status, progress and replies go to one window: the one Connect agent was pressed in, or the one the user last sent a prompt from. Other windows still show that an agent is connected and nothing else. Commands used to go to the most recently opened tab and every tab animated. Backend and tab change.
- SurfCAD tab: the phone chat pop-up keeps a visible border and its tail in every state, and stacks above the feature strip when the keyboard lifts it there. Camera, Send and Stop act once per tap: a click arriving a few tens of milliseconds after the tap used to toggle the screenshot back off and turn a Send into a Stop for the prompt it had just sent (a phone message that showed as sent and never reached the agent). The engaged screenshot button is a filled green button.

## 0.3.6 - 2026-11-05

- Server relay: the frame cap (`MAX_AGENT_MESSAGE_BYTES`) is 8 MB, up from 256 KB. A `mold_fit`, `mold_dfm` or `mold_side_actions` result on a real part was larger than 256 KB, so the server dropped the tab's socket ("Max payload size exceeded"), the command came back `tab_asleep`, and a prompt typed while the socket flapped was lost ("Message was not delivered"). Backend change, ships with the backend deploy.

- `guide { topic: "modeling" }` (3D modeling guidelines: build on the create_assembly seed part, shell before fillets, draft before shell, reuse over rebuilding, joints, check bodyCount) and `guide { topic: "molding" }` (design guidelines for high pressure injection molding: draft, wall thickness, ribs, ejector side, slides and lifters, what mold_fit checks, edges, shape). Also served as `surfcad://guide/modeling` and `surfcad://guide/molding`. The molding numbers that have a code constant are pinned to `src/molding` by a test.
- Tool descriptions point at them: `mold_*`, `insert_boss`, `insert_add_draft` ("Molding rules"), `insert_shell`, `insert_fillet_edges` ("shell first, then concave fillets, then convex"), `insert_mirror`, the pattern tools and `insert_part` ("prefer this over rebuilding geometry by hand"). The start topic carries a pointer line.
- `create_assembly` returns `partId` and `partName` for its seed part (plus a `note`) and takes an optional `part_name`. The agent builds the first part on that id and does not call `create_part` for it. A `create_part` straight after `create_assembly`, with no script, reuses the untouched seed and returns `reusedSeed: true` instead of leaving an empty "Part (1)" behind.
- Server relay: a `mold_*` command a tab has taken gets a 120 s budget (`MOLD_COMMAND_MS`) instead of the 30 s asleep hold; `mold_fit` on a real part used to come back `tab_asleep` while the tab was still computing. A command a tab took but did not answer inside its budget is `command_timeout` (new hint; terminal on the HTTPS fallback); a command no tab took is still `tab_asleep` at 30 s. Backend change, ships with the backend deploy.
- SurfCAD tab: the profile avatar no longer spins while the agent works. The prompt chrome and the phone bot button still show the working state.

## 0.3.5 - 2026-11-05

- Sketching while the session is working: `sketch_begin`, `sketch_add`, `slot_open` and `insert_make_extrude` work after a model-changing call or `set_status working`. The tab held every card an agent command opened while its session was working, so `sketch_begin` answered ok with no sketch, the next `sketch_add` was `no_sketch`, and `insert_make_extrude` fell back to its placeholder rectangle (mcp-bugs-2026-11-04 §1). The contour sketch and the feature slot card are the agent's work surface and open regardless; a sketch or slot card that still cannot open answers `sketch_blocked` / `slot_blocked` instead of ok. A second `sketch_add` with a closed profile already drawn is another loop (`appended: true`, `loops`), as it has been since 0.3.4's `sketch_add` loops; the golden `agent-sketch-while-working` covers the whole sequence.
- A tool the paired tab lists but this package's shipped catalog lacks (a tool the app added after this release, like `insert_boss` was for 0.3.4) is forwarded instead of `unknown_tool`: the server asks the tab's `list_commands` once per name and caches the answer. Not paired, or a name the tab does not know either, is still `unknown_tool`. `tools/list` is unchanged; `list_commands` shows every tab tool.
- Server relay: a tab prompt sent while the agent is present but has no socket open (a fresh `surfcad-mcp` per tool call, between calls) is held by the server and reaches the next process. The tab hears `queued` at once. Each new socket is offered held prompts after hello, and an HTTPS-fallback pull is offered them once per process (`GET /agent/prompts?session=<id>`). The process reports them with `agent.prompt.taken { ids }` when `read_messages` returns them or the webhook POST succeeds; the server then drops them. A prompt offered twice to one process is kept once. Presence ending (inactive, `close_session`, revoke, expiry) fails the held prompts back to the tab.
- `reply_to_user` accepts an `in_reply_to` that an earlier process received. An id that is not a prompt id is still `unknown_prompt`.
- `insert_make_extrude` and `insert_make_revolve` extrude the saved contour the agent names (`contour`: the id `sketch_commit` returned, or the binding name), else the newest saved contour no feature uses yet, so a sketch committed just before is the profile. The result carries `contour`. The placeholder rectangle is seeded only on a part with no such contour; an unknown `contour` is `insert_failed`.
- `confirm_feature` with a feature slot card open (`open_feature` on an extrude, revolve, sweep or loft) commits the card like `slot_commit`, so a contour reassigned with `slot_assign_contour` is written; it used to answer ok and write nothing. `cancel_feature` closes an open slot card.
- `set_status` works with no prompt in flight: the SurfCAD tab now keeps a session-level agent state (working, replying, idle) that an explicit `set_status`, every model-changing tool call, and `post_progress` drive, and that returns to idle 60 s after the last one. An agent-started build, or a build run as a fresh `surfcad-mcp` process per tool call, collapses the chat and spins the avatar like a prompt in flight. No new tool and no wire change: the tab reads `agent.status` with or without an `id`, and classifies the bridge calls it runs itself. The description of `set_status` says so.
- `insert_boss` (the Boss button in Build, after Hole; runtime `screwBoss(part, frame, u, v, opts)`; the name `boss` stays free for scripts): a screw boss standing on a face, its base sunk 0.1 mm into the part so the union is one body even with frame float noise, with a tap-drill pilot for `size` (default), a `clearance` hole, or `none`; `dia` defaults to 2.5 × the screw diameter and `holeDepth` to the boss height. Faces are named `boss1.side` / `.top` / `.bore` / `.floor`. Edit card and `edit_feature` read and rewrite the call.

## 0.3.2 - 2026-10-25

- `set_status` tells the tab which phase the prompt is in. `responding` (alias `typing`): you are reading or writing an answer; the chat stays open with bouncing dots. `building` (alias `working`): you are creating or editing geometry; the chat collapses and the field shows "Agent is working...". Call `set_status { state: "building" }` only once you have everything you need and are actually creating or editing geometry. Do not call building to list parts, faces, edges, or transforms, or for status or read_messages. A model-changing tool also enters building if you skip this call. A read never does. A partial reply does not leave building; the final reply, Stop, or a disconnect does. No activity for 15 minutes, while responding or building, shows the stall notice and leaves Stop up. The notice says "No activity from the agent for 15 min — it may have stalled". It does not set idle. The result `state` is the tab value (`responding` and `typing` are `typing`; `building` and `working` are `working`). Legacy form of `state`: `working: true` is building, `working: false` is idle. Joints work while a prompt is responding or building, so `joint_create` does not need `set_status` idle. `list_commands` with no args lists every tool this server registers, including the MCP-only tools (`pair`, `guide`, `list_helpers`, `reply_to_user`, `set_status`, and the other prompt tools) in the `agent` group.
- No activity for 15 minutes, while responding or building, shows the stall notice and leaves Stop up. It does not set idle. The notice says "No activity from the agent for 15 min — it may have stalled". Relayed bridge commands, `set_status`, `read_messages`, non-final replies, and `agent.activity` restart that window; a call still in flight holds it. The next activity clears the notice.
- `reply_to_user` rejects an `in_reply_to` this session never received with `unknown_prompt` and does not send it to the tab. The page also ignores a reply whose id is not a prompt the user sent. `read_messages` includes `recent` on every response (the last 50 prompts in this session, oldest first, `{ id, state }`, memory only), including when the queue is empty, so an id can be recovered after it was acked. `acked` is still only the ids that call removed. `status.last` remains the newest id only.
- `insert_rounded_box` honours `width`, `depth`, and `height` (X, Y, and Z size in mm; the same axes as `sx`, `sy`, and `sz`). The named size wins when both are set.
- `insert_hole` and `insert_tap_drill_hole` take `depth`: blind depth in mm, into the part from the face. Omit it for a through hole, which is the default.
- An instance with no colors entry of its own is drawn with the definition's paint. An entry on the instance replaces that paint entirely (part color and face colors together).
- A cylindrical face is an axis pick, and a `face_id` is never an ambiguous axis. Copies of one cylinder count as one axis, so a concentric `joint_create` commits on an instance or a pattern. A real tie is `joint_unsolvable` with `details.reason` and `details.candidates` (`id`, `origin`, `direction`, `radius`); nothing is written.
- `joint_delete { joint_id }` deletes one joint and records one assembly undo step. Remaining joints are solved again. A part move that this joint does not name stays. Undo restores the joint. An assembly undo reverts one assembly action, so undoing a joint leaves a part move that joint does not name.
- On a v2 vault, `rename_part` and `rename_assembly` change the display name only (`moved: false`) and write no git. The next `git_save` keeps the same `parts/<id>.js` or `assemblies/<id>.surf.json`. After `confirm: true`, deleting a committed assembly removes `assemblies/<id>.surf.json` whether or not it is open, and `delete_parts` also deletes `parts/<id>.js` when no other assembly references that id. A failed scan is `delete_refused` and writes nothing.
- `list_faces` classifies each face as `type` `planar`, `cylindrical`, or `curved` (`filter.kind` is that type). `filter` `{ kind, normalWithin: { n, deg }, minArea, maxArea, bbox: { min, max } }` keeps only faces that match every given field. `bbox` keeps a face whose triangle bounds overlap the box (part local, mm). A large face is kept when the box covers any part of it, even if its center lies outside. `page` `{ offset, limit }` returns one page. Omitting `page` or `limit` uses offset 0 and limit 100. The result always carries `total` (rows after the filter), `returned`, `offset`, and `limit`, and `nextOffset` when another page remains. Walk pages with `{ offset: nextOffset }` until `nextOffset` is absent.
- `cancel_feature` on a reopened saved contour closes the sketch before the call returns (`sketchClosed: true`). The next `mode` sees that close.

## 0.3.1 - 2026-10-25

- Joints are the default assembly path. Fix one base part with a fixed joint, then place every part that touches or attaches to another with `joint_create` (one call creates the joint and solves placement). Use `part_set_transform` only for parts that touch nothing. Block-out positions are rough; joints set final positions. Server instructions, `guide` start and assembly, and the build-flow note on `insert_*` / `create_*` say so. The Joints card (`joint_open` → `joint_pick` → `joint_set_params` → `joint_commit`) stays the advanced path.
- `part_set_transform`, and `create_part` / `insert_part` with a `position`, add `warning { code: "unjointed_part", part_id, hint }` when the assembly has two or more parts and that part is in no joint. The call still succeeds. A single-part document does not warn, and neither does a base part that already has a fixed joint. Bodies, patterns, and `insert_move` inside one part do not warn. `parts` and `status` list the ids still in no joint as `unjointedParts`. `guide { topic: "errors.unjointed_part" }` is the recovery.
- When you finish a task started from the SurfCAD in-viewer prompt pane, send a closing reply with `reply_to_user` (`final: true`) summarising what was done, so the user gets confirmation. On failure or partial completion, say what was done, what failed and why, and what is left. That sentence is in the initialize instructions, `guide { topic: "start" }`, and the `reply_to_user`, `read_messages`, and `set_status` descriptions. `set_status` is progress only and does not close the task.
- The in-viewer "Agent is working..." hint stays until a final reply, an idle / `working: false` status, Stop, or a disconnect. It does not drop back to idle while tool calls are still arriving. No activity for 15 minutes, while responding or building, leaves the prompt pending (Stop stays up) and says "No activity from the agent for 15 min — it may have stalled". Relayed bridge commands, `set_status`, `read_messages`, non-final replies, and `agent.activity` restart that window; a call still in flight holds it. The next activity clears the notice. The pairing approval prompt says "Allow agent to connect".
- `open_feature` stores the edit session even while the in-viewer prompt hides the card. `edit_feature` merges `params` into that session and still does not write the script; `confirm_feature` does. With nothing open the result is `no_feature_edit`. A key the open feature cannot write is `bad_args` and is not stored. `edit_feature` `params` is an open object (`additionalProperties: true`, no nested `properties`) so a strict client can send the feature's own keys (`height`, `at`, `dx`, and the rest).
- `delete_feature` removes the block from the active part, or from `part_id` (an opaque surf id). A face pick does not change the part. A path or display name is `unknown_part`.
- `list_faces`, `list_edges`, and `list_feature_edges` set `frame` to `"local"`. Centers, normals, axes, and edge midpoints are the part's own frame, including when the part is placed, and they match `select_faces`. Compose them with `part_get_transform` to reach the assembly.
- `insert_polar_array` drills a bolt circle when `boreRadius` is greater than 0: that many holes of that radius and `boreHeight`, at `boltCircleRadius` (must be greater than 0, or the insert is `bad_args`), and it does not copy the body. `boreRadius` 0 copies the body; `boltCircleRadius` 0 (the default) leaves that copy on the axis. A bolt circle of holes is that tool, not a FEATURE-GAP snippet.
- `insert_chamfer_edges { use_selection: true }` with a named face writes `edgesOf` for that face's boundary only, including a face the face graph calls irregular. A face pick with no name that is not planar or cylindrical is refused, not every convex edge. A chamfer that would split the solid fails as `feature_failed` and the part stays as it was.
- Parallel `makeLoft` rings and the slices between stations follow a chordal tolerance, 0.0005 of the part's bounding diagonal, clamped to 0.01–0.25 mm. `opts.resolution`, when set, is the maximum polar gap and only adds samples; omitting it does not fall back to a uniform ray table.
- The Script rail button is gone. `insert_code_snippet` no longer points at it. Pattern on points is Array Type=Points and still `insert_pattern_points`.

## 0.3.0 - 2026-10-25

- Helper registry. `data/helpers.json` (a copy of the repo's `src/lib/surfcad/catalog/helpers.json`, refreshed by `npm run export:agent` and pinned by a test) ships with the package. `guide { topic: "dialect" }` is rendered from it: every script helper by signature in ribbon-order groups. New MCP-only tool `list_helpers { names?, group?, match?, page? }` returns the same registry as JSON (`name`, `group`, `signature`, `params`, `description`; full `doc` and `examples` with `names`; `total`, `returned`, `groups`, `missing`). Every `insert_*` description now ends with `Writes (defaults): …`, the code its block carries at default arguments, and `set_script` points at `list_helpers` for the reserved helper names.
- Error hints. Every error payload from this server carries `hint` (one sentence, the next call to make) and, where the code has an `errors.<code>` guide topic, `see` (`guide { topic: "errors.<code>" }`); `errors` rows inside a result (`feature_failed`, `feature_timeout`, `geometry_worker_crashed`) and the `crash` record carry the same. An `insert_failed` for a sweep with no edge to follow points at `sweepPoints` / `makeSweepPath` (`errors.sweep_path`). A `hint` or `retryable` the tab sent is passed through. Guide resources: `resources/list` returns one `surfcad://guide/<topic>` row per topic (`text/plain`, `_meta.version` = this package's version) and `resources/read` returns the text; `guide { topic }` answers name their resource in a second text item, and `guide {}` lists the error topics on one line.
- `read_messages { wait_ms }` long-polls (0 to 25,000 ms): with an empty queue the call waits for the next prompt or cancel before answering. `paint { color, keys?, part_id? }` is a bridge tool that runs paint_open → paint_set_color → paint_part / paint_faces → paint_confirm in one call.
- `camera_set` takes `side` and `front_of_model`, read from the assembly's longest horizontal extent (X wins a tie), and its description says which side each world view looks from; `set_script` says to keep the feature marker blocks.
- `guide` tool: `guide {}` lists plain-text topics (`start`, `features`, `selection`, `paint`, `limits`, `camera`, `assembly`), `guide { topic }` returns one. The initialize instructions are now a quick-start under 2 KB that points at `guide start`, and the `pair` result points there instead of repeating the build guidance.
- Lean results. Every tool whose result carries `status` (the `mutates: true` tools, `undo`, `redo`, `status`) takes `return: "status" | "summary" | "full"`. This server fills in `"status"` when the caller omits it, so `status.script` is no longer echoed on every call; `"summary"` adds `status.features` (the feature strip rows); `"full"` is the previous shape. The page bridge keeps `"full"` as its default. `get_script` takes `range { fromFeature?, toFeature? }` (feature_tree ids) and returns that span of blocks with `range { fromFeature, toFeature, startOffset, endOffset, features }`; unknown ids are `unknown_feature`. Tool text is compact JSON (the indented form was about 2.4 times larger; `list_commands` 240 KB → 99 KB). Needs a tab whose bridge knows `return`; an older tab ignores the argument and still returns the full status.
- Lean lists. `list_faces` takes `filter { kind, normalWithin: { n, deg }, minArea, maxArea, bbox: { min, max } }` and `page { offset, limit }`; `list_edges` and `list_feature_edges` take `filter { between: [faceKeyA, faceKeyB], minLength, maxLength, bbox }` and `page`. Every list result adds `total` (rows after the filter) and `returned`, and `offset` / `limit` with a page; a bad filter or page is `bad_args`. `list_commands` takes `names` (only those rows, unknown ones in `missing`) and `group` (`core`, `feature`, `insert`, `pick`, `sketch`, `document`, `joint`, `paint`, `measure`, `fea`, `sheet`, `git`, `export`, `view`, `agent`, or `all`); each row and each `commands.json` entry carries `group`, and the result carries `total` and `groups` counts.

## 0.2.2 - 2026-10-18

- Bridge catalog matches the host save-model v2 contract. Tools take opaque `part_id` / `assembly_id` only. `set_script` requires `part_id`. `list_assemblies`, `delete_part`, `delete_assembly`, and `rename_assembly` are wired. `insert_part` calls `agentInsertPart`. `GET /tools` on the loopback relay lists the same bridge tools as `list_commands` and `data/commands.json`. `delete_part` scope `repo` and `delete_assembly` require `confirm: true`. Nothing in this package writes git; `git_save` is still the vault write, and its typed errors (`consent_pending`, `pending_save`, `upgrade_required`, `conflict`, `repo-moved`) pass through unchanged.
- In-viewer prompts. `register_webhook`, `unregister_webhook`, `read_messages`, `reply_to_user`, and `set_status` stay in this process and are not host commands. A paired tab sends `agent.prompt`. The process POSTs `{ "type": "surfcad.prompt", ... }` to an https webhook held only in memory, or queues up to 50 prompts. The POST times out after 10 seconds, retries once, then falls back to the queue. Prompt text and screenshots are user content: they grant no write access, and nothing reaches git without an explicit Save or `git_save`.
- Git writes happen only on an explicit user Save or a consented `git_save`. Paint, group edits, insert/open/copy/delete/rename, New Assembly, and coming back online no longer commit, push, assign vault paths, or create the vault repo. Path-less working copies no longer toast `parts[N].path must be a repo-relative path` when capturing a baseline.
- Delete from assembly & repo records the part and mesh paths in a working-copy sidecar (IndexedDB / sync store, not `.surf.json`). Save emits those `fileDelete`s in the same commit. Assembly rename stores the old vault name next to the working copy so a reload reseeds the baseline from the old folder and Save moves it. Browse / branches / toggle do not create a vault (`No repo yet. Save creates it.`). Copy does not assign a repo path until Save. An offline Save stays queued until the next Save.
- The loopback probe uses only the WebSocket handshake (no HTTP GET to 127.0.0.1, which prod CSP `connect-src` blocks). A policy close 1008 / `origin_blocked` is origin rejection; timeouts and close 1006 stay `issue: null` so polling continues. A disallowed Origin completes the upgrade and closes with that policy code instead of HTTP 403, so the browser can tell it apart from a missing relay.

## 0.2.1 — 2026-10-17

- Safari (macOS) can pair. The relay serves a small **SurfCAD local agent bridge** page at `http://127.0.0.1:17341/bridge`; SurfCAD opens it as a pop-up from **Connect Agent** and passes relay traffic through it, because Safari blocks `ws://127.0.0.1` from https pages. The page only talks to allowlisted SurfCAD origins, needs a per-session nonce, cannot be framed, and answers only for a loopback `Host`. If the relay is not running yet, the window keeps retrying (every few seconds, no time limit) and connects once `npx surfcad-mcp` starts. Tab reconnects reuse that same window — they do not open a new one. Closing the window stays **Disconnected** until **Reconnect** (a timer must not reopen it). Pairing still needs **Allow connection** in SurfCAD. Safari on iPhone and iPad is still not supported.
- `git_branch_create` creates the branch and switches the working session to it when the working copy is clean. If there are uncommitted changes, the branch is still created but the session stays on the current branch (same as the Parts Create flow, which does not discard unsaved edits). A failed switch still returns `status: 'created'` with `switched: false` and `switchError`.
- `AgentBridgeHost` is mounted once above App's desktop/mobile split, so a 768px resize does not remount the pairing socket or mint a new `tabKey`.
- Dropped-tab reservations now expire in `hasTab` / `liveTab` (24 h TTL) and an unref'd sweep drops stale Map entries; a later `register_tab` can reuse the code.
- Pairing Allow uses the shared `surface-success` class (`text-on-dark` contrast ≥4.5:1 rest, ≥3:1 hover) instead of `hover:bg-emerald-500`.
- Fixed: when the SurfCAD tab's socket dropped mid-session, the next tool call hung until the MCP client timed out (`-32001`), and later calls failed with `pair_failed` ("No SurfCAD tab is advertising this pairing code"). Tool calls now return `pairing_lost` within about a second while the link is down, with the hint "Open SurfCAD in Chrome and keep the tab open; it will reconnect." A call already in flight is rejected the same way.
- The connection now recovers by itself. The tab reconnects with backoff (and right away when it becomes visible or goes back online), and the server re-pairs with the same code in the background. On Allow the hub stores `{resumeKey, tabKey}` and never forwards the resume secret on `PAIR_REQUEST`; a matching resume from that same `tabKey` auto-pairs at the hub (the tab sees `resume: true`). After a drop the pairing code stays reserved for that `tabKey` (24 h), so another loopback client gets `token_in_use` instead of the secret. A different client with the same code still has to be allowed in SurfCAD. If the process that owned the relay exits, another running `surfcad-mcp` takes over the port. Closing the account panel, or crossing 768px, does not drop the pairing: `AgentBridgeHost` is mounted once on App above the desktop/mobile split. Allow/Deny is a `document.body` portal, so a pairing request still prompts when the menu is closed.
- The loopback probe tells a visible HTTP 403 Origin rejection apart from a timeout. CORS-hidden opaque OK on https is `browser_blocked` (Chrome Local Network Access looks the same), not `origin_rejected`. Timeouts stay `issue: null` so polling continues.
- The relay pings every socket every 5 s and drops any socket that misses a ping (`SURFCAD_AGENT_BRIDGE_HEARTBEAT_MS` to tune it). Drops, heartbeat timeouts and pairing ends are logged on stderr with a timestamp and reason. Pairing codes are redacted and secrets are never logged. Relay logging no longer writes to stdout, where verbose mode used to corrupt the MCP stdio stream.
- `unknown_token` is now reported as `unknown_token` (it used to come back as `pair_failed`). A bridge call that has to pair first waits at most about a second for Allow, then returns `pair_pending`. The `pair` tool returns `pair_pending` after 30 s instead of running into the client timeout.
- New `rename_part` tool `{ part_id, name }`. A vault part moves its committed `.js` in the same folder (`-2`, `-3` on collision) and that part's path/name in `.surf.json` in one rename commit (tip bytes, not the live buffer). Pending script, placement, and other dirty rows stay for the next Save. A path-less part renames locally with no commit. Unknown ids return `unknown_part`. The UI part rename shares that path.
- `git_save` saves like the app's Save button: parts without a vault path get one, and those scripts plus the `.surf.json` land in one commit. It no longer returns `no_repo_path`. The app promotes those paths once (in `assembleCommitFiles`) and adopts the result, so a second Save does not mint `-2` copies. A failed `listTree` aborts instead of occupying nothing. Occupancy includes `.mesh` siblings.
- `git_add_to_repo` works on a multi-part assembly whose other parts have no paths. They are pathed and committed with it instead of failing `.surf.json` validation on every call.
- Git writes on a real repo return `consent_pending` immediately (with `details.retry` and `details.retry_after_ms`) while the consent dialog waits, instead of blocking until the MCP client times out (`-32001`). Retry after the user clicks Allow. Headless tabs and a denied session still return `real_repo_blocked`.
- `create_part` in a git assembly no longer commits on its own; `git_save` writes it behind the consent dialog.
- Agent `create_part` places at the assembly origin (optional `position [x,y,z]` mm). New `part_get_transform` / `part_set_transform` read and set rigid placement (intrinsic XYZ Euler degrees).
- `status` follows the active part after `set_active_part` (`runState` `not_run_yet` | `ok` | `failed`) and reports that part's own volume/bbox, not the last run of any part.
- `set_script` preserves or re-injects the active part `// @surf-id` header.
